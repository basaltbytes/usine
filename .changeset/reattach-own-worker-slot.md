After a restart, a reattached Attempt holds a slot of the Worker it runs on, so that Worker takes no new Attempt beyond its `max_concurrent_attempts` while the reattached one runs. At startup, before any Run's fiber starts, the engine occupies a slot through `StepExecutor.occupy` for each open Attempt whose checkout it keeps for a reattachment, so a Run that arrives while the reattaching Run still reads whether the Attempt is live cannot take that slot. The Run reattaches the Attempt in that slot. When the Run does not reattach the Attempt, the reattachment fails before it acquires the checkout, or the operator cancels the Run before then, the slot is released only once `StepExecutor.interrupt` confirms that the Attempt's parent task stopped, so no new Attempt takes it while that task may still run. A canceled Run whose parent task cannot be confirmed stopped keeps its checkout and slot, and each reconcile tries the stop again. This also holds after another restart: startup stops the parent task of each closed Attempt through `StepExecutor.interrupt` before `StepExecutor.recover`, and when that stop cannot be confirmed, it keeps the checkout and occupies a slot of the Attempt's Worker until a reconcile confirms the stop. A Run that reattaches an Attempt without such a slot passes the Attempt's Worker to `StepExecutor.reserve`, and reads whether the Attempt is live again once it holds the slot, so an Attempt whose parent task stopped during the wait is reconciled instead of reattached. `RunStore.beginAttempt` logs `Reattached Attempt keeps its own Worker, not the reserved one` at error instead of warning.
