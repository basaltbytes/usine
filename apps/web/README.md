# @usine/web

The usine web UI, served by `@usine/server`. Internal — never published.

Needs attention sits at the top of every screen but Overview, where it is the first block: a two-column list of peach-tinted entries, each with its title, its Project, one line of detail, and its actions, such as Approve and Cancel run for a Run waiting for approval, Reset cycle budget, or Discard leftovers. An approval names its Loop and the number and title of the Item its Run works on. The Worker not configured entry shows its whole detail, with its actions below it. An entry about a Run opens its drawer. On the Run page each entry takes one line, its detail shortened with the full text in its tooltip. The list is absent while nothing needs the operator, and the sidebar shows how many entries there are beside Overview and how many concern each Project. The first screen is Overview, at `/`: Needs attention, with `Nothing needs attention` and the time of the last finished poll when it is empty; Running, one row per Attempt in flight with its Item, Loop, Agent, Worker, start time, last activity, and open connectivity warnings in yellow; Stalled, one row per Item a Loop's trigger matches with no Attempt running on it, with the reason as a short fragment, such as `Canceled 2d ago, unchanged since`, and the one action that applies (Approve, Mark answered or Mark resolved, Reset cycle budget, Retry, Run again, or Resume); Recent runs, the 10 Runs that closed last with their outcome and pull request; and one line with each Worker's slots in use and last preflight. A row about a Run opens its Run page. Each empty block says what it would hold, and the blocks show skeleton rows until the page loads. Below `md`, a Stalled row stacks its Loop, reason, and action under the Item. With no Project registered, Overview points to `repos` in `usine.yaml` and offers **Reload configuration**. The sidebar lists the Projects, each with **Board** and **Tasks** under it; the open page's row is highlighted, and the Project's own row opens the Board. A project opens as a horizontal Board whose authored or proposed lanes group the latest GitHub issues and pull requests. Every lane is in one row, and the Board shows every Task the overview returns. Lanes that accept moves come first in their configured order, then the read-only lanes, with the unmatched lane last. The unmatched lane (Unmapped) and lanes that hold only closed Items (Done) open folded into narrow rails showing their name and count; a rail opens into a lane, and the lane's heading folds it back. A lane is a heading with its name, card count, and the labels and Item states that route Items to it, labels in their GitHub colors, above a stack of Task cards; the heading stays in view while the cards scroll under it, an empty lane shows a dashed outline with No tasks, and during a drag the lane under the pointer gets a muted background. With the keyboard, Left and Right move a dragged card lane by lane. Between two adjacent authored label-backed lanes, an arrow at the end of the left lane's heading points to the next lane and names the Loops whose trigger matches a Task of the left lane now, with or without an open Run, and `paused` after a paused one: in blue when one of them has a queued or running Run on the lane's Tasks, in peach when their open Runs all wait for approval. An arrow with no such Loop stays blank. A Task card joins explicitly linked issues and PRs. It shows each member's number and kind, PR for a pull request, the title on at most two lines, and up to three labels other than the lane's own with a count of the rest. When the task has an open Run, or a failed Run that still needs the operator, one line shows that Run's Loop, state, time, and Agent. The time counts from when the Run opened while it is `Waiting` or `Queued`, from when its current Attempt started while it is `Running`, and from the failure once it is `Failed`; its tooltip gives the full timestamp and what it counts from. The line starts with a dot in the state's color, which pulses while the Run is `Running`. Succeeded and canceled Runs stay on the Task page, in the drawer, and in Run history. Failures, with Retry when the failed Run can be retried or Mark answered or Mark resolved for an Agent's question or blocker, merge conflicts, Run action progress, and move progress appear below that line. A stalled Task says why with the same fragment as Overview, after the Loop when no Run line shows it, with the one action that moves it again, such as Approve or Run again; the Board reads `GET /api/desk` for it. Clicking a card opens its Task page, whether or not it shows a Run. The card's menu lists only what applies: each member on GitHub, Open run for the Run the card shows, Run history when the task has other Runs, Approve for a `Waiting` Run, Retry for a `Failed` one, Cancel run after a confirmation for an open one, and Move to with the other writable lanes. Move to is absent when no other writable lane exists and while a move is saving. The menu button names the current issue or PR, whose labels a move changes. With a mouse it appears while the pointer is over the card, while the card has focus, and while its menu is open; on touch screens it is always shown. The drawer header links to the Item and to any pull request the Run produced. Authored label-backed lanes accept drag-and-drop moves; proposed, state-only, and unmatched lanes are read-only destinations. Cards can move only when another writable lane exists. Boards with proposed lanes explain how to enable moves by configuring `repos[].lanes` in `usine.yaml` and reloading the configuration.

A moved card stays in its destination while the label write and GitHub refresh finish. Progress distinguishes saving from a saved move awaiting synchronization; old lane labels are hidden during that wait. Other cards remain available, and navigating between Projects preserves accepted moves. An unrelated label update does not undo a move, while newer lane or Item state takes over normally. The Board checks for updates every second while moves are pending so confirmation and approval prompts appear promptly. Failed writes show their error and refresh authoritative state. The Board scrolls in both directions within the space below the Project heading; both ends remain reachable on desktop and narrow screens.

The Tasks list, at `/projects/<owner>/<name>/tasks`, shows the Board's Tasks as table rows, most recently active first: by when the last Run was last at work, which is its last Attempt's end, that Attempt's start while it runs, or the Run's opening before any Attempt, or, for a Task without Runs, by when GitHub last updated its current Item. The heading counts open and done Tasks, such as `12 open, 176 done`. Each row shows the current Item's number and the Task's title, the current Item's state (Open, Merged, or Closed) and lane, the Loops that ran on the Task in the order they first ran, how many Runs its Items have, the last Run's Loop, state, and time, such as `12m ago`, with a stalled Task's reason under it as on Overview, and the open pull request, or the merged one marked Merged. A row opens the Task page. Open Tasks show by default; **Done** at the right of the heading, with its count, adds the Tasks whose current Item is closed or merged, as the Done lanes hold them, and keeps `?done=1` in the address, so going back to the list keeps them. The columns follow the table's width, not the window's: Loops and Pull request show when the table is at least 896px wide, and below 672px the state and the last Run fold under the title. A project without Items shows `No tasks`.

The Task page, at `/projects/<owner>/<name>/tasks/<number>`, is addressed by the Task's originating Item: its earliest issue, or its earliest pull request when it has none. The number of any of its Items opens it, and the address then names the originating Item. Its header shows that Item's number, linking to GitHub, and the Task's title; under them the state of the current Item, named with its number when it is a pull request, the lane, that Item's labels other than the lane's own, and Needs attention when it applies, with **Move to** at the right while another writable lane exists and no move is saving. **Runs** lists every Run on the Task's Items, newest first, in a table: state, Loop, the Item when the Task has several, Agent, Attempts, how long the Attempts ran, when the Run opened, and the pull request it produced; a failed Run's typed reason and message, who ran it again, and who approved it sit under the Loop. Below 1280px the table keeps the state and folds the other facts under the Loop, and below 640px the state moves there too. A row opens its Run page. A Run waiting for approval shows **Approve** and a failed Run that still needs the operator shows **Retry** in its row; the row's menu lists the other actions that apply, with Cancel run behind a confirmation, and Edit and retry or Edit and run again open the editor under the row. **Pull requests** lists the Task's pull requests with their state and Conflicts with base, each opening on GitHub. **Comments and reviews** lists the comments and reviews the Runs' Attempts posted, whether the Attempt succeeded, failed, or was canceled, with the Item, the Run, and when it was posted, or when its Attempt ended for one recorded before posting times were, each opening on GitHub. Each section that is empty says how it fills. The page refreshes every 2 seconds while one of its Runs can be canceled, every 15 seconds otherwise, and whenever the overview refreshes after a Run action or a move. An Item outside the Board's 500 newest Items shows Task not found.

Opening a Run from a card's menu, Needs attention, Run history, or Run again on the Task page shows its drawer over the current screen. The drawer is short: the Item's number and title, the Run's state, its pull request (the Item itself when the Item is a pull request and the Run produced none) or No pull request, its Loop and Agent, once an Attempt has started a line with the Worker the newest Attempt runs or ran on and the Duration of all its Attempts, counting while one runs, and the actions that apply. Below them one paragraph gives the outcome: the result of a succeeded Run, the typed reason, message, and salvage of a failed one, what a waiting or queued Run is waiting for, or, for a running Run, its current activity and latest message. **Open run page**, or the expand icon beside Close, leads to the Run page; where the browser supports view transitions, the Run's title and state glide from the drawer into the page. Motion stays off under reduced-motion settings.

The Run page, at `/projects/<owner>/<name>/runs/<run>`, carries the whole Run under the same header, whose Worker and Duration line adds the Tokens the Run's sessions used so far. Selecting the token total opens the breakdown per billing pool and per session under each Attempt, with the price the harness put on a pool that has a dollar rate: API keys, and the Claude plan marked as an estimate; the ChatGPT plan says it has no dollar rate. On the left an outline lists the Task and the Event, each with a two-line preview, then every Attempt with its outcome mark, why it began (from the Event, retried by the operator, edited and retried, retried after an infrastructure failure, or started again after a restart, and whether a restart reattached it), its start time, and its duration, which counts up while the Attempt runs. Once the operator approves a Run whose Loop requires approval, the Event entry and the Event in the reader add one line, such as “Approved by octocat · 15 Oct 19:30 · from the UI”, or “from the GitHub Ask” for a 👍 on the Ask. The line has no name when `usine.yaml` names no `operator`, and shows only “Approved” and the time for a Run approved before usine recorded who approved. Runs of a Loop without approval show no such line. The Attempt being read opens to its sessions, the parent and each child with its live status, Hold state, and how long a working session has worked, then to its checkpoints in order: consecutive messages of one session fold into one entry, such as “developer, 14 messages”, which opens to each message named by its first sentence, shortened to a clause or whole words. Blockers, questions, operator messages, Worker and provider notices, and the outcome stay entries of their own, named by who said them; a blocker or the failure that ended the Attempt is red and a warning yellow. As the reader scrolls, the outline opens the Attempt in view and marks the checkpoint at the reading line. Selecting the Task or the Event shows it in full in the reader, the Event with Raw details for its payload; selecting an Attempt, a session, or a checkpoint scrolls the reader there. Below 1024px the outline is a disclosure above the reader, and a finished Run opens with its outcome's time line at the top of the reader.

The reader shows every Attempt as one document. Each Attempt opens with one line naming its Worker, parent model, each child's harness, model, and effort, its account rate-window readings, and whether the operator intervened. Messages from the parent, each child, and the operator follow in order at a 72-character measure, with the time and the speaker in a narrow column. The calls between two messages fold into one line that says what ran, such as “Ran 5 commands · 25s”, with failed and running calls counted. A label change, comment, or review the Agent made on the Run's Item shows as its own line where it happened, under the fold of the calls that made it: “Removed agent-in-progress, added ready-for-review” with each label in its GitHub color, “Commented on #247” or “Reviewed #320” linking to the comment or review. These lines come from the Item's GitHub timeline, not from the commands: only the App's changes made while that Attempt was at work, so a command that changed nothing shows no line. The Run page reads them when it opens, when an Attempt starts or ends, and every 30 seconds while one runs; when GitHub cannot be read, the reader says so above the conversation. A Board move you make while an Attempt works the Item is written by the same App, but usine records each move before sending it, so the reader shows it as yours, like an operator note with its time: “You moved it from Review to Findings on the Board”. Moves made before usine recorded them still show as the Agent's label change. A delegation shows the task the parent gave. The Attempt ends with its outcome: the failure note with its typed reason, including executor defects that require an explicit retry, and the salvage line, or the result of a successful Attempt. The parent's copy of a child's message and a final message that the outcome repeats are shown once, and so are a comment the outcome links and a label change it states in the same words, such as “removed `agent-in-progress`”: only in the outcome. An exhausted child-session budget shows both the configured and attempted counts in the drawer, the reader, and Needs attention. Opening a fold shows each call: tool starts and finishes share one expandable row that identifies the command, file, search, or delegated task. Commands show terminal output, file reads show source, and edits show their patch or before-and-after text in distinct copyable panels. Other tools show labeled parameters and readable results; Raw details exposes the complete input and output. A live Attempt shows its current activity under the last message, and incoming activity follows the latest message until the reader scrolls away; Jump to latest, in its own band at the reader's foot, resumes following. Each Attempt whose earlier history is not yet loaded offers Load earlier, which preserves the reading position.

The Configuration section shows the instance folder as the orchestrator parsed it, read-only, in five pages that fill the panel: **Loops**, **Agents**, **Workers**, **Repositories**, and **Settings**. Each list opens a detail page with the file's long parts beside a rail of its short facts, the rail first on phones. A Loop's page shows its trigger and selector as written, its Agent with the brain, the repositories it selects, approval, cycle limit, permissions, and Step, and its prompt as Markdown with each `{{ }}` expression outlined; its database-backed **Pause** or **Resume** control sits in the heading, and the list offers it on each row. An Agent's page shows its persona and where its parent model and effort come from. A Worker's page shows its connection and Gateway settings, never the admin token, its slots in use, and the last preflight of its own prerequisites and of each harness. A repository's page lists its lanes in Board order with each label as GitHub has it, the labels usine creates there, and the Loops that select it. Settings lists `settings`, `operator`, and the webhooks mode with what each value does. A Loop or Agent file that did not load comes first in its list, and its page shows the parse stage, the message, and how to recover. **Reload configuration** sits in the heading of every page of the section; it loads the instance folder again, and what changed, the files it left out, or why it was refused stays under the heading until it is dismissed or the operator leaves the section. Pause and Resume are absent in setup mode. Needs-setup mode states that newly supplied GitHub App credentials require restarting `usine up` because the running process reads them only at startup.

The app uses React, TypeScript, TanStack Query, TanStack Router, Tailwind CSS, shadcn components on Base UI with Phosphor icons, and shadcn/typeset over react-markdown for prose. Its visual system follows ADR 0015: dark-only on Catppuccin Mocha. Mantle is the page, the sidebar, and the cards; the work panel is base, inset with a 1px hairline; menus, tooltips, and other floating surfaces are surface0. Secondary text is subtext0, and overlay0 marks graphics only because it is too faint for text. Mauve is the one action color: primary buttons, links, focus rings, selection, and the caret. Run states have semantic colors: blue running or queued, peach waiting and Needs attention, red failed, green succeeded, and overlay canceled. Inter sets all text; JetBrains Mono sets ids, item numbers, times, and code.

A fold's summary describes its calls, such as “Edited conversation.tsx · ran tests.” File summaries count distinct recorded paths and distinguish shared basenames with parent directories. Recognized test and build invocations describe what ran; their results remain in the tool details. Long or varied folds use compact counts, and loading earlier inputs fills in missing file and command details. Under the outline, a red count with previous and next controls steps through the loaded errors: what the Run ended with or the operator must read, which is each failed Attempt's outcome, blockers, questions, operator input a session refused, and connectivity warnings still open. A quieter count, such as “12 recovered”, steps through the tool calls that failed while the Agent went on; navigating to one opens the fold and the failed call together.

## Intervening in a Run

The drawer and the Run page header offer the Run actions that apply. On the Run page, a live Attempt has a composer at the bottom of the reader: it messages the parent, or a child once that child is chosen in the outline. **Pause session** waits at the next tool boundary; sending a message resumes it. **Cancel run** asks for confirmation, then stops the entire Attempt.

Messaging a child places a Hold. The child can answer and accept more turns in the same conversation, while the parent continues waiting for its result. **Release child** lets the result return when the child is idle. Each child has its own Hold, and a paused parent does not prevent messaging its children. Held children remain reachable even when their last activity is outside the loaded transcript page. Holds pause the Attempt's elapsed-time budget; reported tokens continue counting toward `settings.max_attempt_tokens` when that ceiling is set. A failed or canceled Attempt shows the salvage branch its unfinished work was pushed to, or the retained worktree path when the push failed.

Failed Runs offer **Edit and retry** with a task editor and roster agent picker. The selected agent supplies its persona and model settings. The new task and agent apply to later Attempts, including automatic infrastructure retries. Attempts show the task and agent they actually used and whether they received an operator intervention. Messages and delivery receipts identify the configured operator in the transcript; the triggering Event remains unchanged.

## Returning to a conversation

Each Run remembers its opened folds and tools and its reading place in this browser. Leaving and reopening the Run page, or refreshing it, returns to the same reader row and position within it; showing the Task or the Event and selecting the same Attempt again keeps the place too. A reader who leaves at latest continues following incoming activity. Wheel, touch, keyboard scrolling and outline navigation take precedence over a pending restore.

The Run page loads up to 20 earlier pages automatically to recover a saved row. If the row is unavailable, a request fails, or recovery reaches that limit, a notice explains that the reader is showing the nearest available activity. Load earlier remains available. Restoring a place, including this nearest-row recovery, preserves unread activity. The update count includes each loaded row changed since the last acknowledged tail once, including a tool result arriving after its start was read. Earlier pages can reveal additional unread rows. Jump to latest, or scrolling to latest, acknowledges those updates; error and outline navigation preserve them.

Bookmarks expire after 30 days. This browser origin retains up to 20 Runs, the most recent 200 disclosure choices per Run, and at most 512,000 characters of bookmark data. Stored fields contain identities, preferences, a row-relative position and the acknowledged transcript sequence. Transcript text and tool payloads remain in the transcript store. If browser storage is disabled or full, the conversation remains usable; returning to a saved place requires available storage. See [ADR 0025](../../docs/adr/0025-run-conversation-reader-bookmarks.md).

## Conversation browser tests

Install the pinned Chromium browser once with `pnpm --filter @usine/web exec playwright install chromium`, then run `pnpm --filter @usine/web test`. The suite runs unit tests in Node and interaction tests in Chromium using the real MessageScroller, Base UI disclosures, sidebar, and browser layout. Board move tests use the actual HTTP client with controlled HTTP responses to replay stale refreshes, failures, concurrent card moves, and navigation during a request. CI installs Chromium and its operating-system dependencies before running the suite. A machine with its own Chromium, such as a Worker built by [`infra/hetzner/cloud-init.yaml`](../../infra/hetzner/cloud-init.yaml), sets `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` to the browser's path instead; `vitest.config.ts` passes it to Playwright as `executablePath`, and `turbo.json` lists it in the `test` task's `env` so that `pnpm test` from the repository root sees it.

## How to add UI

The registry is the component library; the theme is the only place colors and type live.

- **Use a registry component first.** Everything under `src/components/ui/` came from `pnpm dlx shadcn@latest add <name>` (run inside `apps/web`; `components.json` holds the preset). Compose those primitives (`Item`, `Card`, `Badge`, `Sheet`, `Message`, `Collapsible`, `Empty`, …) in screen files. Before writing a new element, check whether a registry component already covers it; the full set is installed.
- **Extend with tokens, not hex.** Colors, fonts, and radii are CSS variables in `src/index.css`, exposed to Tailwind through the `@theme inline` block. A new semantic color is a new token pair there (`:root` and `.dark`) plus one `--color-*` line; screens then use utilities such as `text-run-active`. Never write a literal color in a component.
- **Never hand-roll a parallel component.** No `styles.css`, no ad-hoc button or badge classes. A composition shared by several screens (for example `src/components/status-badge.tsx`) wraps a registry primitive and lives in `src/components/`, next to `ui/`, so the distinction between vendored and composed stays visible.
- **Registry files are ours to edit.** Fix a type or a11y issue in place. They are exempt from the `usine/*` lint rules (see the `.oxlintrc.json` override) because upstream does not follow them, and `knip` treats them as entry files so unused components are not reported.
- **Conversation tools use AI Elements.** `src/components/ai-elements/` adapts the upstream Tool, CodeBlock, and Terminal components to Base UI, Phosphor icons, and the app's tokens; its README records provenance and adaptations. Compose these panels with readable tool content. Complete transport payloads belong under Raw details. shadcn MessageScroller owns conversation scrolling; every direct content row uses a stable `MessageScrollerItem` identity.
- **Markdown goes through `Markdown`.** `src/components/markdown.tsx` renders agent and operator prose with react-markdown inside a `typeset typeset-chat` container; `src/typeset.css` is the unmodified download from https://ui.shadcn.com/typeset.css and the `.typeset-chat` preset in `src/index.css` defines its settings. Source and patches use CodeBlock; command output uses Terminal.
- **Screens are file routes.** `src/routes/` is the TanStack Router routes directory (`__root.tsx` shell, `index.tsx` the Overview page from `src/desk/`, `projects/$owner/$name.tsx` the project layout, `projects/$owner/$name/index.tsx` board, `projects/$owner/$name/runs/$run.tsx` Run page, `projects/$owner/$name/tasks/index.tsx` Tasks list, `projects/$owner/$name/tasks/$number.tsx` Task page, `configuration/route.tsx` the Configuration section around `loops/`, `agents/`, `workers/`, `repositories/`, and `settings.tsx`, whose screens live in `src/configuration/`); the Vite plugin regenerates `src/route-tree.gen.ts`, which is committed and excluded from lint and format. Route files export only `Route`; shared pieces live outside `src/routes/`. The Run drawer is a root search param (`?run=`) so it overlays any screen; route params are lowercase so their file names stay kebab-case.
- **A rebuilt bundle needs no restart.** `@usine/server` reads `index.html` and `assets/*` from `apps/server/dist/web` on every request, so after `pnpm build` a page reload serves the new bundle. GitHub credentials, the `webhooks` block of `usine.yaml`, and some `workers` changes are read at startup only; the rest of the instance folder reloads from any Configuration page.
- **Navigation lives in `src/components/app-sidebar.tsx`**, composed from the `sidebar` registry component; screens render inside `SidebarInset` under a breadcrumb header. The inset panel keeps the viewport's height, and the content below its header scrolls inside it.
- **Pick the page width.** `Page` takes `width="prose"`, the default, which stops content at 768px for prose and short lists, or `width="full"` for tables and side-by-side layouts such as the Configuration section.
- **Keep the scale.** `src/index.css` defines the only five sizes: `text-xs` 12px for captions and meta, `text-sm` 13px for body text and the default, `text-md` 14px for emphasised UI, `text-lg` 16px for section titles, and `text-xl` 20px for screen headings. Other size utilities generate no CSS, and arbitrary sizes are off the scale. Headings are Inter in semibold; `font-mono` is for ids, item numbers, times, and code only. Counts and times use `tabular-nums`. Sentence case everywhere; no uppercase labels.

An exhausted Item cycle budget appears in Needs attention with the participating Loops and counts. **Reset cycle budget** records an explicit answer and refreshes the overview. The runtime fetches current trigger input before opening further work.

Open **Resume details** beside a Claude or Codex child in the Run page's outline to see its saved session id, its worktree, and **Resume this session**, one command to paste in the operator's own terminal. For a local worker it changes into the worktree and resumes the session there. For an ssh worker it runs that command over `ssh -t` to the worker's `destination`, with `-p` when `usine.yaml` sets `port`, quoted once more for the remote shell, and the worktree line names the worker. A worker `usine.yaml` no longer declares gets the local form and a line that says so. The command wraps in the block, and **Copy command** copies it as one line. Resuming needs the harness login the attempt used and the worktree, which attempt cleanup removes. Older transcripts and Pi children show that no saved harness session was recorded.

A Loop or Agent file that failed to load at startup or at a reload appears in Needs attention as **Loop quarantined** or **Agent file not loaded**, with the file and the reason. It stays there until the file is fixed and the configuration is reloaded.

A Worker that `usine.yaml` no longer declares appears in Needs attention as **Worker not configured** while Attempts are recorded on it, with their count; startup doesn't reconcile those Attempts. Declare the Worker again and restart `usine up`, or choose **Discard leftovers**, then **Confirm discard**, to stop tracking them. Discarding removes nothing from the Worker.

Choose **Mark resolved** in a failed Run’s drawer or Run page to clear its Needs attention warning and related Project and Board attention. Open the drawer from Needs attention or Run history. Resolution persists across reloads and restarts; the failed outcome, Attempt details, transcript, and retry controls remain available. A later failed Attempt requests attention again.

Choose **Run again** in a succeeded or canceled Run's drawer or Run page to open a new Run of its Loop on the same Item content, with the Run's task and Agent; **Edit and run again** lets you change them first. The drawer or page then shows the new Run, and its Event says who ran it again, when, and from which Run. When the Item's cycle budget is used up, no Run opens and the actions say so.

An Agent's blocker appears in Needs attention as **\<loop\>: blocked**, with the blocker, and **Mark resolved** lets the Run's Loop act on the Item's newest state. An Agent's question appears in Needs attention as **Question from \<loop\>**, with the question. In its drawer and Run page the button reads **Mark answered**; the Run's Loop then acts on the Item's newest state.
