Polling fetches a changed Item and hashes its payload. A Loop whose `if:` matches creates an Event from that hash, the engine opens a Run for the Event, and the Run's fiber runs the Run's one Step as Attempts until the Run closes.

2. Change detection: `GitHubPolling.changes` ([polling.ts:333](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/github/src/polling/polling.ts#L333)) sends `GET /repos/{owner}/{repo}/issues?state=all&sort=updated&direction=asc&per_page=100` with `If-None-Match`, and with `since=<watermark - 5 s>` once a watermark exists. [ADR 0007](https://github.com/basaltbytes/usine/blob/main/docs/adr/0007-polling-triggers-content-hashed-events.md) relies on GitHub not counting an authenticated 304 against the rate limit. The listing stops after ten pages ([polling.ts:48](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/github/src/polling/polling.ts#L48)) and the next cycle continues from the watermark.

3. Every cycle fetches again every open pull request in the stored cursor, changed or not, because mergeability can change without an `updated_at` change ([ADR 0007](https://github.com/basaltbytes/usine/blob/main/docs/adr/0007-polling-triggers-content-hashed-events.md), [#155](https://github.com/basaltbytes/usine/issues/155)). When GitHub no longer has an Item that only the cursor kept, such as an open pull request or an Item whose Loop failed, because it was deleted, transferred, or is out of the App's reach, the poll logs a warning, drops the Item from the cursor, and revokes its unstarted Runs as it does for an Item that stops matching. It also sets `gone_at` on the Item's row in `usine_item_projections`, which keeps the last payload, and the Board places a gone Item by its closed state, so its card leaves the open lanes. A later poll that observes the Item again clears `gone_at`. The other Items and the cursor continue. The cursor does not keep open issues, so at most once every 10 minutes per repository the cycle asks GitHub whether it still has each issue stored as open, with one GraphQL request per 50 issues and an aliased `issue(number:)` field for each, and treats an issue that comes back null, deleted or transferred, as above ([#391](https://github.com/basaltbytes/usine/issues/391)). The re-check of a queued Event also marks an issue gone (step 5 of [The Run fiber](#the-run-fiber)).

4. `observeItem` ([repository-sync.ts:215](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/polling/repository-sync.ts#L215)) reads the Item's cycle generation, fetches its GraphQL payload slice (`GitHubPolling.snapshot`, [polling.ts:442](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/github/src/polling/polling.ts#L442)), and stores it as the Item's projection. The content hash is the SHA-256 of the payload as canonical JSON with `createdAt`, `updatedAt`, `closedAt`, `mergedAt`, and `submittedAt` removed ([content.ts:7](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/github/src/polling/content.ts#L7), [polling.ts:549](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/github/src/polling/polling.ts#L549)).

5. `evaluateItem` ([loop-evaluation.ts:52](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/polling/loop-evaluation.ts#L52)) evaluates each Loop of the Item's stream. The dedup key of an issue or pull request Event is the JSON array `[loop, repository, number, contentHash]`, with the cycle generation appended once it is above zero ([loop-evaluation.ts:29](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/polling/loop-evaluation.ts#L29)). The Event id is the dedup key ([trigger-submission.ts:101](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/trigger-submission.ts#L101)). The ledger keeps every key forever, so the same Loop acts once on the same Item content. A Board move sends a Hint: `Operator.moveBoardItem` calls `PollingTriggers.hint` after its label write ([operator.ts:556](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/operator/operator.ts#L556)). `refreshHint` ([polling.ts:395](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/polling/polling.ts#L395)) fetches that one Item through the same `observeItem` and `evaluateItem` path and never advances the cursor. ## Submission and the claim

`RunEngine.submit` ([engine.ts:52](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/engine.ts#L52)) calls `RunStore.recordAndClaim` ([store.ts:103](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/store/store.ts#L103)), one transaction:

```mermaid
flowchart TB
  record["Insert the Event,<br/>record the sighting"] --> existing{"Run for the Event<br/>or its newest reopening?"}
  existing -- "yes, Canceled, and<br/>the Item came back" --> reopen["Insert a reopening<br/>of the Event"]
  existing -- "yes, otherwise" --> claimed(["Claimed: that Run"])
  existing -- no --> ignored{"Ignored?"}
  ignored -- "revoked, and<br/>the Item came back" --> reopen
  ignored -- yes --> ignoredResult(["Ignored"])
  ignored -- no --> generation{"Old<br/>generation?"}
  reopen --> generation
  generation -- yes --> ignoredResult
  generation -- no --> held{"Question holds<br/>Loop and Item?"}
  held -- "yes, same state" --> heldResult(["Held: the Event waits"])
  held -- "no, or the Item<br/>changed again" --> blocking{"Open Run of<br/>Loop and Item?"}
  blocking -- Running --> queued(["Queued: the Event waits"])
  blocking -- "Pending, Waiting, Queued" --> supersede["Cancel that Run:<br/>Superseded"]
  blocking -- none --> budget
  supersede --> budget{"Budget<br/>admits?"}
  budget -- no --> blocked(["CycleBlocked"])
  budget -- yes --> opened(["Claimed: a new Pending Run"])
```

1. Insert the Event, ignoring a duplicate dedup key. Record it in `usine_loop_items` as the Event the Loop last saw for the Item, and keep what the Loop saw before. `RunStore.revoke` records a sighting that did not match. The re-check of a queued Event records nothing, because the trigger may still submit that Event from a fetch made before the closing Run changed the Item.
2. Find the Run of the Event, or of its newest reopening or [Run again](#run-again). If there is one, return `Claimed` with that Run. If the Event is in `usine_ignored_events`, return `Ignored`. There is one exception to both, when no Attempt worked on the Event's state: its Run is `Canceled` (by the operator, a supersede, or a revoke), or a revoke ignored the Event while it waited in the queue. If the Loop saw the Item not matching or saw another Event since it last saw this one, the Item came back to that state ([#267](https://github.com/basaltbytes/usine/issues/267)). The engine then inserts a reopening: an Event with the dedup key `["reopened", n, <original dedup key>]` and the new sighting's payload, task, and Agent, and continues with it from step 3. Its Run id hashes that key, so the original Event keeps its Run and every existing Run keeps its id. A `Succeeded` or `Failed` Run always keeps its Event; a failed Run waits for an operator retry. An Event that a newer Event superseded in the queue stays ignored. A canceled Run whose Item the Loop never saw before the cancel, such as a Run canceled before the upgrade that added this rule, keeps its Event until the Loop sees the Item leave and come back.
3. If the Event belongs to an older cycle generation, return `Ignored`. If an operator question or blocker holds the Loop on the Item, return `Held` ([Operator questions and blockers](#operator-questions-and-blockers)), unless the Event shows that the Item changed again.
4. Find the open Run of the same Loop and Item and decide with `claimRun` ([lifecycle.ts:225](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/lifecycle.ts#L225)). If that Run is `Running`, queue the Event. If it's `Pending`, `Waiting`, or `Queued`, supersede it: it becomes `Canceled` with reason `Superseded`, and a new Run opens. If there is no open Run, open a new one.
5. Before opening a Run, check the Item's cycle budget ([queries.ts:84](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/cycle-budget/queries.ts#L84)). If the budget is used up, return `CycleBlocked` and open nothing. A supersede decided in step 4 still commits, so the older Run ends `Canceled` and no Run replaces it.

```ts title="packages/engine/src/engine/lifecycle.ts"
/**
 * Decides what to do with an Event that no Run has claimed: open a Run, queue the Event
 * while the Item's Run is running, or supersede the Item's unstarted Run. The ledger handles
 * duplicate and ignored Events before this decision; a running Attempt always finishes (ADR 0007).
 */
export const claimRun = (blocking: Option.Option<Run>, eventId: EventId): ClaimDecision => {
  if (Option.isNone(blocking)) return { _tag: "OpenRun" };
  const run = blocking.value;
  if (run.state._tag === "Running") return { _tag: "QueueEvent" };
  if (RunState.isUnstarted(run.state)) {
    return { _tag: "SupersedeRun", runId: run.id, state: RunState.supersede(run.state, eventId) };
  }
  return { _tag: "OpenRun" };
};
```

A queued Event opens no Run and adds no row except the Event itself. It's different from the `Queued` Run state below, which a Run enters only after an approval.

After the transaction, `submit` stops the superseded Run's fiber and starts the new one.

## States

Run states are tagged classes in [state.ts](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/core/src/run/state.ts). Each transition function accepts only its legal source states, so an illegal transition fails to compile. The two diagrams below split the transitions, and label each transition with the `RunStore` function that writes it.

```mermaid
stateDiagram-v2
  [*] --> Pending: recordAndClaim,<br/>claimQueued
  Pending --> Waiting: parkForApproval
  Waiting --> Queued: approve
  Pending --> Running: beginAttempt
  Queued --> Running: beginAttempt
  Running --> Succeeded: finishAttempt
  Running --> Failed: finishAttempt,<br/>beginAttempt
  Failed --> Running: retry
  note left of Running
    InfraFailure, Attempt < 3:
    next Attempt, same Run
  end note
  Succeeded --> [*]
```

A cancel moves a Run to `Canceled` from every open state. A supersede, which `recordAndClaim` writes, and a revoke apply only to states where no Attempt has started.

```mermaid
stateDiagram-v2
  Pending --> Canceled: cancel, revoke,<br/>recordAndClaim
  Waiting --> Canceled: cancel, revoke,<br/>recordAndClaim
  Queued --> Canceled: cancel, revoke,<br/>recordAndClaim
  Running --> Canceled: cancel
  Canceled --> [*]
```

```ts title="packages/core/src/run/state.ts"
/** Moves a pending Run to the waiting state until its Loop's required approval arrives. */
export const awaitApproval = (_state: Pending): Waiting => new Waiting();

/** Returns the approved state; the Run still waits for a Worker slot before execution. */
export const approve = (_state: Waiting): Queued => new Queued();

/** Returns the running state for a first Attempt after any required approval has been granted. */
export const start = (_state: Startable): Running => new Running();

/** Closes the run after a successful attempt. */
export const succeed = (_state: Running): Succeeded => new Succeeded();

/** Closes the run after a failed attempt when no auto-retry applies; `shouldAutoRetry` decides that. */
export const fail = (_state: Running): Failed => new Failed();

/** Returns the reopened state for operator retry; attempt N+1 belongs to the same Run and Step. */
export const retry = (_state: Failed): Running => new Running();

/** Cancels from any open state. */
export const cancelByOperator = (_state: Open): Canceled =>
  new Canceled({ reason: new OperatorCanceled() });

/**
 * Cancels an unstarted run because a newer Event for the same Item replaced it.
 * A running Attempt always finishes, and the engine evaluates the newer Event after it ends (ADR 0007).
 */
export const supersede = (_state: Unstarted, by: EventId): Canceled =>
  new Canceled({ reason: new Superseded({ by }) });

/** Cancels an unstarted run because its Item stopped matching the loop's trigger. */
export const revoke = (_state: Unstarted): Canceled => new Canceled({ reason: new Revoked() });
```

An Attempt ends as `Succeeded`, `Failed` with a typed failure, or `Canceled` ([outcome.ts](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/core/src/attempt/outcome.ts)). The failures are `InfraFailure`, `DefectFailure`, `AgentFailure`, `BlockedFailure`, `QuestionFailure`, `RunawayFailure`, and `ChildSessionBudgetFailure` ([failure.ts](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/core/src/attempt/failure.ts)). A `QuestionFailure` carries the question an Agent asked the operator and a `BlockedFailure` the blocker it reported; both hold the Loop on the Item ([Operator questions and blockers](#operator-questions-and-blockers)). The engine retries only an `InfraFailure` without the operator, up to three Attempts in total ([lifecycle.ts:12](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/lifecycle.ts#L12)). The cap uses the Attempt number rather than a count since the last operator retry ([attempt.ts:64](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/core/src/attempt/attempt.ts#L64)), so after an operator retry of a third or later Attempt, an `InfraFailure` fails the Run again. An Attempt that a restart finds no longer live counts as an `InfraFailure`. A Worker capability error at preparation becomes an `AgentFailure` ([scheduler.ts:51](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/scheduler.ts#L51)), so a Run whose harness is logged out waits for the operator.

## The Run fiber

`RunDriver` ([run-driver.ts](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/run-driver.ts)) keeps one fiber per open Run in a `FiberMap`, except for `Waiting` Runs, which have none until an approval. `drive` ([run-driver.ts:341](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/run-driver.ts#L341)) does this:

<Steps>

1. Read the Run's Submission. With `approval: required`, put the Run in `Waiting` and end the fiber. The approval starts a new fiber.

2. Reserve a Worker slot. `StepExecutor.reserve` ([scheduler.ts:131](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/scheduler.ts#L131)) serves reservations in order of Event receipt time, one slot per `max_concurrent_attempts`. Before it reserves, the fiber asks the executor whether the Run's open Attempt is still live (`openAttempt`). A Run that reattaches a live Attempt takes the slot startup occupied for it on that Attempt's Worker through `StepExecutor.occupy`, and a Run that doesn't reattach its open Attempt releases that slot before it reserves. A Run that reattaches an Attempt without such a slot names that Attempt's Worker: it waits for a slot of that Worker only, and its reservation goes before the ones that name no Worker ([#177](https://github.com/basaltbytes/usine/issues/177)).

3. Enter Attempt admission ([admission.ts:58](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/admission.ts#L58)) and run `executeAttempt` ([run-driver.ts:288](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/run-driver.ts#L288)): after a wait for a named Worker's slot, ask the executor again whether the open Attempt it found live is still live (`openAttempt`, [run-driver.ts:234](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/run-driver.ts#L234)), since its parent task may have stopped while the Run waited, then `beginAttempt` starts a new Attempt or reattaches the live one, then `execute`, then `finishAttempt`.

4. Repeat while the decision is `RetryAttempt`. Each retry reserves a new Worker slot.

5. Process the newest queued Event of the same Loop and Item (`continueWithNewest`, [run-driver.ts:179](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/run-driver.ts#L179)). `TriggerCondition.recheck` ([trigger-condition.ts:87](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/trigger-condition.ts#L87)) fetches the Item again and evaluates `if:`, and answers `matches` or `no-longer-matches`. GitHub answering that it no longer has the Item (`GitHubItemNotFoundError`) answers `item-gone`, and any other failure or a five-second timeout answers `matches` ([trigger-condition.ts:96](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/trigger-condition.ts#L96)). `no-longer-matches` marks the queued Events as revoked. `item-gone` revokes them too and sets `gone_at` on the Item's row in `usine_item_projections`, so the Board places the Item by its closed state. While an operator question or blocker holds the Loop and Item, there is no queued Event to process.

</Steps>

`RunDriver` retries a failed store write four times, with exponential backoff starting at 100 ms ([run-driver.ts:47](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/run-driver.ts#L47)). `reconcile` restarts a fiber that stopped on an engine failure; it runs at engine start and every three minutes ([engine.ts:37](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/engine.ts#L37), [engine.ts:181](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/engine.ts#L181)). Before the first reconcile, `recoverWorkspaces` ([engine.ts:286](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/engine/engine.ts#L286)) asks the executor to salvage or remove every checkout an earlier process left, except the checkout of an open Attempt whose parent task is live, which stays for its Run to reattach. For each such Attempt it also occupies a slot of the Attempt's Worker (`StepExecutor.occupy`) before any Run's fiber starts, so a Run that arrives while the reattaching Run still reads the Attempt can't take that slot ([#177](https://github.com/basaltbytes/usine/issues/177)). `RunDriver` stays responsible for that checkout until the reattaching execution's preparation holds it, which the scheduler reports through `ExecutionSink.checkoutAcquired` before it launches the Attempt. When the Run closes the Attempt before then, because the parent task stopped before the Run reattached it, the Run can't read whether it's live, the reattachment failed first, or the operator canceled the Run, `RunDriver` reconciles the checkout then, before the next Attempt starts: it stops a parent task that is still live, the executor salvages the checkout, and the next Attempt resumes from that salvage ([#180](https://github.com/basaltbytes/usine/issues/180)). When the stop can't be confirmed, the checkout stays and the Run's fiber stops before the next Attempt, so the next reconcile drives the Run again. It runs once per start, in the engine layer, so the executor sees each persisted Attempt once. It skips the Attempts recorded on a Worker that `StepExecutor.workers` doesn't list, that is, a Worker `usine.yaml` no longer declares: one warning per start gives their count and the Workers, and their checkouts stay where they are until the Worker is declared again or the operator discards their leftovers.

## Run again

`RunStore.runAgain` opens a new Run for the Item state a `Succeeded` or `Canceled` Run worked on, in one transaction ([#152](https://github.com/basaltbytes/usine/issues/152)). A Run that succeeded can leave its Item unresolved, and a label removed and added within one poll interval is seen only as its end state, so neither opens a Run by itself ([#342](https://github.com/basaltbytes/usine/issues/342)).

- The Event carries the Run's Event payload and revision, the Step, approval requirement, and cycle limit of the Loop file as it is now, the task and Agent the operator chose, and the Item's current cycle generation. `Operator.runAgain` derives the Agent's persona, brain, and parent model from the roster, as edit and retry does.
- Its dedup key is `["operator-run-again", n, <trigger dedup key>]`, where the trigger dedup key is the key of the Event the trigger submitted for that state, and `n` is the next of that Event's reopening numbers. A later sighting of the unchanged Item follows the newest reopening, so it joins the new Run and opens nothing.
- It records no sighting in `usine_loop_items`, and `usine_run_again_events` records the Run it ran again and the operator login that asked.
- The Item's cycle budget admits it as it admits a polled Event: when the budget is used up, the result is `CycleBlocked` and the Item's Ask opens. Once the Run opens, its fiber parks it for approval when the Loop requires approval.
- The engine refuses a Run in another state, and a Run whose Loop already has an open Run on the Item, before it records anything. A paused Loop still runs again, because the operator asks for it.

An unstarted Run opened this way is revoked by the next poll that finds the Item no longer matching the Loop, as any other unstarted Run is.

## Operator questions and blockers

An Agent that needs a decision only the operator can make posts its question on the Item and opens its final answer with `[usine:question]` ([How an Attempt runs](/architecture/execution/#the-durable-layer)). The Attempt fails with `QuestionFailure`, which never retries automatically, and the Run becomes `Failed`. Needs attention lists it as a `RunFailureNeed` that shows the question.

An Agent that hits a blocker it cannot resolve records the blocker on the Item and opens its final answer with `[usine:blocked]`. The Attempt fails with `BlockedFailure`, which never retries automatically either, and Needs attention lists it as **\<loop\>: blocked** with the blocker. Other Agent failures, such as a harness that is not logged in, stay `AgentFailure` and hold nothing. A child's harness failure, such as a failed Codex turn, posts nothing on the Item either: it reaches the parent as a report that opens with `[usine:failed]` and ends the Attempt with `AgentFailure`.

In the same transaction as the failure, `RunStore.finishAttempt` starts a hold on the Run's Loop and Item in `usine_loop_items` ([#241](https://github.com/basaltbytes/usine/issues/241), [#341](https://github.com/basaltbytes/usine/issues/341)), unless the Loop last saw the Item not matching. Without the hold, the Agent's own question or blocker comment would be new content, a new Event, and a new Run that asks the same question or meets the same blocker, until the cycle budget ran out. While the hold lasts:

- The first Event that the Loop sees after the question or blocker is the Item's held state. When an Event was already queued behind the Run, that Event is the held state. Sightings of the held state return `Held` and open no Run.
- `nextQueued` and `pendingContinuations` leave the Loop and Item out, so the fiber that closed the Run and `reconcile` open none of its queued Events.
- An Event with content other than the held state ends the hold: the Item changed again, for example through the operator's reply or a pushed commit, and the Event is claimed as usual.
- `revoke` ends the hold, and the Item's return opens a Run as for a canceled Run.
- An operator retry or edit and retry of the Run ends the hold; Events then wait behind the running Run as usual.
- Resolving the failure ends the hold and runs `continueWithNewest` for the Run, so the newest queued Event of the Item gets its turn after the trigger re-check.

The question or blocker stays in Needs attention until the operator resolves the failure or retries the Run, as for any failed Run.

## Cycle budgets

A Loop can open `max_cycles` Runs on one Item between operator resets, three by default ([cycle-budget.ts:20](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/core/src/cycle-budget.ts#L20)). Schedule Loops have no budget ([trigger-submission.ts:111](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/trigger-submission.ts#L111)). `admit` ([queries.ts:84](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/cycle-budget/queries.ts#L84)) counts the Loop's reserved Runs in the current generation. When the count is at the limit, it stores a `CycleBudgetAsk` in `usine_item_cycle_budgets.ask_json`. From then on no Loop opens a Run on that Item: every submission that would open one returns `CycleBlocked`. A Run canceled before its first Attempt gives its reservation back.

The Ask appears only in the UI's Needs attention list; usine posts nothing to GitHub ([#36](https://github.com/basaltbytes/usine/issues/36)). The reset ([cycle-budget.ts:83](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/engine/src/cycle-budget/cycle-budget.ts#L83)) records the answer Event, increments the generation, clears the Ask, moves unstarted Runs' reservations into the new generation, and sets `reset_pending`. The next poll of that repository starts from an empty cursor ([polling.ts:195](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/orchestrator/src/polling/polling.ts#L195)), so the Item's current state produces new Events whose dedup key includes the new generation. [ADR 0022](https://github.com/basaltbytes/usine/blob/main/docs/adr/0022-item-cycle-budgets-and-comment-reviews.md) explains why the budget is per Item.

## Drain

The first SIGINT or SIGTERM completes the `RunEngineShutdown` latch ([shutdown.ts:5](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/apps/server/src/shutdown.ts#L5)), which immediately closes Attempt admission. The process then waits for admitted Attempts to record their outcome: for at most `max_attempt_minutes` when it's set, and with no limit otherwise ([up.ts:171](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/apps/server/src/up.ts#L171)). A second signal stops the wait. An Attempt interrupted this way keeps its parent task live in durable storage, and the next `usine up` reattaches it ([durable-session.ts:193](https://github.com/basaltbytes/usine/blob/7c0c3d3696123d11e3d5b9cc3d27e18bb21e84e9/packages/executor/src/durable-session.ts#L193)). [ADR 0023](https://github.com/basaltbytes/usine/blob/main/docs/adr/0023-graceful-attempt-drain.md) explains why the engine controls admission.

## One Run from trigger to pull request

The `start-dev` Loop of the dogfood instance ([The dogfood instance's Loops](/architecture/loops-shipped/)), on an SSH Worker behind a Gateway:

```mermaid
sequenceDiagram
  participant G as GitHub
  participant P as PollingTriggers
  participant E as RunEngine
  participant X as Executor
  Note over G: operator labels issue N<br/>ready-for-agent
  P->>G: GET /issues?since
  G-->>P: issue N changed
  P->>G: GraphQL slice
  Note over P: if: true, key<br/>[start-dev, repo, N, hash]
  P->>E: submit
  Note over E: recordAndClaim: Pending<br/>approval required: Waiting
  Note over E: operator approves:<br/>Queued, fiber starts
  Note over E: reserve a slot,<br/>beginAttempt: Running
  E->>X: execute Attempt 1
  Note over X: attach token to the Gateway,<br/>clone, worktree --detach,<br/>Pi parent starts a Codex child
  X->>G: git push, gh pr create,<br/>through the Gateway
  X-->>E: envelopes to transcript rows
  Note over X: harvest commits and PR M,<br/>detach, remove the worktree
  X-->>E: StepResult
  Note over E: Attempt and Run Succeeded,<br/>continueWithNewest
```

The Codex child also adds `ready-for-review` to pull request M. The next poll detects that M changed, `review-pr` matches it, and a new Run opens for the pull request.
