A provisioned worker is an `ssh` worker that creates a machine at a cloud provider for each attempt and deletes it after the attempt ([ADR 0029](https://github.com/basaltbytes/usine/blob/main/docs/adr/0029-worker-kinds-and-adapter-set.md)). Each machine runs one attempt, in the attempt's own container, as on a [long-lived SSH worker](/guides/add-a-worker/#a-container-per-attempt). In the export format, the worker has a [`provisioner`](/reference/configuration/usine-yaml/#workersprovisioner) instead of a `destination`.

| Provider                        | Machine                                                                 | Network access   | GitHub token on the machine                         |
| ------------------------------- | ----------------------------------------------------------------------- | ---------------- | --------------------------------------------------- |
| Hetzner Cloud with a gateway    | a server from your snapshot in the gateway's network, no public address | the gateway only | none: the gateway adds the token to GitHub requests |
| Hetzner Cloud without a gateway | a server from your snapshot with a public IPv4 address                  | any host         | a token file, mode 600, removed after the attempt   |
| Boat                            | a Boat sandbox in Germany, Finland, or France, with Boat's Ubuntu image | any host         | a token file, mode 600, removed after the attempt   |

Use **Configuration > Workers > New** to create a worker, or **Edit** on a worker page to change it. Paste one worker object into the raw editor, without the surrounding `workers:` list shown in import examples. A refused save displays the validation, restart, or preflight reason.

## Prerequisites

- Every configured worker has `kind: ssh`.
- An SSH key pair for the worker on the orchestrator machine. The worker's `identity_file` is its private key.
- A credential for each harness that your agents use, outside the machine. See [Harness credentials](#harness-credentials).
- For Hetzner Cloud: the `hcloud` CLI with an active context for the project, and `jq`. For a worker behind a gateway, the gateway of [SSH workers behind a gateway](/guides/add-a-worker/#ssh-workers-behind-a-gateway).
- For Boat: a Boat account and the `boat` CLI.

## Harness credentials

A machine created for one attempt keeps no harness login: a login saved in a snapshot contains one refresh token, and the first machine that refreshes it invalidates it for the others. So at `usine up`, and when a revision adds the worker, preflight refuses a provisioned worker if a harness that its agents use has no credential outside the machine.

| Harness     | Credential                                                                                                                                                                                                                                                                                            |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claude Code | `anthropic` in the gateway's [`llm_providers`](/reference/configuration/usine-yaml/#workersgateway), with a subscription token or an API key on the gateway. Or `provisioner.api_keys.anthropic`, which each attempt's container gets as `ANTHROPIC_API_KEY`. If both are set, the gateway's applies. |
| Codex       | `openai` in the gateway's `llm_providers`, with a ChatGPT login or an API key on the gateway. Or `provisioner.api_keys.openai`, which each attempt's container gets as `OPENAI_API_KEY`. If both are set, the gateway's applies.                                                                      |
| Pi          | Not available. Pi children run only on local workers.                                                                                                                                                                                                                                                 |

A Boat worker can use [gateway subscriptions over Tailscale](#gateway-subscriptions-over-tailscale), or supply its Claude Code and Codex agents with `api_keys`. With an OpenAI key, each attempt gets its own `CODEX_HOME` with a `config.toml` that points Codex at `api.openai.com` with the key from `OPENAI_API_KEY`, so Codex needs no login. Behind a gateway that doesn't hold the provider's credential, the machine reaches the provider through the gateway's forward proxy, and the first machine's checks fail if the egress allowlist doesn't have `api.anthropic.com` or `api.openai.com`; `api.openai.com` isn't in the default allowlist.

The run page counts children that use an API key under API keys, and those that use a subscription on the gateway under the Claude or ChatGPT plan.

## Hetzner Cloud

Each attempt gets a server created from a snapshot that you build with `infra/hetzner/snapshot.sh`. Behind a gateway, the server joins the gateway's private network with no public address, and the executor connects to it through the gateway with `ssh -J`. [`infra/hetzner/README.md`](https://github.com/basaltbytes/usine/blob/main/infra/hetzner/README.md#provisioned-workers) describes the files.

<Steps>

1. Create an API token for the Hetzner Cloud project. In the Hetzner Cloud Console, open the project, select **Security** > **API tokens** > **Generate API token**, and select **Read & Write**. The console shows the token once. Add it to `.env` in the instance folder, the [environment file](/reference/configuration/cli/#environment-file) that usine reads at startup: run this command, paste the token, and press Enter.

   ```sh title="Instance folder"
   (umask 077; read -r token && echo "HCLOUD_TOKEN=$token" >> .env)
   ```

   A Hetzner Cloud token applies to every resource of its project. usine deletes only servers that have its `usine-instance` and `usine-worker` labels.

2. Create the worker's key pair and register the public key in the project. Skip the second command if the gateway's setup registered the same key:

   ```sh title="Orchestrator machine"
   ssh-keygen -t ed25519 -f ~/.ssh/usine_worker -C usine-worker
   hcloud ssh-key create --name usine-worker --public-key-from-file ~/.ssh/usine_worker.pub
   ```

   The snapshot authorizes this key for the `usine` user, whom the executor connects as. Hetzner adds the registered key for root, which the server's sshd refuses; it keeps Hetzner from emailing a root password for each server.

3. Set up the gateway: steps 1 to 5 and 9 of [SSH workers behind a gateway](/guides/add-a-worker/#ssh-workers-behind-a-gateway). Its network is `usine-gateway` by default. Step 5 gives the gateway a credential for each harness that your agents use, and removes the login hosts from its egress allowlist. The gateway's use of a subscription token is untested against Anthropic ([#234](https://github.com/basaltbytes/usine/issues/234)).

4. Build the snapshot in the gateway's network. Use the public key of the worker's `identity_file`; its private key must be next to it. `GATEWAY_SSH` is the gateway's `Host` alias:

   ```sh title="usine checkout"
   SSH_KEY=usine-worker NETWORK=usine-gateway GATEWAY_SSH=usine-gateway \
     ./infra/hetzner/snapshot.sh ~/.ssh/usine_worker.pub
   ```

   The script creates a temporary server from `infra/hetzner/cloud-init.yaml` and `infra/hetzner/gateway/worker-cloud-init.yaml`, waits for cloud-init, pulls the attempt image, and saves the server as a snapshot labeled `usine=snapshot`. It then deletes the server and prints the snapshot's ID and description, such as `usine-worker-claude-2.1.308-codex-0.164.0`. The snapshot has the gateway's address and domain, so it works only in that gateway's network. It has no harness login and no token. If you created the gateway with other `GATEWAY_IP`, `DOMAIN`, or `NETWORK_CIDR` values, set the same ones for `snapshot.sh`.

   Run the script from a checkout of the usine release that you run, so that the snapshot has that release's attempt image. The image must be public on GHCR, because a machine created for one attempt has no `docker login`.

   The temporary server is a `cx23` in `fsn1` unless you set `SERVER_TYPE` and `LOCATION`. The type must be available in the location, and Hetzner's Cost-Optimized types, such as `cx23` and `cx33`, often aren't; a snapshot built on a `cpx12` runs `cpx32` servers. A server created from the snapshot needs a disk at least as large as the temporary server's, so build it on the smallest type that you set in `server_type`.

5. Run `usine config export ./config-export`, then add the worker below to the exported `usine.yaml`. Keep the other entities and import the complete folder with `usine config import ./config-export --message "Add Hetzner worker"`:

   ```yaml title="config-export/usine.yaml (fragment)"
   workers:
     - name: hetzner-pool
       kind: ssh
       max_concurrent_attempts: 4
       root: /home/usine/.usine
       identity_file: ~/.ssh/usine_worker
       gateway:
         domain: gw.internal
         destination: usine-gateway
         admin_token_env: USINE_GATEWAY_ADMIN_TOKEN
         llm_providers: [anthropic, openai]
       provisioner:
         provider: hetzner
         token_env: HCLOUD_TOKEN
         server_type: cx33
         location: fsn1
         image: usine-worker-claude-2.1.308-codex-0.164.0
         network: usine-gateway
         ssh_key: usine-worker
   ```

   - `max_concurrent_attempts` is the number of servers in flight, counting those being created.
   - Each server runs one attempt, so the memory check counts one attempt per server. A `cx33` or `cpx32` has the 8 GB that usine's own gates need ([#270](https://github.com/basaltbytes/usine/issues/270)).
   - `location` must be in the network's zone. The gateway's network is in `eu-central`, which has `fsn1`, `nbg1`, and `hel1`.
   - `image` is the description or ID that `snapshot.sh` printed. With a description, each server is created from the newest available snapshot that has it.
   - `network` is required with a `gateway`.

6. Run `usine restart` if the orchestrator is running, or `usine up` if it is stopped. It reads `HCLOUD_TOKEN` and the gateway's `USINE_GATEWAY_ADMIN_TOKEN` from `.env`:

   ```sh title="Instance folder"
   usine up
   ```

   Preflight creates no server. It checks the token, the server type in the location, the image, the SSH key, the network, the gateway's admin API, and each harness's credential. If the server type is out of stock in the location, preflight logs a warning and `usine up` starts; servers are created once Hetzner has it again. Hetzner documents no endpoint for the project's server limit, so preflight reads none. The first server of each day checks the rest. See [Machine checks](#machine-checks).

</Steps>

### Without a gateway

Without a `gateway`, each server gets a public IPv4 address, and the executor connects to it there. If you set `network`, the executor connects to the server's private address instead, which works only from an orchestrator in that network. Build the snapshot without `NETWORK`:

```sh title="usine checkout"
SSH_KEY=usine-worker ./infra/hetzner/snapshot.sh ~/.ssh/usine_worker.pub
```

The attempt's GitHub token is written to the server, as on an [SSH worker](/guides/add-a-worker/#ssh-workers) without a gateway, Claude Code needs `api_keys.anthropic`, and Codex needs `api_keys.openai`.

The server's sshd accepts only the `usine` user's key, from any address. To accept SSH only from the orchestrator's address, create a Hetzner firewall and set its name in `provisioner.firewall`, so that each server gets it when it's created:

```json title="firewall.json"
[
  {
    "direction": "in",
    "protocol": "tcp",
    "port": "22",
    "source_ips": ["203.0.113.10/32"],
    "description": "SSH from the usine orchestrator"
  }
]
```

```sh title="Orchestrator machine"
hcloud firewall create --name usine-hetzner-pool --rules-file firewall.json
```

Run `usine config edit worker hetzner-pool` to set `provisioner.firewall`, then restart to apply it. This is the relevant part of the worker record:

```yaml title="worker hetzner-pool (fragment)"
provisioner:
  provider: hetzner
  firewall: usine-hetzner-pool
```

### Update the snapshot

Build a new snapshot when a usine release changes the attempt image or `infra/hetzner/cloud-init.yaml`. Its description names the new harness versions, so run `usine config edit worker hetzner-pool`, change `provisioner.image`, and run `usine restart` to apply the saved revision. The running process cannot apply a changed `provisioner` live and logs `RestartRequiredError`. A new snapshot with the same description, from `DESCRIPTION`, needs no restart, because each server is created from the newest one. Delete the old snapshots, which Hetzner bills by size:

```sh title="Orchestrator machine"
hcloud image list --type snapshot --selector usine=snapshot
hcloud image delete <id>
```

## Boat

Each attempt gets a Boat sandbox: a VM with Boat's Ubuntu 24.04 image, which has Git, gh, Node.js, Docker, and the harnesses. usine connects to it over SSH as Boat's user `user` and runs the attempt in a container from the attempt image, whose `usine` user must have the user ID of `user`; the [machine checks](#machine-checks) compare them.

<Steps>

1. Create a Boat API key. Boat shows the key once. Add it to `.env` in the instance folder, the [environment file](/reference/configuration/cli/#environment-file) that usine reads at startup: run the second command, paste the key, and press Enter.

   ```sh title="Instance folder"
   boat api-key create usine-boat-pool --ttl 365d
   (umask 077; read -r key && echo "BOAT_API_KEY=$key" >> .env)
   ```

   usine reads the account and its limits, creates, renames, lists, and deletes sandboxes, and adds an SSH key to each. Boat doesn't document the actions of each `--preset`, and a key without `--preset` or `--actions` has full access to the account. A key expires after its `--ttl` (90 days by default, `never` for no expiry), and preflight then fails.

2. Create the worker's key pair. usine adds `<identity_file>.pub` to each sandbox:

   ```sh title="Orchestrator machine"
   ssh-keygen -t ed25519 -f ~/.ssh/usine_boat -C usine-boat
   ```

3. Run `usine config export ./config-export`, then add the worker below to the exported `usine.yaml`. Keep the other entities and import the complete folder with `usine config import ./config-export --message "Add Boat worker"`:

   ```yaml title="config-export/usine.yaml (fragment)"
   workers:
     - name: boat-pool
       kind: ssh
       max_concurrent_attempts: 4
       root: /home/user/.usine
       identity_file: ~/.ssh/usine_boat
       provisioner:
         provider: boat
         token_env: BOAT_API_KEY
         size: default
         api_keys:
           anthropic: USINE_ANTHROPIC_API_KEY
   ```

   - `size` is `small`, `default` (4 vCPU, 8 GB), `large`, or `xlarge`, which needs a Boat plan of $100 per month or more.
   - `identity_file` is required. A `region` is refused because Boat documents no region choice. For subscription logins, use the gateway setup below.

4. Add the Anthropic API key to `.env` the same way. Restart a running instance with `usine restart`, or start a stopped instance as shown below, to read both keys:

   ```sh title="Instance folder"
   (umask 077; read -r key && echo "USINE_ANTHROPIC_API_KEY=$key" >> .env)
   usine up
   ```

   Preflight creates no sandbox. It checks that Boat accepts the key and reads the account's limits: a size that Boat doesn't offer the account fails preflight, and an account that can't start sandboxes now, or whose active-sandbox cap is below `max_concurrent_attempts`, logs a warning.

</Steps>

On a Boat worker:

- Without a gateway, a sandbox can reach any host. The installation token is in a file on the machine, readable by the attempt, which an agent can use from anywhere until the token expires, within the hour ([ADR 0026](https://github.com/basaltbytes/usine/blob/main/docs/adr/0026-eu-ssh-worker.md)). The API keys are in the attempt container's environment, where an agent can read them and spend them.
- usine creates each sandbox with none of the account's secrets (`noEnv`), so it can't act on your account or other sandboxes. It turns off snapshots, because Boat can store snapshot copies outside the EU and no attempt resumes a sandbox. It also turns off command monitoring and the automatic stop, since usine deletes the sandbox. A creation succeeds only if a machine of the size is ready (`failFast`); otherwise Boat creates and bills nothing.
- The sandbox name records usine's recovery tags: `usine <instance> <worker> <run> <process> <attempt>`.

### Gateway subscriptions over Tailscale

Use a gateway to keep the GitHub installation token, Claude subscription token, and ChatGPT login off Boat sandboxes. The sandbox gets only its attempt's caller token. Boat retains direct internet access; this setup does not enforce an egress allowlist.

1. Configure the gateway's [provider credentials](/guides/add-a-worker/#ssh-workers-behind-a-gateway), including both providers in `llm_providers` when both harnesses run. Join the gateway and orchestrator to your tailnet. Record the gateway's IPv4 address with `tailscale ip -4`.
2. Set `USINE_GATEWAY_PROXY_HOST=0.0.0.0` in the gateway's environment file and restart `usine-gateway`. Apply the updated `infra/hetzner/gateway/gateway-nftables.conf`: it accepts TCP port 80 on `tailscale0`. Keep the admin API on loopback and the forward proxy on the private address. The public firewall must continue to refuse port 80.
3. Create a Tailscale OAuth client with `auth_keys` write access and permission to create keys tagged `tag:usine-attempt`. Add its ID and secret to the instance's `.env` as `TAILSCALE_CLIENT_ID` and `TAILSCALE_CLIENT_SECRET`. The executor creates a preauthorized, ephemeral, single-use key for each sandbox, with a ten-minute expiry, and revokes it after joining. These OAuth credentials stay on the orchestrator.
4. Adapt your tailnet policy to grant attempt nodes only the gateway's TCP port 80. For example, use the following grant with a gateway tagged `tag:usine-gateway`:

   ```json
   { "src": ["tag:usine-attempt"], "dst": ["tag:usine-gateway"], "ip": ["tcp:80"] }
   ```

   Configure tag ownership for your OAuth client. Remove broader grants or legacy ACLs that also match attempt nodes: grants are additive. No other user or tag should have access to `tag:usine-attempt`; if the orchestrator needs tailnet SSH, grant only its tag TCP port 22. Normal Boat SSH uses the endpoint Boat returns and needs no inbound tailnet grant. Keep your policy file in your own tailnet administration.

5. Build a saved snapshot from this repository. Set `BOAT_API_KEY` in the shell, then run:

   ```sh
   infra/boat/build-snapshot.sh usine-attempt \
     ghcr.io/basaltbytes/usine-worker:claude-2.1.308-codex-0.164.0 \
     ~/.ssh/usine_boat
   ```

   The script requires `curl`, `jq`, OpenSSH, and a paid Boat plan; the free trial refuses saved snapshots. It creates a source sandbox with `noEnv: true`, installs Tailscale, pulls the image, and creates a stopped container so Boat retains the image. It stops Tailscale and removes its state before saving, so each sandbox creates its own node identity. It waits for the saved snapshot to become `ready`, then deletes the source sandbox. Rebuild the snapshot whenever the attempt image changes. Saved snapshot copies can be stored outside the EU, so keep credentials and repository checkouts out of the source sandbox.

6. Export with `usine config export ./config-export`. Update the worker in the exported `usine.yaml`, keeping the rest of the configuration, then import the folder and restart to apply the gateway and provisioner changes:

   ```yaml title="config-export/usine.yaml (fragment)"
   workers:
     - name: boat-pool
       kind: ssh
       root: /home/user/.usine
       identity_file: ~/.ssh/usine_boat
       gateway:
         domain: gw.internal
         destination: usine-gateway
         admin_token_env: USINE_GATEWAY_ADMIN_TOKEN
         llm_providers: [anthropic, openai]
       provisioner:
         provider: boat
         token_env: BOAT_API_KEY
         snapshot: usine-attempt
         tailnet:
           gateway_address: 100.64.0.2
           client_id_env: TAILSCALE_CLIENT_ID
           client_secret_env: TAILSCALE_CLIENT_SECRET
   ```

   ```sh
   usine config import ./config-export --message "Configure Boat gateway"
   usine restart
   ```

Preflight checks the saved snapshot's readiness, creates and revokes an auth key to check the OAuth client's tag permissions, and checks the gateway at its tailnet address. After SSH answers, the executor joins the sandbox with `--accept-dns=false` and `--accept-routes=false`. It configures `git.<domain>` and `llm.<domain>` on the host and in attempt containers, plus gh's HTTP socket. Package downloads use Boat's direct internet connection; port 3128 stays closed on the tailnet.

Cleanup detaches the caller token, logs the sandbox out of Tailscale, and deletes the sandbox. After an orchestrator crash, reconciliation deletes orphan sandboxes; Tailscale removes offline ephemeral nodes automatically, including when logout could not run. A live sandbox remains on the tailnet until cleanup or reconciliation, so restore the orchestrator or delete orphan sandboxes after an outage.

Check the policy from an attempt node: port 80 at the gateway should answer, while ports 22, 3128, and 7070 should not. Children appear under the Claude or ChatGPT plan on the run page when the gateway reports a subscription credential. Without a gateway, continue to provide `api_keys` as shown above.

## Machine lifecycle

1. When a slot is free, the scheduler takes the next waiting run in [queue order](/reference/configuration/loop-files/#priority). The engine persists its attempt, then creates the machine with that attempt in its initial labels. The attempt waits for SSH for up to `provisioner.timings.ssh_wait` seconds (600 by default).
2. The executor waits for cloud-init, creates `root`, and waits for Docker. The first machine after the configured check interval also gets the [machine checks](#machine-checks).
3. The attempt starts on the machine and runs as on a long-lived SSH worker. Both providers retain the attempt label until deletion.
4. After the attempt releases its checkout, the release of its slot deletes the machine. If usine can't confirm that the attempt's parent task stopped, the slot and the machine stay until a reconcile confirms the stop.
5. After a restart, recovery finds each attempt's machine by its tags. After recovery, and at each reconcile every 3 minutes, usine deletes the machines of the instance that no attempt or creation of the running process holds. It keeps a machine whose recovery failed, for the next process.

A failed creation retries within the same attempt, keeping its slot. The worker pauses further creation for `provisioner.timings.creation_backoff_min` seconds (30 by default), doubling after each consecutive failure up to `creation_backoff_max` (600 by default). Success resets the pause. Other workers continue, and canceling the attempt interrupts creation and frees its slot. The **Workers** page and the log show the reason and the time of the next try:

| Reason                     | Hetzner Cloud                                                                                 | Boat                              |
| -------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------- |
| No machine of the type now | `resource_unavailable`, or a plan shown as currently unavailable                              | 503: no machine of the size ready |
| Account limit              | `resource_limit_exceeded`                                                                     | 402 or 429                        |
| Refused or failed request  | an API error                                                                                  | an API error, or no host key      |
| No answer                  | the API doesn't respond, or the server doesn't answer over SSH within the configured SSH wait | the same                          |

### Host keys

The executor connects to a machine only with a host key that it knows before the first connection, and never trusts the key that a first connection presents:

- Hetzner Cloud: the executor generates an Ed25519 host key pair for each server and passes it in the server's cloud-init user data (`ssh_keys`), which replaces the image's host keys at first boot. cloud-init runs the user data on a server created from a snapshot too, because the new server has an instance ID of its own. A server whose image has no cloud-init never presents the key, so the executor's connections fail until the creation times out. Hetzner's metadata service serves the user data to the server, so the server's nftables rules let only root, which cloud-init runs as, reach it: the `usine` user, the attempt's container, and its agent can't read the private key. `snapshot.sh` builds the snapshot from `infra/hetzner/cloud-init.yaml` and, behind a gateway, `infra/hetzner/gateway/worker-nftables.conf`, which have the rules, so they reach every server created from it. A snapshot built before the rules has none; build a new one.
- Boat: the executor uses the host key that `POST /sandboxes/{id}/sshkey` returns. If Boat returns none, the creation fails, and the sandbox is deleted without a connection.

The executor writes each key to `.usine/known-hosts/<provider>-<id>` in the instance folder before its first connection, and connects with `StrictHostKeyChecking=yes`. The files stay across restarts, so recovery connects to an earlier process's machine with the key that process wrote. For a machine with no file, recovery fails without connecting, and usine keeps the machine for a later process; to reconnect, write `usine-<provider>-<id> <host key>` to the file, or delete the machine by hand (see [Leftover machines](#leftover-machines)).

### Machine checks

Preflight at `usine up` has no machine, so the checks that need one run on its first machine after `usine up` and on the next machine created after `provisioner.timings.machine_check_interval` seconds since the last successful check (86400 by default): Git, the memory for one attempt, the gateway from the machine, Docker and the attempt image, the container limits, and each harness. A failure shows as a preflight failure does, the machine is deleted, and the worker pauses its creations as for a failed creation. The **Workers** page shows the configured interval. A UID mismatch fails this check with the image name and the `--build-arg USINE_UID=<SSH user UID>` needed to rebuild it.

The machine's attempt containers share a `usine-pnpm-store` Docker volume, initialized even when the machine skips the periodic preflight. The volume is deleted with the machine after the attempt, so it does not cache packages across attempts. See [Shared pnpm store](/guides/add-a-worker/#shared-pnpm-store) for ownership and disk reclamation.

Each machine runs one attempt, so the check derives each container limit that [`workers[].container`](/reference/configuration/usine-yaml/#workerscontainer) leaves out for one attempt: the machine's total, less a reserve for its own processes. The worker's machines keep those limits until the next successful machine check, and the **Workers** page shows them.

### Machines in the web UI

- Until the attempt starts, the run page says that the run's machine is being created, with the provider and the time since the creation started.
- The **Workers** page and the **Overview** list the machines in flight, with the provider's ID, age, and attempt of each.

## Leftover machines

usine deletes the machines that no attempt holds after startup recovery and every 3 minutes, so machines are left only while no `usine up` runs for the instance, or while the provider refuses to delete them, which the log shows. Delete machines by hand only while no `usine up` runs for the instance, so that you don't delete a running attempt's machine. The instance tag is `github-app-<App ID>`, with the GitHub App's ID.

- Hetzner Cloud: list the servers by label, add `,usine-worker=<worker>` for one worker, and delete them:

  ```sh title="Orchestrator machine"
  hcloud server list -l usine-instance=github-app-123456
  hcloud server delete <id>...
  ```

- Boat: the sandboxes' names start with `usine github-app-<App ID> <worker>`. Delete them in the [Boat dashboard](https://boat.dev/dashboard), with `boat delete <id> --yes`, or with `DELETE /sandboxes/{id}` on Boat's API.

## Costs

- Hetzner Cloud bills every started hour that a server exists, so an attempt of a few minutes costs an hour. On 2026-10-25, a `cx33` cost €0.0144 per hour, and Hetzner showed its Cost-Optimized and Regular Performance plans as currently unavailable ([research note](https://github.com/basaltbytes/usine/blob/main/docs/research/hosted-sandboxes.md#hetzner)). Hetzner also bills each snapshot by its size.
- Boat bills each second that a sandbox runs, and a deleted sandbox costs nothing more. On 2026-10-25, `default` cost $0.036 per hour, and a plan from $20 per seat per month included 555 hours of it.
- Claude Code and Codex children with `api_keys` or a gateway API key are billed by Anthropic and OpenAI at API rates.
