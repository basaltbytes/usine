The operator API reads instance state, manages configuration, and operates runs. This reference renders the committed [OpenAPI 3.1 document](/openapi.json). For the contract of a running instance, request `GET /api/openapi.json` from that instance. The schema endpoint is public and contains no instance configuration or credentials.

Token timestamps and device authorization polling intervals use finite JSON numbers.

## Authentication

Send an instance token as `Authorization: Bearer <token>`. Browser clients can use the `usine_session` cookie; writes with a session also require `X-Usine-CSRF`. See [Sign in](/guides/sign-in/) for browser sessions, and [Create a device token](/guides/create-a-device-token/) for token issuance. The document marks health, sign-in, and schema operations as public. `GET /api/auth/session` returns effective permissions as `{permission, scope}` grants. Roles and token ceilings both limit access; a forbidden operation returns HTTP 403. Lists include only projects with read access.

Viewer requires `read`, operator adds `operate`, and maintainer adds `maintain` on a project. Instance `admin` grants all operations, including membership, bindings, workers, settings, and upgrades. Project resource handlers check the target project in addition to the route requirement. See [roles and scopes](/reference/access/#roles).

`POST /api/tokens` accepts a name and scopes and returns the secret once. `PUT /api/tokens/:id/scopes` changes an owned token's ceiling. Neither accepts scopes wider than the caller's effective permissions. Token listing includes scopes. The local admin token has instance admin permissions and a null member; its writes are attributed to `local admin`.

Use HTTPS through a reverse proxy for remote access. Browser requests must use an origin accepted by the instance. URL-encode path parameters, including slashes in repository names and qualified loop names. An acknowledgement from an asynchronous action means the server accepted the request; read the corresponding status to learn its outcome.

## Paths and versions

Paths use `/api/...`. The schema’s `info.version` is `unversioned`; `GET /api/version` returns the running release string. The public `/api/ready` endpoint returns 200 after startup recovery and 503 while startup is incomplete.

The reference covers the operator HTTP API, including sign-in, members, and tokens. Static UI assets and the separate signature-verified GitHub webhook listener are outside this contract.

## Configuration capabilities

`GET /api/configuration/capabilities` returns `harnesses` (registered IDs), `efforts` (reasoning levels), and `harnessDetails`. Each detail has an `id`, a display `label`, and a nullable `handoff`. A handoff contains the terminal `command`, a nullable `homeVariable` for a saved session directory, and `gateway`, which states whether the command can resume a gateway-authenticated session. Clients use this metadata for harness labels and resume details.

## SQLite reader health

`GET /api/health` is public and returns `{ "ok": true, "sqliteReader": "worker" }` during normal operation. `sqliteReader` changes to `fallback` while the server uses the main connection and waits to retry worker startup, or `respawning` while a replacement starts and passes its probe. Reads use the main connection in both states. The endpoint returns HTTP 200 throughout recovery; long reads on the main connection can delay responses. The server logs worker failures and retries after 1 second, 5 seconds, 30 seconds, and then every 5 minutes. Recovery resets this delay.

## Polling summaries and detail

`GET /api/overview` returns project and board summaries with item titles, states, labels, counts, and identities. Its runs use `RunSummaryView` and its attempts use `AttemptSummaryView`. `GET /api/desk` uses the same summary types for running, stalled, and recent runs.

Each run summary read uses one read-only snapshot for run state and attempts. The SQLite worker executes these reads so long overview, board, and run-list queries permit transcript appends and health responses to continue. Board reads include history counts, timing, and loop states in that same database snapshot. Concurrent completion and retries preserve consistent run state, attempt outcomes, and operator actions. The overview run list reads open runs and recent closed runs together, so each run appears once. Run detail and evidence use the same snapshot boundary. During SQLite reader recovery, these snapshots use a transaction on the main connection, where long reads can delay responses.

Read `GET /api/runs/:runId` for the run's task, result message, each attempt's task, event payload, and transcript. The task endpoint, `GET /api/projects/:owner/:repository/tasks/:item`, also returns full run and attempt records. The board's **Run again** action reads run detail before submitting the saved task and agent.

Session records in transcripts and usage responses include an optional `pool` resolved at launch and an optional `endpoint` provider name for API-key models. Usage reads the recorded pool; older records without it use the historical harness and model rule. Endpoint names exclude URLs and credentials.

## Pull request changes

The task page lists **Changes** beneath each pull request. Open the disclosure and use **Compare** to select the whole PR or an attempt with recorded commits. Files are collapsed initially, show added and removed counts, and mark test and generated files by path. Patch text does not affect these marks. The latest polled CI checks and review decision appear only for the whole PR. With no recorded attempt changes, **Compare** shows plain text. On phones, long file paths wrap to keep the file name visible. Open a file to read the patch without leaving usine.

Recorded attempt changes remain available after CI fails or a newer push cancels the CI wait. Each result is stored with the producing attempt. A successful retry adds a comparison and retains earlier attempt numbers and commit ranges.

For older records, an upgrade associates the saved step result with its recorded producer. Without a producer ID, the upgrade uses the latest attempt only if its outcome is Succeeded or AwaitingCi. Other older results remain in run detail and are omitted from the comparison selector.

`GET /api/projects/:project/pull-requests/:repository/:item/files` requires read access to the project. Encode the repository (`owner/name`) as one path segment. The query's `scope` selects `PullRequestFiles` for the whole PR or `CommitRangeFiles` for an attempt. Both require `base` and `head` as full commit SHAs. Use the projected PR base for whole-PR reads and the recorded checkout base for attempts. Attempts without a recorded base or whose base equals their head are omitted from the selector. Task detail provides those commit selections in `attemptChanges`, including runs beyond the first history page.

Responses contain the resolved `base`, `head`, `files`, and `filesTruncated`. Each file has paths, status, counts, test and generated marks, and either a text patch with a truncation flag or an omitted patch. GitHub omits patches for some binary and large files. PR lists are limited to 3,000 files and comparisons to 300; a limited list is marked explicitly. GitHub provides no comparison file total, so a comparison with exactly 300 files is conservatively marked as limited. Successful reads are cached on the server by commit selection and in the browser without automatic refetch. The server cache holds up to 64 MiB of file paths and patch text and evicts the least recently read responses first. A response larger than that budget is returned without server caching. Task live updates supply PR base and head SHAs, so retargeting a PR refreshes its changes even when its head stays the same.

Open PRs recorded before comparison bases were polled are fetched once on the next poll, including when GitHub reports no changes. This refresh is persisted across restarts. Until a base and head are recorded, the Changes view says **Pull request base or head not recorded yet**.

A missing PR or unavailable commit comparison returns a `404` error envelope with `FileChangesNotFoundError`. When GitHub answers `404` because the GitHub App installation doesn't cover the repository, the endpoint returns `503` with `ProjectNotInstalledError`; grant the installation access to the repository, then retry. A whole-PR selection whose base or head changed returns `409` with `PullRequestFilesChangedError`; refresh the task before retrying. GitHub rate limits return `503` with `GitHubRateLimitError`.

## Change notices and conditional reads

`GET /api/changes` returns `text/event-stream`. A `change` event contains `{revision, reset, changes}`, where each change has a `kind` and an entity `id`. Notice kinds include projects, items, runs, attempts, workers, configuration, attention, navigation, and activity. Notices contain identifiers only. Event IDs increase monotonically. Send `Last-Event-ID` to resume; a `reset: true` notice requests fresh reads when the cursor is unavailable. The server retains the latest 256 notices and filters live delivery and replay by the current permissions. Idle streams send a heartbeat every 15 seconds without computing read projections. Invalid or expired cursors, server restarts, and subscribers that fall behind produce a reset.

Successful operator JSON reads return an `ETag`. Authentication and setup responses use `Cache-Control: no-store`. Send it as `If-None-Match`; an unchanged response returns HTTP 304 with no body. Validators are private to the authenticated representation.

`X-Usine-View: shell` on `/api/overview` returns navigation and compact task identities. `X-Usine-View: attention` returns attention entries. `X-Usine-View: board` on `/api/projects/:project` returns settled lane counts; read their cards from `/api/projects/:project/lanes/:lane/items?offset=0` in pages of 50. `X-Usine-View: task` on a repository task read returns the first 25 runs and `runsTotal`; read subsequent pages from `/api/projects/:owner/:repository/tasks/:item/runs?offset=25`. Page responses include `nextOffset`, which is null at the end. `GET /api/workers` returns worker configuration and slot usage.

The board representation includes `board.cardedItemKeys` for every linked item with a card, including cards in unloaded pages. Use these keys to distinguish runs without cards from runs on paginated cards.
