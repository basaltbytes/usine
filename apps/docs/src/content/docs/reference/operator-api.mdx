The operator API reads instance state, manages configuration, and operates runs. This reference renders the committed [OpenAPI 3.1 document](/openapi.json). For the contract of a running instance, request `GET /api/openapi.json` from that instance. The schema endpoint is public and contains no instance configuration or credentials.

Token timestamps and device authorization polling intervals use finite JSON numbers.

The server reads request bodies of up to 4 MiB. An operator operation with a larger body returns HTTP 413, and `POST /api/mcp` returns a JSON-RPC parse error. GitHub webhook deliveries have their own limit.

## Authentication

Send an instance token as `Authorization: Bearer <token>`. Browser clients can use the `usine_session` cookie; writes with a session also require `X-Usine-CSRF`. See [Sign in](/guides/sign-in/) for browser sessions, and [Create a device token](/guides/create-a-device-token/) for token issuance. The document marks health, sign-in, and schema operations as public. Each operation's `x-usine-permission` names the permission that it requires: `public`, `read`, `operate`, `maintain`, `admin`, `session` (any credential), `tokens` (token management), `local` (the local admin token), or `setup`. `GET /api/auth/session` returns effective permissions as `{permission, scope}` grants, and `operations` for a device token with an operation ceiling. Roles and token ceilings both limit access; a forbidden operation returns HTTP 403. Lists include only projects with read access.

Viewer requires `read`, operator adds `operate`, and maintainer adds `maintain` on a project. Instance `admin` grants all operations, including membership, bindings, workers, settings, and upgrades. Project resource handlers check the target project in addition to the route requirement. See [roles and scopes](/reference/access/#roles).

`POST /api/tokens` accepts a name, scopes, optional `operations`, and an optional `expiresAt` in epoch milliseconds, and returns the secret once. `operations` lists the operation IDs from this document, such as `operator.approve`, that the token may call; a call to another operation returns HTTP 403, except reading the session, signing out, and public operations, which need no token. `PUT /api/tokens/:id/scopes` changes an owned device token's scopes and, with `operations`, its operation ceiling: an array replaces the ceiling, `null` removes it, and an absent key keeps it. Neither accepts scopes wider than the caller's effective permissions or unknown operation IDs. When the caller has an operation ceiling, the token's resulting ceiling must be part of it, including a ceiling that a scope edit keeps. A device token with an expiry can create, or change the scopes of, only tokens that expire no later than it does. Token listing includes scopes, `operations`, and `expiresAt`, which is null for a device token without an expiry. It also includes `unknownOperations` when a stored ceiling names operation IDs that this document doesn't have, such as an ID that a release renamed; the token can't call them. The first request with such a token after the instance starts logs a warning that names the unknown IDs. The local admin token has instance admin permissions and a null member; its writes are attributed to `local admin`.

Use HTTPS through a reverse proxy for remote access. Browser requests must use an origin accepted by the instance. URL-encode path parameters, including slashes in repository names and qualified loop names. An acknowledgement from an asynchronous action means the server accepted the request; read the corresponding status to learn its outcome.

## MCP tools

`POST /api/mcp` serves the operator operations as MCP tools over Streamable HTTP, with the same bearer token or browser session as other routes. Each tool is named by its endpoint identifier, such as `approve` for `operator.approve`, and takes one object with the path parameters, the query parameters, and `body` for a request body. The tool list contains only the operations that the caller's permissions and operation ceiling permit; `GET /api/changes` has no tool. Each call runs the operation with the caller's credential, so permissions, project checks, and audit apply as they do over HTTP. A result is the JSON response text. usine cuts a successful result at 24 KB and an error at 10 KB, less than Claude Code and Codex show of one tool result, and adds a note that says how to read the rest, such as a narrower operation or a later `offset`. A page of a paged read, of the item read, and of a run's transcript and texts ends before 20 KB of JSON. The overview, project, and task summaries leave out cards, project runs, and run results; the run brief leaves out the event payload and the transcript, and the configuration summary leaves out prompts and personas. A session answers only the credential that opened it, and ends after one hour without a request, or when the caller's tool list changes. A request for a session that ended or belongs to another credential returns HTTP 404, and the client starts a new session. `usine mcp` serves the same tools over stdio. See [Connect an MCP client](/guides/connect-an-mcp-client/).

## Paths and versions

Paths use `/api/...`. The schema’s `info.version` is `unversioned`; `GET /api/version` returns the running release string. The public `/api/ready` endpoint returns 200 after startup recovery and 503 while startup is incomplete.

The reference covers the operator HTTP API, including sign-in, members, and tokens. Static UI assets and the separate signature-verified GitHub webhook listener are outside this contract.

## Configuration capabilities

`GET /api/configuration/capabilities` returns `harnesses` (registered IDs), `efforts` (reasoning levels), and `harnessDetails`. Each detail has an `id`, a display `label`, and a nullable `handoff`. A handoff contains the terminal `command`, a nullable `homeVariable` for a saved session directory, and `gateway`, which states whether the command can resume a gateway-authenticated session. Clients use this metadata for harness labels and resume details.

## Configuration reads

`GET /api/configuration` returns a summary of the configuration entities by kind: projects, repositories, loops with their trigger stream and pause state, agents with their harness and model, workers with their slots, label names, the number of role bindings, settings, and the loop and agent files that failed to load with the reason. It leaves out loop prompts, agent personas, lanes, and preflight results. `GET /api/configuration/entities/:kind/:identifier` returns one entity with its JSON value and its YAML or Markdown text. `X-Usine-View: full` on `/api/configuration` returns everything that the configuration editor reads. `GET /api/configuration/revisions` returns up to `limit` revisions and ends a page before 20 KB of JSON; pass `nextBefore` as `before` to read the next page.

## SQLite reader health

`GET /api/health` is public and returns `{ "ok": true, "sqliteReader": "worker" }` during normal operation. `sqliteReader` changes to `fallback` while the server uses the main connection and waits to retry worker startup, or `respawning` while a replacement starts and passes its probe. Reads use the main connection in both states. The endpoint returns HTTP 200 throughout recovery; long reads on the main connection can delay responses. The server logs worker failures and retries after 1 second, 5 seconds, 30 seconds, and then every 5 minutes. Recovery resets this delay.

## Polling summaries and detail

`GET /api/overview` and `GET /api/projects/:project` return summaries: each project has its lanes with their card counts, and no cards, project runs, or labels. Read a lane's cards from `GET /api/projects/:project/lanes/:lane/items`. `X-Usine-View: full` returns every card, the open runs and the latest 50 closed runs, and the label catalog. Runs in these reads use `RunSummaryView`, and their attempts use `AttemptSummaryView`. `GET /api/desk` uses the same summary types for running, stalled, and recent runs. It returns the running attempts, then the stalled items, then the recent runs, as many as fit 20 KB of JSON, and `omitted` counts the entries of each list that it leaves out; `X-Usine-View: full` returns every entry.

Each run summary read uses one read-only snapshot for run state and attempts. The SQLite worker executes these reads so long overview, board, and run-list queries permit transcript appends and health responses to continue. Board reads include history counts, timing, and loop states in that same database snapshot. Concurrent completion and retries preserve consistent run state, attempt outcomes, and operator actions. The overview run list reads open runs and recent closed runs together, so each run appears once. Run detail and evidence use the same snapshot boundary. During SQLite reader recovery, these snapshots use a transaction on the main connection, where long reads can delay responses.

A task read, `GET /api/projects/:owner/:repository/tasks/:item`, returns the task's items, its lane, `runsTotal`, and its newest runs as `RunSummaryView`, up to 10 KB of them. `GET /api/projects/:owner/:repository/tasks/:item/runs?offset=<n>` returns the other runs in pages. Read `GET /api/runs/:runId` with `X-Usine-View: full` for the run's task, result message, each attempt's task, event payload, and transcript. **Run again** on the board and the task page, and **Edit and retry** on the task page, read run detail for the saved task and agent.

A transcript's `Started` payload has a `parentModel` with the selected Pi parent model, or `null` for an attempt without a parent session.

Session records in transcripts and usage responses include an optional `pool` resolved at launch and an optional `endpoint` provider name for API-key models. Usage reads the recorded pool; older records without it use the historical harness and model rule. Endpoint names exclude URLs and credentials.

## Item text

`GET /api/projects/:owner/:repository/items/:item` returns an issue or pull request of a board task as polling last stored it, with a page of its entries: the body, then the comments and reviews by time, then the review comments by thread. Each entry has its kind, author, and time, its text from `offset`, and the length of its whole text. A page contains up to 20 KB of JSON and can end inside an entry. Pass `next.entry` and `next.offset` as the `entry` and `offset` query parameters to read the next page; `next` is null after the last entry. Polling stores the latest 20 comments and the latest 20 reviews, and the first 10 comments of the first 50 review threads; `omitted` counts the rest, which are on GitHub at `url`. An item that isn't on its project's board returns `404` with `BoardItemNotFoundError`.

## Run brief and transcript pages

`GET /api/runs/:runId` returns the run's brief: the run summary with its waits and attempts, each with its outcome and failure message, and the run's duration and usage. The brief has the first 1,500 characters of the task prompt, of the result message, and of the newest report that an attempt kept, each with the `length` of the whole text. It has no event payload and no transcript. `X-Usine-View: full` returns the run detail that the run page reads, with the latest transcript page; its `after`, `before`, and `attempt` cursors need that header, and a cursor without it returns `400`.

`GET /api/runs/:runId/transcript` returns a page of one attempt's transcript, newest entry first. Each entry has its sequence, time, direction, `kind`, such as `ToolFinished`, `TextOutput`, or `Failed`, the ID of the session that produced it, and its payload as JSON text without the kind and the session. `attempt` selects the attempt and defaults to the newest. A page ends before 20 KB of JSON, and a long entry, such as a large tool output, is cut inside its text: the next page starts at the rest of that entry. Pass `next.attempt`, `next.before`, and `next.offset` as the `attempt`, `before`, and `offset` query parameters to read older entries; `next` is null after the attempt's first entry. The server reads the transcript 20 rows at a time and stops when the page is full.

`GET /api/runs/:runId/text/:part` returns a page of one text of the run, from `offset`: `task`, the effective task prompt; `result`, the result message; `report`, an attempt's report, the newest unless `attempt` selects one; or `event`, the JSON text of the event payload. A page ends before 20 KB of JSON; pass `nextOffset` as `offset` until it is null. A run without the text returns an empty page with `length` 0.

To find why an attempt failed, read the brief, take the attempt's `id` from `run.attempts`, and read `GET /api/runs/:runId/transcript?attempt=<id>`: the first page starts at the attempt's last entries.

## Pull request changes

The task page lists **Changes** beneath each pull request. Open the disclosure and use **Compare** to select the whole PR or an attempt with recorded commits. Files are collapsed initially, show added and removed counts, and mark test and generated files by path. Patch text does not affect these marks. The latest polled CI checks and review decision appear only for the whole PR. With no recorded attempt changes, **Compare** shows plain text, and the panel says whether the PR's attempts pushed no new commits or recorded none. When the PR's base or head changed after the task loaded, **Retry** refreshes the task and loads the latest changes. On phones, long file paths wrap to keep the file name visible. Open a file to read the patch without leaving usine.

Recorded attempt changes remain available after CI fails or a newer push cancels the CI wait. Each result is stored with the producing attempt. A successful retry adds a comparison and retains earlier attempt numbers and commit ranges.

For older records, an upgrade associates the saved step result with its recorded producer. Without a producer ID, the upgrade uses the latest attempt only if its outcome is Succeeded or AwaitingCi. Other older results remain in run detail and are omitted from the comparison selector.

`GET /api/projects/:project/pull-requests/:repository/:item/files` requires read access to the project. Encode the repository (`owner/name`) as one path segment. The query's `scope` selects `PullRequestFiles` for the whole PR or `CommitRangeFiles` for an attempt. Both require `base` and `head` as full commit SHAs. Use the projected PR base for whole-PR reads and the recorded checkout base for attempts. A task read with `X-Usine-View: task` or `X-Usine-View: full` provides attempt commit selections in `attemptChanges`, including runs beyond the first history page. Attempts without a recorded base are left out. Attempts that pushed no new commits are included with a base equal to their head; the task page leaves them out of its selector and says that they pushed no new commits.

Without `X-Usine-View: full`, a response contains the files from the `offset` query parameter, as many as fit 20 KB of JSON and at most 100, with `total` and the `nextOffset` of the next page, which is null after the last file. A first file whose patch alone is larger than the page has its patch cut and marked truncated. The web app sends `X-Usine-View: full` and receives every file with its whole patch.

Responses contain the resolved `base`, `head`, `files`, and `filesTruncated`. Each file has paths, status, counts, test and generated marks, and either a text patch with a truncation flag or an omitted patch. GitHub omits patches for some binary and large files. PR lists are limited to 3,000 files and comparisons to 300; a limited list is marked explicitly. GitHub provides no comparison file total, so a comparison with exactly 300 files is conservatively marked as limited. Successful reads are cached on the server by commit selection and in the browser without automatic refetch. The server cache holds up to 64 MiB of file paths and patch text and evicts the least recently read responses first. A response larger than that budget is returned without server caching. Task live updates supply PR base and head SHAs, so retargeting a PR refreshes its changes even when its head stays the same.

Open PRs recorded before comparison bases were polled are fetched once on the next poll, including when GitHub reports no changes. This refresh is persisted across restarts. Until a base and head are recorded, the Changes view says **Pull request base or head not recorded yet**.

A missing PR or unavailable commit comparison returns a `404` error envelope with `FileChangesNotFoundError`. When GitHub answers `404` because the GitHub App installation doesn't cover the repository, the endpoint returns `503` with `ProjectNotInstalledError`; grant the installation access to the repository, then retry. A whole-PR selection whose base or head changed returns `409` with `PullRequestFilesChangedError`; refresh the task before retrying. GitHub rate limits return `503` with `GitHubRateLimitError`.

## Conversations

Members talk to the [supervisor](/reference/configuration/settings/#supervisor) through conversations. A conversation has a scope, the instance or one project, and every member who can read that scope can read it; for any other caller, it doesn't exist and returns `404` with `ConversationNotFound`. Starting a conversation, posting, and canceling need `operate` on the scope, a member credential, and a ready supervisor. `GET /api/conversations/status` returns `ready`, or `setup-required` with the reason, such as no `settings.supervisor` or no container runtime on the host. While the supervisor isn't ready, a post returns `409` with `SupervisorNotReady`.

`POST /api/conversations` takes a scope, an optional `anchor` with a `kind` and a `reference`, an optional title, and the first message. usine stores the anchor's kind and reference without reading them, and adds a `key`: the lowercase hex SHA-256 of the JSON array `[kind, reference]`. `GET /api/conversations` lists the conversations that the caller can read, latest activity first. Each has its last turn, or null before the first, the sequence of its last message, `lastActivity`, a one-line `preview` of the last message of at most 140 characters, and `unread`; `?anchor=<key>` keeps those with that key. A message has a JSON `body`, a `format` such as `markdown`, and an optional `reply.format` that the answer is asked to use; usine doesn't check either format.

For a member, `unread` is `true` when the conversation has a message from someone else, the supervisor or another member, or a failed turn, after the member's read marker. The member's own messages never make a conversation unread. For a credential without a member, `unread` is null. `POST /api/conversations/:conversation/read` with `{"through": <sequence>}` moves the caller's marker to that message, or to the last message if `through` is later. It needs a member credential and `read` on the scope. A marker never moves back, and marking read emits no change notice.

Each message queues a turn. A conversation runs one turn at a time, in message order, so a message posted during a turn waits for it. A turn's credential is read-only: it has `read` on the conversation's scope, within the current permissions and operation ceiling of the device token or browser session that posted its message. It can't call an operation that needs `operate`, `maintain`, or `admin`, or any conversation route; the turn's calls of those operations become permission requests, described below. usine checks this again at every request of the turn, so revoking the posting token ends the turn's access. A queued turn whose token was revoked, or whose member lacks `operate` on the scope, fails with the reason. Signing out of a browser session doesn't affect a turn. API responses show who posted a message, never the credential. The turn's context is the member's login and the turn's grants, the current time, the project, and, as data that the context says isn't an instruction, the anchor and up to 20 entries of **Needs attention**; the supervisor reads everything else through its tools. `GET /api/conversations/:conversation/events?after=<sequence>` returns up to 200 session events after `after`, such as text and tool calls, with `next` for the following read. Each change to a conversation emits a `conversation` change notice with its ID. Canceling a running turn stops its session and keeps its events. After a restart, a turn that was running is `failed` with the `Interrupted` failure, and queued turns run. No turn has a time or token limit.

### Permission requests

A turn has a tool for every operator operation that needs `operate`, `maintain`, or `admin`, within the posting token's operation ceiling. Members, tokens, provider logins, setup, authentication, and conversation operations have no tool. When the turn calls one, usine resolves the call's target and its project with the turn's read access; a target that the turn can't read, or one in another project than the conversation's, returns an error to the turn and stores nothing. A conversation on a project requests only operations in that project: an operation outside a project, such as an upgrade or a worker operation, returns an error that says to ask in a conversation on the instance. A configuration write needs the permission that the configuration editor checks for the entity: `maintain` on a loop's project, and `admin` for a project or any other kind. A role binding write or a configuration revert returns an error that says a member makes the change in **Configuration**, and stores nothing. A call in a project that a standing grant covers runs at once and returns the operation's result. Any other call runs nothing: usine stores a permission request with the operation, its arguments, the target, and the project, and the tool returns that the request waits for a member.

`GET /api/conversations/:conversation` returns the conversation's `requests`, oldest first. Each has `toolCall`, the `callId` of the turn's `ToolStarted` event of the call, `summary`, `arguments`, `target`, `project`, which is null for an operation outside a project, `permission`, which answering needs on the call's scope, `grantable`, `state`, and `answerable`, which says whether the caller can answer it now. `POST /api/conversations/:conversation/requests/:request/answer` takes `{"answer": "once" | "always" | "deny"}` from a member credential:

- `once` runs the call.
- `always` runs the call and stores a standing grant for the operation in the call's project. Later calls of the operation in that project, from any conversation, run without a request. An operation outside a project returns `400` with `NotGrantable`, and so do the operations that send free text to a coding agent, `intervene`, `editAndRetry`, and `runAgain`, and configuration writes. `grantable` is false for these requests. A grant covers only calls that need the permission of the call it came from.
- `deny` runs nothing.

usine checks the caller's access when they answer, including `deny`, and returns `403` when it doesn't permit the operation in the call's scope. An answer to a request that has one returns `409` with `RequestAnswered`, and an answer in a conversation that the caller can't read or that doesn't exist returns `404`; neither changes anything. An allowed call runs as the member who answered, through the operator API, with a credential that has that member's access at that moment, within the call's scope, and that can call only the allowed operation. The operation's own checks and records apply, so an approval, for example, records that member as the approver. The answer returns the request with its outcome: `Ran` with the operation's result, or `Failed` with its error, such as a `409` from a retry of a run that isn't failed. An allowed call finishes and its outcome is stored even when the caller closes the request. A call that ran when the orchestrator stopped is `Interrupted` after the restart, since usine can't tell whether it changed anything, and usine never runs it again.

When every request of a turn has an answer and the turn has ended, usine posts a message with the `usine` role that lists the outcomes, and queues a turn with the access of the member who posted the original message. That turn's context has each outcome as data: the result of each allowed call, and each denial. The outcomes take at most 48,000 characters: when the results don't fit, usine cuts the longest first and says so in each cut outcome. No tool reads a stored result, so the supervisor reads the target again.

`GET /api/supervisor/grants` lists the standing grants that aren't revoked, in projects that the caller can read, each with its operation, project, the member who allowed it, `createdAt`, `lastUsedAt`, `applies`, and `revocable`. A grant applies only while the access of the member who created it, through the credential they answered with, permits its operation in its project: a member who loses that access or is removed, or whose token is revoked, ends the grant's effect. A grant also covers a call only when the access of the member who posted the turn's message, through the credential they posted with, permits the call; otherwise the call waits for an answer. `DELETE /api/supervisor/grants/:grant` revokes a grant; it needs the access that the grant's operation needs in its project, and revoking a revoked grant changes nothing. `GET /api/supervisor/actions` lists up to 100 allowed calls in conversations that the caller can read, latest answer first, each with its conversation, turn, the member who allowed it, the grant if one covered it, and its outcome. Each change to a grant or an allowed call emits a `permission` change notice. A supervisor turn can't call any of these operations.

## Change notices and conditional reads

`GET /api/changes` returns `text/event-stream`. A `change` event contains `{revision, reset, changes}`, where each change has a `kind` and an entity `id`. Notice kinds include projects, items, runs, attempts, workers, configuration, attention, navigation, activity, conversations, and supervisor permissions. Notices contain identifiers only. Event IDs increase monotonically. Send `Last-Event-ID` to resume; a `reset: true` notice requests fresh reads when the cursor is unavailable. The server retains the latest 256 notices and filters live delivery and replay by the current permissions. Idle streams send a heartbeat every 15 seconds without computing read projections. Invalid or expired cursors, server restarts, and subscribers that fall behind produce a reset.

Successful operator JSON reads return an `ETag`. Authentication and setup responses use `Cache-Control: no-store`. Send it as `If-None-Match`; an unchanged response returns HTTP 304 with no body. Validators are private to the authenticated representation.

`X-Usine-View` selects another representation of some reads; without it, the overview, a project, and a task are the summaries that [Polling summaries and detail](#polling-summaries-and-detail) describes. `X-Usine-View: full` on `/api/overview`, `/api/projects/:project`, or a task read returns every card, run, and label, and every run's comments and commit ranges. `X-Usine-View: shell` on `/api/overview` returns navigation, the projects' runs, and compact task identities. `X-Usine-View: attention` returns attention entries. `X-Usine-View: board` on `/api/projects/:project` returns settled lane counts; read their cards from `/api/projects/:project/lanes/:lane/items?offset=0`. `X-Usine-View: task` on a task read returns the first 25 runs, `runsTotal`, and every run's comments and commit ranges; read the other runs from `/api/projects/:owner/:repository/tasks/:item/runs?offset=25`. A page of cards has up to 50 cards and a page of runs up to 25 runs, and a page ends before it passes 20 KB of JSON. Page responses include `total` and `nextOffset`, which is null at the end. `X-Usine-View: full` on `/api/runs/:runId` returns the run detail with its transcript, on `/api/configuration` the configuration as the configuration editor reads it, on `/api/desk` every desk entry, and on a pull request files read every file. `GET /api/workers` returns worker configuration and slot usage.

The board representation includes `board.cardedItemKeys` for every linked item with a card, including cards in unloaded pages. Use these keys to distinguish runs without cards from runs on paginated cards.
