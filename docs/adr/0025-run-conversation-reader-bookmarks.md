# Run conversation reader bookmarks belong to the browser

The Run drawer restores a reader's conversation filter, disclosures and reading position after closing or refreshing. These choices describe one reader's browser, so they use browser storage keyed by Run identity. They do not change the durable Transcript or add operator API fields.

The existing TanStack Query cache remains the owner of fetched transcript pages. Closing the drawer can reuse that cache; refresh starts with the newest page and retrieves earlier pages through the drawer's existing mutation. The projection's Attempt/session/call identities identify tool rows, and transcript sequences identify notices. A bookmark contains one of those identities, its reading surface (row, completed group or result), and the surface's offset relative to the viewport. Completed-group bookmarks reference an original member so inserting earlier members does not invalidate them. The existing disclosure map supplies explicit reader choices; automatic reveals use the same reducer without pretending to be user navigation.

MessageScroller still owns following and explicit navigation. Restoration temporarily disables following, opens the required disclosures and waits for their layout before navigating through the public MessageScroller API. A second animation frame allows scrollability to settle. PreserveReadingPosition resumes after restoration and continues preserving context through transcript updates. Explicit navigation cancels recovery. Automatic history recovery has a 20-page limit; missing rows, request failures and that limit lead to an explained nearest-row position without acknowledging unread activity.

Unread activity uses the last acknowledged raw transcript sequence. The row index deduplicates starts and results, and rebuilding from that checkpoint discovers unread rows on earlier pages after refresh. Reopening at an anchored position cannot acknowledge fresh updates. Following latest in Everything or an explicit jump to latest acknowledges them; filtered views and error navigation preserve them.

No existing browser-persistence adapter was present. The small reader storage boundary uses the pinned Effect Schema decoder, accepts only versioned bounded metadata, and handles inaccessible or exhausted storage with a safe diagnostic. It retains at most 20 Runs for 30 days, 200 recent disclosure choices per Run, and 512,000 serialized characters. Scrolling captures the current row immediately but debounces writes; drawer teardown, page exit and backgrounding flush pending state. Invalid or obsolete bookmarks start with the normal conversation defaults. Transcript contents and tool payloads are excluded.

## Amendment (2026-10-20, #403): the outline folds turns, and the error count counts what the operator must read

The outline listed every message of the Attempt being read by its first sentence, under its session. On a Run of forty turns that list was forty truncated sentences, and the checkpoints that mattered (a blocker, a question, an operator message, a Worker that stopped answering, the outcome) were lost among routine progress notes. The outline now lists an Attempt's checkpoints on one rail in conversation order. Consecutive turns of one session fold into one entry with the session's name and a count, which opens to the sentences on request. Every other checkpoint stays an entry of its own, so nothing the operator needs to find is inside a fold. The reading mark sits on the folded entry while it is closed and on the sentence once it is open. Folds open only when the operator asks, because opening the fold being read on every scroll would bring back the long list. Which folds are open is not part of the bookmark; it resets with the page.

The red count under the outline counted every tool call that returned an error. Agents run commands that fail as part of their work, read the output, and go on, so a Run that succeeded showed "18 errors" and read as broken. The count now holds only what the Run ended with or what the operator must read: each failed Attempt's outcome, the last of which is the Run's failure, every blocker and question, operator input a session refused, and connectivity warnings still open on a running Attempt. A tool call that failed while its Attempt went on afterwards is counted apart in a quieter "recovered" count with its own navigation, so it can still be reached. A failed call the Attempt did not go on from is not counted as recovered: the Attempt's outcome already covers it.
