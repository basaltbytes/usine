# One GitHub App is the factory's identity; worker credentials are per-attempt, single-repo, short-lived

The factory authenticates to GitHub as a single operator-owned **GitHub App**, created via the manifest flow at bootstrap and installed on the managed repos. Everything the factory does on GitHub — polling, board label writes, worker pushes, PRs, comments — acts as that one identity (`<app>[bot]`); the roster's Agents share it, with the acting agent's name stamped in content (comment/PR signature) and the run record. The default manifest requests the minimum the acceptance loops need — `metadata:read`, `contents:read+write`, `issues:read+write`, `pull_requests:read+write`, `checks:read` — and deliberately **excludes `workflows:write`** and all admin scopes; merging is bounded by branch protection, not permission absence. The orchestrator is the only holder of the App private key (a 0600 secrets file in the gitignored `.usine/` runtime folder, env vars taking precedence) and mints ≤1h installation tokens from it: installation-wide for its own polling and UI writes, and **per attempt scoped to that attempt's single repo** for workers. Attachment stays adapter-internal per ADR 0006 — the local executor exposes the token ambiently to the run host; the exe.dev executor uses exe.dev's **native GitHub integration** (per-repo grants attached `--for` the attempt's window, credential injected at their edge, never on the VM). The registry must be covered by the installation: drift surfaces as a per-project error in the needs-you strip while covered repos keep running. Untrusted content is bounded by loop-authored gates — the per-loop approval gate plus CEL over the payload slice (`authorAssociation`) — not by an engine trust construct.

## Considered Options

- **Fine-grained PAT** — simplest bootstrap, but it *is* the operator: agent activity indistinguishable from and unnotified to the human, one shared 5,000 req/hr pool with their own tooling, long-lived with revoke-only bounding. Rejected; a PAT quick-start mode was also rejected to avoid a second credential path.
- **GitHub App** (chosen) — own bot identity and notifications, separate rate pool (5,000 scaling to 12,500), short-lived installation tokens mintable per repo, installation list as per-repo scoping, and the webhook-deliveries feed (issue #18) — at the cost of manifest-flow ceremony (issue #23) and private-key custody.
- **Per-agent GitHub identities** — one App per roster agent gives real per-agent attribution and revocation, but multiplies ceremony and key custody per agent per instance. Out of scope; single identity + in-content signature.
- **Worker credential: static PAT / installation-wide refresh** — a long-lived PAT on workers reopens the radius the App closed; an installation-wide refreshed token widens a compromise to every managed repo. Rejected for the per-attempt single-repo mint.
- **exe.dev attachment mode** — pushing usine's own token through exe.dev's generic HTTP-proxy integration would keep one identity everywhere and deny exe.dev standing access; writing the token in-VM would be uniform with the local adapter. The **native integration** was chosen as zero-code and platform-idiomatic, consciously accepting its two costs (below).
- **`workflows:write` by default** — would let CI-repair agents fix workflow files themselves, but a leaked token could rewrite CI into an exfiltration vector. Excluded; the operator can grant it on the App later.

## Consequences

- Blast radius of a compromised worker: one ≤1h GitHub token (or lapsing edge grant) opening exactly one repo; harness login state (Claude/ChatGPT sessions — bounded by provider-side device revocation); the Pi provider API key (bounded by rotation and provider spend caps); cached clones of that worker's repos. Never on a worker: the App private key, other repos' tokens, the runtime store, other workers' credentials.
- Pushes from exe.dev workers attribute as `exe-dev-github-integration[bot]` (or the operator via `--act-as-user`), not the factory's bot — attribution forks per worker class, carried instead by the agent signature. exe.dev also holds a standing App connection to the granted repos: an accepted second trust root.
- Bootstrap (issue #23) gains the App ceremony: manifest-flow creation, installation on managed repos, key into `.usine/`.
- Polling (ADR 0007) runs on installation tokens the orchestrator self-mints — the operator's personal rate pool is untouched; conditional 304s remain free.
- CI-repair loops cannot edit `.github/workflows/` by default; the failure is a typed push rejection, and the remedy is an explicit operator grant on the App.
- Per-loop permission-subset minting (e.g. read-only tokens for review loops) stays additive: the token-mint API already accepts permission subsets; nothing in the seam precludes it.
