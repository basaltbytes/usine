# Durable CI waits

A developer or fix attempt can end its session after pushing while the run remains open in `AwaitingCi`. The engine stores the pull request number, exact head, fix loop, timeout, and label actions with the run, ends the attempt window, and releases its worker slot. Polling and repository hints reconcile the stored waits without starting a model or reserving a worker; startup excludes these runs from driving fibers and recovers their checkouts as finished work.

A loop's optional `ci` policy is captured with the trigger event, so a configuration edit cannot remove the requirement from an existing run. An ordinary successful answer from a configured loop still waits for the harvested pull request head. Explicit handoffs must match a harvested pull request and its pushed head. Harvesting verifies the named PR's source repository and branch against origin rather than requiring the PR API's head SHA to match: GitHub can update PR metadata minutes after a successful push. Malformed handoffs fail as agent failures; unverified handoffs fail as retryable infrastructure failures. CI snapshots compare the source branch with the PR head and report pending for the branch head while PR metadata lags, preventing old checks from settling or superseding the wait. The configured fix loop and timeout override values in the answer. Completion actions are label additions and removals on items in the same repository, which can be retried safely after a partial write or restart.

Only GitHub's successful aggregate for the recorded head allows completion actions and success. Missing checks remain pending unless GitHub reports the recorded head as `CONFLICTING`. A conflict with no checks uses the same fix event path, with instructions to merge the base branch and resolve conflicts; `UNKNOWN` mergeability continues waiting. Failed checks submit one event to the configured, active PR fix loop with failed job names and at most 12,000 characters of log evidence. The event uses the source run and head as its dedup key and enters ordinary cycle-budget admission, approval, and scheduling. A persisted `ciFailureHead` distinguishes these events from label trigger matches: a queued fix rechecks that the PR remains open at that failing head, rather than requiring the label condition again. An accepted fix closes the source run as `HandedOff`, recording the failed head, reason, fix loop, and fix run ID. Its attempt also ends as `HandedOff`. Both outcomes are neutral: they create no failure attention entry and add no failure or cancellation to statistics. The run page links to the fix run; task lists and board cards show the continuing run's status.

The fix event persists the source wait’s pending completion actions before source settlement. When the fix attempt returns a verified handoff or a required-policy success, its CI wait combines these inherited actions with its own, in that order. Each subsequent fix inherits the combined actions, so the final successful head applies the originating issue and PR label changes.

A fix for the same loop and failed head can open while its source awaits CI because the source attempt has already ended. It still passes ordinary cycle-budget admission. Other events continue to queue behind CI waits. A CI fix queued behind another active run leaves its source awaiting admission; a later observation looks up the admitted fix run ID before evaluating head supersession or check results. If that fix has already pushed or finished, the source still ends as `HandedOff`. If admission exceeds the CI deadline, the source fails. Submission precedes source settlement, so a restart repeats the deduplicated admission and obtains the same fix run ID. Missing or paused fix loops, refused events, and exhausted budgets leave the source failed. Exhausted budgets retain their ordinary operator ask. Existing failed rows keep their recorded outcomes.

A newer PR head cancels the wait without applying its actions, an extension to the supersession rules in ADR 0007 after the attempt has ended. A timeout fails the attempt and run into Needs attention. Settlement checks the waiting state and expected head in one database transaction, preserving the session end time; late observations cannot change a settled or canceled run. GitHub label writes precede local success and may repeat if the process stops between them. GitHub cannot atomically compare a head and mutate labels; the monitor checks the current head before applying actions.

The run page and board show **Waiting for CI** with a link to the PR checks. Review loops can omit `ci` and finish at the end of their session. This replaces agent-side CI watches for configured developer and fix loops while retaining ordinary session completion for other loops.

## Amendment — 2026-11-08: pending CI deadlines

A pending CI deadline records an infrastructure failure because a queued or stalled CI job is outside the agent's execution. The run still requires operator attention, without automatically starting another agent. The exemption from the automatic infrastructure retry rests on the settlement path: CI settlement sets the attempt and run outcome in one transaction and never passes through attempt completion, where the retry decision is made. A CI wait whose CI ran only in part follows the same path. The failure's cause records the CI resolution, pull request, and head. Timeout diagnostics include pending job names and elapsed times, with the matching job's last successful workflow duration when available. Diagnostics have a ten-second limit so GitHub reads cannot stall settlement.

## Amendment — 2026-11-11: partial pending diagnostics (#1052)

The ten-second limit discarded the job list whenever one duration history read was slow, which is when GitHub degrades and the diagnostic matters most. History reads now stop seven seconds after the diagnostic starts, or at the first rate limit, and the diagnostic keeps the job names, elapsed times, and durations read before then. The ten-second limit still bounds the whole read. Running jobs come first and the diagnostic counts the pending jobs after the first ten, so a stalled running job isn't hidden behind queued ones. A head pending only on legacy commit statuses lists those statuses. The baseline run must share the pending run's workflow and event, because `push` and `workflow_dispatch` runs can have a different job set; it isn't filtered by branch, because a new pull request branch has no successful run of its own.
