# Executor contract: a one-shot run host over a duplex attempt channel

The Worker seam's executor contract provides **preflight** (verify-only readiness with typed capability errors), **scoped preparation** (one cached clone per worker+repo, fetched on demand, and a fresh worktree per attempt), and **cancellation**. Preparation returns a live `PreparedAttempt` that launches its one-shot run host and owns its checkout and credential lifetime. The serializable `AttemptWorkspace` descriptor contains the worker, RunSpec, and worktree location. Closing the owning scope stops any active session and releases the resources; launch also releases them before returning after any terminal outcome. Orchestrator and run host talk over a duplex attempt channel: attempt-scoped, protocol-versioned framed messages — normalized events out, steer/interrupt in — carried by any byte transport (stdio locally, `ssh <vm> -- <cmd>` on exe.dev). The run host's final message is the step result (agent final message plus harvested facts: commits, PRs, comments); the orchestrator persists the event flow as it arrives, and that record is the transcript — no file artifacts leave the worker. Credentials are machine-attached worker capabilities, ambient to the run host and verified by preflight, never carried in a RunSpec or on the channel. Workers are named entries in `usine.yaml` (an implicit local worker when none is declared); the engine assigns attempts, capped by per-worker `maxConcurrentAttempts`, queuing runs as `pending` beyond it.

## Considered Options

- **Persistent worker daemon** — a long-lived usine process per worker, multiplexing attempts and enabling mid-attempt reattach. Rejected for v1: daemon lifecycle, orchestrator↔daemon version skew, and worker-side session state. The envelopes are attempt-scoped and versioned precisely so a daemon transport can carry them later without changing a message.
- **One-shot run host** (chosen) — local = spawn a child process, exe.dev = one SSH exec; crash isolation per attempt, zero worker-side state between attempts, and the channel-loss story collapses into ADR 0002's typed-infra-error retry.
- **Per-run credential injection** — orchestrator passes secrets at spawn. Rejected: secrets transit the channel, and it breaks exe.dev's edge-injected no-token-on-VM design, forking the two adapters.
- **Workspace artifact collection** — shipping declared files (diffs, logs) off the worker before cleanup. Deferred: nothing in the three acceptance loops needs it; result facts plus the transcript cover observe-and-intervene.
- **Fresh clone / persistent checkout per repo** — rejected for slow attempts and for no isolation respectively; cached-clone-plus-worktree takes both wins for a fetch lock and worktree hygiene.

## Consequences

- No reattach in v1: an orchestrator restart or dropped link mid-attempt fails the attempt with a typed infra error, eligible for capped auto-retry as a new Attempt — the same crash story as ADR 0003.
- Cancellation (operator cancel and supersede) is two-stage and idempotent: an interrupt message lets the Pi parent stop children cleanly and flush final events, then a grace timeout, then hard kill. On exe.dev: stop the SSH session, then separately confirm termination of the recorded remote run host before workspace removal.
- Making a worker ready is out-of-band and adapter-specific — guided setup locally, a baked VM image on exe.dev; harness login (Claude/ChatGPT OAuth) is always the operator's task. Version skew between orchestrator and a baked image surfaces at preflight, not mid-run.
- Anything durable an agent produces must be pushed to GitHub or said on the channel — the worktree is gone after the attempt, on success and failure alike.
- A `worker:` selector on loops stays a later additive field (workers are name-keyed), the same pattern that keeps repo-scoped loop files possible (ADR 0001).
- exe.dev fits without leakage: lobby commands are adapter internals for machine lifecycle, edge injection is one credential-attachment mode, and completion rides the SSH child's exit.

- **Revised 2026-09-05**: `Executor.prepare` requires an Effect scope and returns a `PreparedAttempt` with `workspace` and `launch(io)`. The separate public `Executor.launch` and `Executor.cleanup` operations are removed. This is an intentional 0.x source compatibility change: callers provide a scope, while adapters register finalizers as they acquire resources. The engine-facing `StepExecutor` interface and capacity lease semantics are unchanged.
- Preparation stays interruptible, including credential attachment and clone/fetch/lock waits. Partial failures close the Attempt's child scope immediately. Clone staging is scoped inside the repository lock so cleanup cannot remove a sibling's in-progress clone. Local tokens are wiped after checkout cleanup; exe.dev attachments reserve their own reference before the remote request, refresh on each acquisition, and release exactly once even if the reply or cleanup fails.
- A live prepared Attempt launches at most once. Its run-host session is tied to the same scope so scope closure interrupts the channel before remote-process, worktree, and credential cleanup. Resource cleanup logs each failure and continues releasing other resources; an operational cleanup failure never changes successful agent work into a retry. Startup sweeps reclaim resources abandoned by a crash.

- The execution budget is supplied as `CheckoutRequest.maxAttemptMinutes` and applied to the live run-host session. Scope cleanup runs after the session timer ends, so a successful Attempt stays successful even if checkout removal or credential release passes the execution deadline. Remote termination and checkout deletion form one guarded cleanup operation: if the remote stop request fails, retain the checkout for recovery while independently releasing its credential grant. A failed partial prepare still rolls back its checkout directly.


## Harness readiness (2026-09-06)

`Executor.preflight(worker, brains)` receives the instance roster. The existing run host implements a separate `--preflight <brain-json>` command, with the `HarnessReadiness` response owned by `@usine/core/agent/capability`. Local and exe.dev adapters transport that command instead of embedding vendor authentication rules in each executor. This extends the existing run-host and harness SDK adapters without adding a worker service or credentials to the Attempt channel. Custom run hosts must answer the probe even if their Attempt protocol version matches. Malformed readiness responses fail as typed run-host capability errors; transport failures and probe timeouts remain retryable infrastructure failures because they do not establish a capability gap.

Preparation repeats the assigned brain’s probe before credential acquisition and checkout mutation, covering roster edits and later logouts. Capability failures require operator action, using the same non-retryable `AgentFailure` classification as unsupported models and unavailable billing pools. The run host probes Codex’s exact verified CLI versions and ChatGPT account, Claude’s worker-provisioned CLI and subscription login, and Pi’s installed SDK with model-specific API-key authentication. Claude’s Agent SDK explicitly launches the same `claude` executable the probe checks. These checks start no prompt and never install tools or initiate login; normal credential inspection can refresh existing credentials.

Codex 0.144.0 remains the pinned protocol conformance baseline; 0.153.4 is also supported after generated-type review and live adapter contracts. Codex child completion includes graceful app-server shutdown through stdin EOF: turn interruption can leave background terminals alive, and immediate process signals bypass the app server’s thread cleanup in stdio mode. The adapter waits for that bounded shutdown before publishing a terminal result, with logged forced termination on timeout.

## Amendment (2026-10-08, #176): reattach is in; the run host serves remote Workers only

The local Worker no longer launches a run host. Each Attempt's Pi parent runs in the orchestrator process as a pi-durable task behind `AttemptRuntime` (`@usine/durable`), and the executor keeps what it already owned: preflight, the worktree, credentials, salvage, and harvesting commits and pull requests after the parent finishes. The reason is the one recorded in `docs/research/pi-durable.md`: a durable task commits every turn and tool call before it is shown, so an orchestrator restart can continue the Attempt instead of throwing away its work and spending a retry on a new one.

This reverses "no reattach in v1". At startup the engine asks the executor whether an open Attempt's parent task is still live. A live Attempt is reattached: it keeps its id and number, spends no retry, and `prepare` with `reattach` takes over its existing worktree with freshly issued credentials. A parent task that is gone fails the Attempt as before and the next Attempt resumes from its salvage. Startup recovery leaves the worktree of a live open Attempt alone and cancels the live task of an Attempt the engine has already closed. The reattach reads the RunSpec the parent started with from the parent task's stored request (`AttemptRuntime.request`), because harvesting after a reattach still counts commits from the original base, and storage the orchestrator owns is the only place it can trust that base once Workers are remote.

Interrupting a local launch that was not stopped first means the orchestrator is stopping, so the task stays live and the worktree stays on disk. Every other end of an Attempt cancels the task: failure, operator cancel, and runaway ceilings. Operator cancel and a tripped wall-clock ceiling go through one stop with a reason, called before anything interrupts the launch, because interruption alone no longer stops the parent; a tripped token ceiling fails the launch itself. The stop cancels the parent task, waits the interrupt grace for the Attempt to settle, then interrupts its execution. Local preflight probes harnesses in-process with `@usine/agents/preflight`; the run-host executable and protocol version checks remain for exe.dev only.

Nothing that runs for an Attempt inherits the orchestrator's environment, which holds the App private key (ADR 0011). The local executor builds one environment per Attempt (the allowlisted variables, the Attempt's single-repo credential configuration, and the Worker's `TURBO_CACHE_DIR`), passes it as `AttemptRequest.environment` for the parent's children and everything they run, and runs its own harvesting `git` and `gh` commands with exactly that environment. The run host process received the same environment before; moving the parent in-process must not widen it.

The run host and the attempt channel stay as the transport for remote Workers: exe.dev still runs the one-shot run host over SSH, and its `isLive` is always false until its parent moves into the orchestrator too (#176, step 3). Commit and pull request harvesting moved to `@usine/core/step/harvest`, which both the run host and the local executor import, so the two paths cannot drift.

## Amendment (2026-10-11, #176): the Worker is where children run

On every Worker the Pi parent runs in the orchestrator as a durable task, and the Worker is the place its children run; the Attempt's child host says where. The executor passes the child host with each `execute` call, next to the environment, and durable storage never keeps it: it describes this process's SSH client (its options and the agent socket it reaches the VM through), which a restarted process supplies afresh, and a reattachment only needs the stored worktree to know the checkout is its own. Preflight runs the `@usine/agents/preflight` checks where the children will run, with the environment a child gets, so the run host's `--preflight` command and its protocol version check are gone. The exe.dev executor no longer launches the run host: each Claude Code or Codex child is one SSH command on the VM, so exe.dev Attempts reattach after a restart like local ones. An SSH client that exits does not prove its remote command stopped, so each remote child records its pid beside the worktree while it runs, and cleanup, cancel, recovery, and reattach stop every recorded child first. Pi children run their tools in the orchestrator process, so an exe.dev Worker reports a Pi brain as unavailable.

## Amendment (2026-10-11, #176): the run host and the byte protocol are gone

The run host package (`@usine/run-host`, the `usine-run-host` executable) and the protocol-v7 byte framing (the `Start` frame, input frames, and their JSON codecs) are deleted. Every Attempt's Pi parent runs in the orchestrator as a durable task and every Worker only runs its children, so no process on a Worker reads or writes attempt channel frames. The envelopes stay: the durable relay sends the parent's activity as outbound envelopes, each checked by the same `admit` rule, and records operator input as inbound ones, and the transcript stores them with their protocol version. The Pi parent session code in `@usine/agents` (the `AgentRuntime` service, `piParentLayer`, the subagents extension, and `@usine/agents/pi/live`) went with the run host, its only caller; the durable task has its own parent and `subagent` tool.

## Amendment (2026-10-19, #332): a reload preflights the brains it adds

A reload of the instance folder runs `Executor.preflight` on every Worker for each brain that no Agent of the running roster has, before it replaces the roster. A failure refuses the whole reload with `ReloadPreflightError` and keeps the running configuration. Refusing is the rule startup already follows, where a failed preflight stops `usine up`, and the one the reload follows for a changed `workers` or `webhooks` block: while Workers run Attempts, the roster that new Runs use is always one they verified, and the operator reads the failure in the reload result instead of in the first Attempt's `AgentFailure`. Accepting the reload and marking the Agent unavailable would add an unavailable state that Loop evaluation, the scheduler, and the operator surfaces all have to read, for a failure the operator fixes by logging in or editing the Agent file and reloading again. Preparation still probes the assigned brain, which covers a logout after the reload.

## Amendment (2026-10-19, #331): a reload resizes, adds, and removes Workers

A reload now applies three `workers` changes. A new `max_concurrent_attempts` resizes the Worker's slots: a higher count is preflighted with every rostered brain and the new count, because the memory check divides the machine's memory by that count, and its slots take waiting Runs at once; with a lower count the Worker takes a new Attempt only while it runs fewer Attempts than the new count, and each extra slot retires when its Attempt ends. A new Worker of the executor's kind gets the startup preflight and takes Attempts once it passes. A removed Worker takes no new Attempt, its running Attempts finish, and it leaves `StepExecutor.workers` with its last Attempt, so its leftovers can be discarded from then on. A failed preflight refuses the whole reload, as the 2026-10-19 amendment above set for brains. No time limit applies to a retiring slot or a removed Worker: the reload changes only where new Attempts run, and running Attempts end as they would without it.

The scheduler counts leases per Worker against a capacity in one transactional reference, and one transaction takes the earliest reservation together with a free slot. Resizing is then a change of capacity, and retiring needs no slot token to find and remove.

Every other `workers` change still refuses the reload with `RestartRequiredError`, which names the field: a changed `kind`, `destination`, `identity_file`, `port`, `root`, or `gateway`, a renamed Worker, and a new Worker of another kind. The SSH executor builds each Worker's machine, the Gateway forwards, and the admin clients when its layer builds and reads the admin tokens once at startup, so changing them under running Attempts would leave those Attempts' cleanup and credential renewals on a machine the executor no longer knows; one executor runs every Worker, so another kind needs another executor (#228). A rename is a removed Worker and a new one on the same machine: the old name's Attempts would keep running while the new name takes its full count, so the machine would run more Attempts than either count allows, and the old name's leftovers would no longer be reconciled at startup. For the same reason the SSH executor cannot take a new Worker after it starts, so a reload adds back only an SSH Worker that `usine up` started with and keeps a removed Worker's forward until it stops (#387).

## Amendment (2026-10-19, #277, #382): the harvest records the comments and reviews an Attempt posted

`harvestFacts` records a `Comment` fact for each comment and review the Attempt posted on its Run's Item, with its URL and its kind: a comment in the conversation of the issue or pull request (`issue-comment`), a submitted pull request review (`review`), or a comment on the pull request's diff (`review-comment`). It runs in the same harvest as commits and pull requests, through the same `git` and `gh` runner in the Attempt's checkout and environment. The Item is the `number` and `url` of the Run's payload. The harvest asks GitHub's REST API for the Item's comments and, on a pull request, its reviews and review comments, and keeps those written by the login of the Attempt's own credential since the Worker prepared the checkout. The RunSpec records that time as `preparedAt`, and a reattached Attempt reads it back from the stored request with `baseCommit`. A schedule Run has no Item, and an Attempt prepared before `preparedAt` existed has no start, so neither asks GitHub. As with pull requests, a GitHub failure or a ten-second stall keeps the commits, records no comment, and logs a warning.

The login is the one GitHub's GraphQL `viewer` returns for the Attempt's own credential, not one derived from the App's slug. Each Worker kind writes as the credential it gives the Attempt: local and SSH Workers write as the App's bot through the installation token or the Gateway, and an exe.dev Worker writes as exe.dev's integration bot (#355). Asking GitHub who the credential is gives the right login on every kind without a declared identity per Worker, and the harvest needs nothing beyond the RunSpec it already reads. The Run reader (#353) reads the same writes from the Item's timeline with the App's slug. The harvest does not reuse that query: it runs in the executor with the Attempt's credential rather than the App's, and the timeline can trail a write by seconds, while the harvest runs right after the parent's last turn.

Comments count as delivered work for the rule ADR 0018 added on 2026-10-19: an Attempt whose parent's last turn answered the operator fails only when the harvest holds no commit, pull request, or comment. A released parent whose deliverable is a review or a comment on the Item therefore succeeds (#382).
