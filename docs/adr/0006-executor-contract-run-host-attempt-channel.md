# Executor contract: a one-shot run host over a duplex attempt channel

The executor contract at the worker seam provides **preflight** (verify-only readiness with typed capability errors), **scoped preparation** (one cached clone per worker and repo, fetched on demand, and a fresh worktree per attempt), and **cancellation**. Preparation returns a live `PreparedAttempt` that launches its one-shot run host and manages its checkout and credentials; the serializable `AttemptWorkspace` contains the worker, RunSpec, and worktree location. Closing the owning scope, or launch reaching a terminal outcome, stops the session and releases resources.

The orchestrator and run host talk over a duplex attempt channel of attempt-scoped, protocol-versioned framed messages (normalized events out, steer and interrupt in) on any byte transport: stdio locally, `ssh <vm> -- <cmd>` on exe.dev. The run host's final message, the step result, is the agent's final message plus harvested commits, PRs, and comments. The orchestrator stores arriving events as the transcript; no files leave the worker. Credentials are machine-attached, in the run host's environment, verified by preflight, and never in a RunSpec or on the channel. Workers are named entries in `usine.yaml` (one implicit local worker by default). The engine assigns attempts up to each worker's `maxConcurrentAttempts` and queues the rest as `pending`.

## Considered options

- **Persistent worker daemon** (multiplexed attempts, mid-attempt reattach): rejected for v1 for its lifecycle, version skew, and worker-side session state. Versioned, attempt-scoped envelopes let a daemon transport them later.
- **One-shot run host** (chosen): a child process locally, one SSH exec on exe.dev. Per-attempt crash isolation, no worker state between attempts, and channel loss is ADR 0002's typed-infra-error retry.
- **Per-run credential injection** (secrets passed at spawn): rejected. Secrets would cross the channel, and exe.dev injects tokens at its edge with none on the VM, so the adapters would diverge.
- **Workspace artifact collection** (copying diffs and logs off the worker): deferred. No acceptance loop needs it; result facts and the transcript suffice.
- **Fresh clone, or persistent checkout per repo**: rejected as slow and unisolated. A cached clone with per-attempt worktrees gets both, for a fetch lock and worktree cleanup.

## Consequences

- No reattach in v1: an orchestrator restart or dropped link fails the attempt with a typed infra error, retried automatically (capped) as a new attempt, as in ADR 0003.
- Cancellation (operator cancel, supersede) is two-stage and idempotent: an interrupt lets the Pi parent stop children and flush events, then a grace timeout, then a hard kill. On exe.dev, usine stops the SSH session, then confirms the recorded remote run host ended before removing the workspace.
- Worker readiness is out of band and per adapter: guided setup locally, a prebuilt VM image on exe.dev. The operator does harness logins (Claude or ChatGPT OAuth). Image version skew shows at preflight, not mid-run.
  - _Note, 2026-10-25 ([ADR 0029](./0029-worker-kinds-and-adapter-set.md)):_ this assumes a worker is a long-lived machine. A worker that creates one machine per attempt ([#550](https://github.com/basaltbytes/usine/issues/550), [#551](https://github.com/basaltbytes/usine/issues/551)) has no machine at `usine up` and no operator login on its machines. Its preflight checks what exists before an attempt, such as the provider credential and quota; its harnesses use a subscription session or an API key stored outside the machine ([#549](https://github.com/basaltbytes/usine/issues/549)); and image version skew shows at preparation, when the probe of the assigned brain runs on the new machine. Its cached clone lasts one attempt. The contract doesn't change.
- Agents must push durable output to GitHub or send it on the channel: every attempt's worktree is deleted.
- A `worker:` loop selector can be added later, since workers have names (as with repo-scoped loops, ADR 0001).
- exe.dev fits without leaks: lobby commands are adapter internals, edge injection is one attachment mode, and completion is the SSH child's exit.
- **Revised 2026-09-05**: `Executor.prepare` requires an Effect scope and returns a `PreparedAttempt` with `workspace` and `launch(io)`; public `Executor.launch` and `Executor.cleanup` are removed. In this intentional 0.x source change, callers provide a scope, and adapters register finalizers as they acquire resources; `StepExecutor` and lease semantics are unchanged.
  - Preparation stays interruptible, including credential attachment and clone, fetch, and lock waits. A partial failure closes the attempt's child scope at once. Clone staging is scoped inside the repository lock, so cleanup can't remove a sibling's in-progress clone. Local tokens are wiped after checkout cleanup. An exe.dev attachment reserves its reference before the remote request, refreshes on each acquisition, and releases exactly once even if the reply or cleanup fails.
  - A prepared attempt launches at most once. Its run-host session shares the scope, so closing it interrupts the channel before remote-process, worktree, and credential cleanup. Cleanup logs each failure and continues, and never turns successful work into a retry. Startup sweeps reclaim crash leftovers.
  - The budget `CheckoutRequest.maxAttemptMinutes` applies to the live run-host session. Scope cleanup runs after the session timer, so cleanup past the deadline can't fail a successful attempt. Remote termination and checkout deletion are one guarded cleanup: if the remote stop fails, the checkout is kept for recovery and its credential grant is still released. A failed partial prepare rolls back its checkout directly.

## Harness readiness (2026-09-06)

`Executor.preflight(worker, brains)` receives the instance roster. The run host implements a separate `--preflight <brain-json>` command returning `HarnessReadiness` (`@usine/core/agent/capability`), which the local and exe.dev adapters transport, so no executor embeds vendor authentication rules, and no worker service or credentials join the channel. Custom run hosts must answer it even if their protocol version matches. A malformed response is a typed run-host capability error; transport failures and probe timeouts stay retryable, since they show no capability gap.

Preparation repeats the assigned brain's probe before acquiring credentials or changing the checkout, covering roster edits and later logouts. Capability failures need operator action and are non-retryable `AgentFailure`s, like unsupported models and unavailable pools. The run host probes Codex's exact verified CLI versions and ChatGPT account, Claude's worker-provided CLI and subscription login (the Agent SDK launches that same `claude` executable), and Pi's SDK with the model's API-key authentication. Probes send no prompt, install nothing, and start no login; normal credential inspection can refresh credentials.

Revised 2026-10-24 (#496): Codex 0.159.2 is the pinned protocol baseline, replacing 0.144.0. Preflight accepts 0.159.0 through 0.159.3, which have the same protocol crates as 0.159.2. It also accepts 0.153.4, so running workers pass preflight until they upgrade: its generated types have the same shape as 0.159.2's for every request, response, and notification field that the adapter uses, and it passed the live contracts. Preflight no longer accepts 0.144.0, so a baseline change reviews only the versions that workers run. A Codex child ends with a graceful app-server shutdown by stdin EOF: interrupting a turn can leave background terminals running, and before Codex 0.155.0 a signal in stdio mode skipped the app server's thread cleanup. From 0.155.0, EOF and SIGTERM run the same cleanup within a 45-second deadline. The adapter waits for this bounded shutdown before publishing a result, forcing and logging termination on timeout.

## Amendment (2026-10-08, #176): reattach is supported; the run host serves remote workers only

The local worker no longer launches a run host: each attempt's Pi parent is a pi-durable task in the orchestrator, behind `AttemptRuntime` (`@usine/durable`). The executor keeps preflight, the worktree, credentials, salvage, and harvesting. Per `docs/research/pi-durable.md`, a durable task commits every turn and tool call before showing it, so a restart continues the attempt instead of discarding its work and spending a retry.

This reverses "no reattach in v1". At startup, the engine asks the executor whether each open attempt's parent task is live. A live attempt is reattached (same id and number, no retry spent): `prepare` with `reattach` takes over its worktree with fresh credentials. If the task is gone, the attempt fails as before, and the next resumes from salvage. Startup recovery keeps live open attempts' worktrees and cancels live tasks of attempts the engine already closed. Reattach reads the original RunSpec from the task's stored request (`AttemptRuntime.request`): harvesting counts commits from the original base, and with remote workers only orchestrator storage is trusted for it.

A local launch interrupted without a stop means the orchestrator is stopping, so the task and worktree stay. Every other end cancels the task: failure, operator cancel, runaway ceilings. Interruption alone no longer stops the parent, so operator cancel and a wall-clock trip call one stop with a reason before interrupting the launch; a token trip fails the launch itself. The stop cancels the parent task, waits the interrupt grace for the attempt to end, then interrupts execution. Local preflight probes harnesses in-process with `@usine/agents/preflight`; run-host executable and protocol checks remain for exe.dev only.

Nothing run for an attempt inherits the orchestrator's environment, which contains the App private key (ADR 0011). The local executor builds one environment per attempt (allowlisted variables, the attempt's single-repo credential configuration, the worker's `TURBO_CACHE_DIR`), passes it as `AttemptRequest.environment` to the parent's children and their commands, and runs its own harvesting `git` and `gh` with it, so moving the parent in-process doesn't widen what the run host got.

The run host and channel remain the remote transport: exe.dev still runs the one-shot run host over SSH, with `isLive` false until its parent also moves (#176, step 3). Commit and PR harvesting moved to `@usine/core/step/harvest`, shared by the run host and local executor so they can't diverge.

## Amendment (2026-10-11, #176): the worker is where children run

On every worker, the Pi parent is a durable task in the orchestrator, and the worker runs its children, at the attempt's child host. The executor passes it with each `execute` call, next to the environment. Durable storage never keeps it, since it describes this process's SSH client (options, agent socket to the VM), and reattachment needs only the stored worktree. Preflight runs `@usine/agents/preflight` where children run, with a child's environment, so the run host's `--preflight` and protocol check are removed. The exe.dev executor no longer launches the run host: each Claude Code or Codex child is one SSH command on the VM, so exe.dev attempts reattach like local ones. An exiting SSH client doesn't prove its remote command stopped, so each remote child records its pid next to the worktree, and cleanup, cancel, recovery, and reattach stop every recorded child first. Pi children run their tools in the orchestrator, so exe.dev workers report Pi brains as unavailable.

## Amendment (2026-10-11, #176): the run host and byte protocol are removed

`@usine/run-host`, the `usine-run-host` executable, and the protocol-v7 byte framing (`Start` and input frames, their JSON codecs) are deleted: no worker process reads or writes channel frames. Envelopes stay. The durable relay sends parent activity as outbound envelopes, each checked by the same `admit` rule, and records operator input as inbound ones; the transcript stores them with their protocol version. The Pi parent session code in `@usine/agents` (`AgentRuntime`, `piParentLayer`, the subagents extension, `@usine/agents/pi/live`) went with its only caller, the run host; the durable task has its own parent and `subagent` tool.

## Amendment (2026-10-19, #332): a reload preflights the brains it adds

Before replacing the roster, a reload of the instance folder runs `Executor.preflight` on every worker for each brain no running agent has. A failure refuses the reload with `ReloadPreflightError`, keeping the running configuration, as a failed preflight stops `usine up` and changed `workers` or `webhooks` refuse a reload. New runs always use a roster the workers verified, and the operator sees the failure in the reload result, not in a first attempt's `AgentFailure`. Marking the agent unavailable instead would add a state that loop evaluation, the scheduler, and the UI must read, for a failure fixed by logging in or editing the agent. Preparation still probes the assigned brain, covering a later logout.

## Amendment (2026-10-19, #331): a reload resizes, adds, and removes workers

A reload now applies three `workers` changes:

- A new `max_concurrent_attempts` resizes slots. A higher count is preflighted with every rostered brain and the new count (the memory check divides machine memory by it), and new slots take waiting runs at once. With a lower count, the worker takes attempts only while it runs fewer than the count; extra slots retire as their attempts end.
- A new worker of the executor's kind takes attempts once the startup preflight passes.
- A removed worker takes no new attempt and leaves `StepExecutor.workers` with its last running one; then its leftovers can be discarded.

A failed preflight refuses the whole reload, as in #332. Retiring slots and removed workers have no time limit: a reload changes only where new attempts run. The scheduler counts leases per worker against a capacity in one transactional reference, and one transaction takes the earliest reservation with a free slot, so resizing is a capacity change and retiring needs no slot token.

Any other `workers` change refuses the reload with `RestartRequiredError`, naming the field: a changed `kind`, `destination`, `identity_file`, `port`, `root`, or `gateway`, a rename, or a worker of another kind. The SSH executor builds each machine, gateway forward, and admin client when its layer builds, and reads admin tokens once at startup; changing them under running attempts would leave their cleanup and credential renewals on a machine it no longer knows. One executor runs every worker, so another kind needs another executor (#228). A rename is a removal plus an addition on one machine: the old name's attempts keep running while the new name takes its full count, exceeding both counts, and startup no longer reconciles the old name's leftovers. For the same reason, the SSH executor takes no new workers after it starts: a reload adds back only an SSH worker `usine up` started with, and keeps a removed worker's forward until it stops (#387).

## Amendment (2026-10-19, #277, #382): the harvest records an attempt's comments and reviews

`harvestFacts` records a `Comment` fact, with URL and kind, for each comment and review the attempt posted on its run's item: `issue-comment` (issue or PR conversation), `review` (submitted PR review), or `review-comment` (PR diff comment). It runs with the commit and PR harvest, through the same runner, checkout, and environment. The item is the run payload's `number` and `url`. The harvest lists the item's comments, and a PR's reviews and review comments, through GitHub's REST API, and keeps those by the attempt's bot login since checkout preparation. The RunSpec records that time as `preparedAt` and the login as `botLogin`; a reattached attempt reads both from the stored request with `baseCommit`. Schedule runs have no item, and attempts prepared before `preparedAt` existed have no start, so neither queries GitHub. As with PRs, a GitHub failure or ten-second stall keeps the commits, records no comment, and logs a warning.

The scheduler sets the bot login in the attempt's `CheckoutRequest`, from `Executor.kind`. Local and SSH workers write as the App through its installation token or the gateway: `<slug>[bot]`, the login of the App's bot account, the REST form the run reader matches since #348. exe.dev workers write through exe.dev's GitHub integration (ADR 0011) as `exe-dev-github-integration[bot]` (#355). The bot account also authors the attempt's commits, so an attempt whose account can't be read fails before preparation (ADR 0011, #242). Without a login in the RunSpec (prepared before `botLogin` existed), the harvest asks GraphQL `viewer` for the credential's login and logs which source it used. `viewer` is only the fallback because an installation token has no user and GitHub doesn't document `viewer` for one; a failure would record no comment.

The harvest doesn't reuse the run reader's timeline query (#353, App token): it runs in the executor with the attempt's credential, right after the parent's last turn, and the timeline can lag by seconds.

Comments count as delivered work for ADR 0018's rule of 2026-10-19: an attempt whose parent last answered the operator fails only if the harvest has no commit, PR, or comment. A released parent whose deliverable is a review or comment succeeds (#382).

## Amendment (2026-10-20, #394): the harvest keeps only comments signed by the attempt's agent

Every attempt on a local or SSH worker writes as the App's bot login, so login and window can't separate two attempts on one item. Two loops' runs on one PR, such as a review and its fix, each recorded the other's comments, and under the ADR 0018 rule an attempt that last answered the operator could succeed on another's comment. The harvest now keeps a comment, review, or review comment only if its body, ignoring trailing whitespace, ends with the agent's `githubSignature`: the `— usine agent: <name>` line the prompt asks every agent to end its GitHub comments, issues, PRs, and reviews with. The harvest log counts other bodies as `unsigned`, which explains a missing fact. `githubSignature` is in `@usine/core/agent`, beside the agent it names, because the harvest is in `@usine/core` and can't import `@usine/agents`. `HarvestSpec` reads the RunSpec's `agent`.

The run reader excludes such writes as ambiguous using every attempt's window on the item; passing those windows to the executor would move orchestrator state there for one check. Two concurrent attempts of one agent on one item still sign alike. That's rare: one loop's runs on an item don't overlap, and retries are sequential. #429 tracks the window approach.

## Amendment (2026-10-20, #387): a reload adds SSH workers

The SSH executor keeps its machines in a reference the scheduler updates on each reload, through `SshWorkers` beside the `Executor`, so a reload adds SSH workers like local ones. A new worker joins the executor before its preflight, which runs on its machine through its gateway's forward, and leaves if the reload is refused. Each gateway admin-API forward is scoped: the first worker behind the gateway opens it, the last closes it. A removed worker stays until its last attempt ends, because that attempt's renewals, detach, and cleanup use its machine and forward.

A new worker's gateway admin token is read at the reload that adds it. An unset variable refuses the reload instead of adding a worker that can't attach tokens: a running process doesn't see variables set after it started, so the refusal says to set the variable and restart, or name one the process has. Changed settings of a running worker still refuse the reload, as in #331.

## Amendment (2026-10-21, #429): the harvest leaves out comments posted while another attempt of its agent was open

This replaces the last paragraph of the #394 amendment. `harvestFacts` and `harvestPostedComments` take `windows`, which reads this attempt's window on the item (`startedAt` through `endedAt`) and the overlapping windows of other attempts of the same agent there (`AttemptWindows` in `@usine/core/attempt`). The harvest keeps a signed comment or review only if its posting time (creation, or a review's submission) is in this attempt's window after checkout preparation and in no overlapping window, by the run reader's second-precision rule (`windowHolds`). GitHub's `since` also lists comments posted before the window and edited in it; any attempt could have made the edit, so none records them. Attempts with one login and one signature leave GitHub no way to tell their comments apart, and crediting a comment posted while both were open could let one succeed on the other's work.

The engine reads windows from its run tables (`RunStore.attemptWindows`). The executor passes `Sink.windows` to the harvest, or `RecoverySink.windows` when startup reconciliation harvests a failed attempt. The harvest reads windows after GitHub lists the comments: a later attempt of the agent on the item overlaps this one even if it starts during the harvest, and the engine records its start before its agent can post, so a read after listing has the window of every posting attempt, and an earlier read could miss one. Nor can the RunSpec, built at preparation, contain them.

The same read gives this attempt's end. The engine closes a canceled attempt, recording `endedAt`, before stopping the executor, which harvests while it stops. A same-agent attempt that starts after that end doesn't overlap, so only the canceled attempt's own window excludes comments the newer one posts during the shutdown; the log counts these as `outside`. If windows can't be read, the harvest can't attribute comments: a finished attempt's harvest fails as for a failing `git` command, and an unsuccessful attempt records no comment.

## Amendment (2026-10-24, #470): a free slot goes to the run furthest along the pipeline

Slots went to runs in event order, after reservations that name a worker (#177). With a label pipeline, that order starves the later stages. On 2026-10-21, the operator approved six `start-dev` runs on a worker with two slots. The two pull requests that the first runs opened waited about two hours for review, because each freed slot went to the next `start-dev` run, whose event arrived earlier. Work in progress piled up, and merges, which free the operator's attention and reduce conflicts, came last.

A free slot now goes to the first waiting run in this order (`leaseOrder` in `packages/orchestrator/src/lease-order.ts`):

1. A reservation that names a worker, as before.
2. A run of a loop whose file sets `priority`, higher first.
3. A run with a lane position, later lane first. The position is the first lane, in the repository's `lanes` order, with a label source among the item's labels in the run's event. It's the lane that the item was in when the trigger matched (ADR 0024, 2026-10-21).
4. Any other run, such as a schedule run or a run in a repository without `lanes`.

Event order ranks runs at the same position.

Lanes are the default source because the operator already orders the pipeline in `usine.yaml`, so the common case needs no new setting. The position comes from the event's labels, not the trigger expression: an `if` also names the labels it excludes (`review-pr` excludes `review-passed` and `ready-to-merge`), so it doesn't say which lane a loop serves. A repository without `lanes` gives no position, because its board's proposed lanes are in name order, not pipeline order.

`priority` ranks above every lane instead of on the lane numbers, so a value means the same in every repository, whatever its lane count. To order loops by hand, set `priority` on each of them.

The scheduler reads the position when a run starts waiting, from the current loop file and lanes, so a reload doesn't reorder runs that already wait. `StepExecutor.reserve` takes the run ID, so the lease log and the Overview can name the run. `WorkerStatus.queue` lists the waiting runs in lease order, and the Overview's line for a queued run gives the number of runs ahead of it.

## Amendment (2026-10-24, #495): a storage error fails the running attempts

pi-durable 1.2 fails the session on any storage error, a read included. It aborts the running tasks, which stops their children, closes the harness, and rejects later calls with `SessionFailed`. Version 1.1 reported a failed read and ran the step again, and it marked a session poisoned by a failed commit only in an error message. So `DurableHarness` wrapped the storage to spot poisoning commits, matched the message, reopened the session in place, and counted repeated reports to find a step that couldn't succeed (#179, #215). Version 1.2 settles `harness.closed` with the error instead, and a task whose fault write fails no longer runs again, so the wrapper, the message match, and the report count are gone.

An attempt whose harness fails while it runs fails with an `InfraFailure` whose cause is `DurableStorageFailed`, and the engine retries it from salvage, as it does any infrastructure failure. With 1.1, the attempt continued on the reopened harness: its parent ran its turn again, and the child that the failure stopped ended as an interrupted tool call. Failing the attempt instead records the storage fault on the attempt rather than inside its transcript, bounds a fault that repeats by the attempt cap, and salvages the checkout once the child has stopped. The reopened harness aborts those attempts' tasks before the other tasks resume, so their parents don't run twice.

A storage error before the harness resumes its tasks stops `usine up` with that error: no attempt has run yet, and a reopen would read the same storage. A reopen that fails, or a reopened harness that fails within a minute, stops the harness until a restart, so one unreadable record can't fail it in a loop. The startup check for unreadable conversation documents reads the storage directly, because a failed read through the harness now fails it.
