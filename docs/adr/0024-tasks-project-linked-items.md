# Board tasks join explicitly linked Items and their Run histories

A feature often starts with a development Run on an issue and continues with review and fix Runs on its PR. Independent Item cards lose that continuity when the issue's trigger label disappears. The Board projects a Task from connected Items in one Project, with all their saved Runs in chronological order.

Relationships come from full PR URLs in an issue's observed `closedByPullRequestsReferences` or its saved Run results. URLs must identify a PR in the same repository. Number-only references in PR payloads can refer to another repository and do not establish a relationship. Titles, branches, and prompt text are never used to infer one. Items remain separate until both snapshots and an explicit relationship are available; the existing 500-Item Board window still applies.

The earliest issue number supplies the Task title. The Item with the newest open Run controls the lane. Between Runs, an open PR takes precedence, followed by the latest settled PR, then the originating issue. Existing label/state precedence applies to that current Item. Moves target its explicit GitHub number, and the UI names it. Approvals, failures, and cycle Asks on any member still mark the Task as needing attention.

The Task is a read projection without a stored identity or new execution lifecycle. Run ownership, deduplication, approval, retry, and per-Item cycle budgets stay with their existing records. Connected components avoid duplicate cards when several issues share a PR. The engine supplies all saved Run summaries for visible Items independently of the overview's recent-history limit, and each Run's existing drawer exposes its Attempts and transcript.

The UI reports Run and Attempt counts. It does not derive task cost from account rate-limit snapshots or duration from timestamps that do not record completion.

## 2026-10-20: the Task has a page

A Run that succeeded or was canceled left the card, so the only way back to it was a card that still showed a Run. The Task now has a page at `/projects/<owner>/<name>/tasks/<number>`, and a click on a card opens it. The Task still has no stored identity, so the page is addressed by its originating Item, the earliest issue or, without one, the earliest pull request; any member's number finds the same Task, and the address then names the originating Item. The page reads the Task through the Board projection, so it joins the same Items, places the Task in the same lane, and covers the same 500 newest Items. The comments and reviews it lists come from the Runs' `Comment` facts, which record no time, so each is dated by the end of the succeeded Attempt that recorded it.

## 2026-10-21: a running Run keeps its card in its trigger's lane

A Loop removes its trigger label as its first step, so it doesn't trigger again. While the Run ran, its pull request had no lane label, and the card fell through to a state lane such as Pull requests; the Board looked idle while a review ran ([#467](https://github.com/basaltbytes/usine/issues/467)). While a Task's newest open Run is `Running` and its current Item is open, the Task goes to the first label lane that matches the labels the Item had when the Run's trigger matched. Those labels come from the payload of the Event the Run was opened for, which `RunReader.events` reads for the running Runs. Otherwise, and when no label of that payload routes to a lane, the current Item's labels and state place the Task as before. A Run that has not started does not hold its card: its Agent hasn't changed the labels yet, and the poll revokes it once its trigger stops matching. A label change during the Run, by the Agent or a Board move, places the card once the Run ends. No lane setting names the Loops a lane keeps, because the Event already records where each Run came from.
