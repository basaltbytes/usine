# Customer code runs on EU machines that usine controls and connects to over SSH

exe.dev's control plane, the `ssh exe.dev` lobby every VM command passes through, is in the United States for every account; its terms are governed by California law, and it publishes no data processing agreement ([research note](../research/agent-sandboxes.md), section 1). Customer code checked out and run on an exe.dev Worker therefore leaves EU infrastructure that usine controls, and no agreement covers it. Customer Attempts run instead on EU machines usine controls: an `ssh` Worker kind for any Linux machine the orchestrator connects to over SSH, first rented from Hetzner Cloud in Falkenstein, Nuremberg, or Helsinki under Hetzner's data processing agreement, built from a cloud-init file in the repository and open to SSH from the orchestrator's address only ([#223](https://github.com/basaltbytes/usine/issues/223), stage 1).

The SSH Worker runs Attempts exactly as the exe.dev Worker does: the Pi parent is a durable task in the orchestrator, each Claude Code or Codex child is one SSH command with its pid file beside the worktree, and checkouts, sweeps, salvage, recovery, and reattachment are the same code, shared by both kinds. The kinds differ only in how a machine is found (the lobby for exe.dev, `usine.yaml` for SSH) and in how an Attempt gets access to its repository. The executor contract of [ADR 0006](./0006-executor-contract-run-host-attempt-channel.md) needs no change: credentials stay machine-attached, and making a Worker ready, harness logins included, stays the operator's out-of-band task.

The Attempt's repository access is the one-hour single-repository installation token the orchestrator already mints ([ADR 0011](./0011-github-app-identity-scoped-worker-tokens.md)), written for the Attempt into `<root>/workers/<worker>/credentials/<attempt>` beside the Worker's checkouts the way the local Worker writes it, with mode 700 on the directories and 600 on the files: git's credential helper reads the token file and gh reads its own configuration directory, so running children read the renewed file without restarting. The token is sent on the standard input of the command that writes it, so it is in no process's arguments or environment and is not written to any log, and git and gh output is scrubbed of it before it is kept. It is removed when the Attempt's scope closes, and the first use of a Worker by a new orchestrator process removes whatever an earlier process left.

The file mode keeps other Unix users out, not other Attempts: every Attempt on a Worker runs as the same SSH user, and the path is predictable from the Worker root and the Attempt id, so an Attempt's processes can read the token of any other Attempt running on the same machine at the same time ([#231](https://github.com/basaltbytes/usine/issues/231)). Stage 1 accepts this, and a GitHub token on the machine for up to an hour, because each customer gets its own Worker, so the Attempts that share a machine work for one customer; because each token opens one repository and expires within the hour; because it is the blast radius ADR 0011 already accepts for the local Worker; and because on the existing child host EU Workers can be built in days. Stage 2 of #223, a gateway with a credential-injecting proxy, removes the token from the machine and with it the exposure.

*Note, 2026-10-14:* an SSH Worker can now sit behind a Gateway ([ADR 0027](./0027-gateway-credential-proxy.md), `gateway` on the Worker in `usine.yaml`), and such a Worker has no GitHub token on its machine. The executor attaches each Attempt's token to the Gateway and gives the machine only the Attempt's caller token, which the SSH connection carries in the children's environment and no file or command line contains. Attempts on one machine still run as one user, so one can read another's caller token from its processes and use that Attempt's repository through the Gateway while the attachment is in force, from inside the private network only ([#243](https://github.com/basaltbytes/usine/issues/243)); none can take a GitHub token off the machine. A Worker without a Gateway keeps the posture above.

## Considered Options

- **Keep exe.dev**: the Worker works today, but its control plane and terms stay outside the EU and outside any agreement. Rejected.
- **exe.dev's Frankfurt region or Enterprise BYOC**: the VMs move, but exe.dev still operates the hosts and the lobby. Rejected for the same reason.
- **Gateway first**: no token on the machine from the start, but two to three weeks before any customer code can leave exe.dev. It is stage 2.
- **A Hetzner-specific Worker kind**: it would tie the executor to one provider's API. An SSH destination in `usine.yaml` covers any machine, and creating machines is a script in `infra/hetzner`, outside the executor.

## Consequences

- Pushes from an SSH Worker are attributed to the factory's own App, as on the local Worker; the attribution fork ADR 0011 records for exe.dev does not apply to this kind.
- Each customer gets its own Worker machine, because concurrent Attempts on one SSH Worker can read each other's tokens, as an exe.dev VM has the grants of every repository it runs.
- `usine up` selects the executor from the Worker kind in `usine.yaml`.
