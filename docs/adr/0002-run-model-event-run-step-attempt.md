# Run model: Event → Run → Step → Attempt

usine adapts Inngest's run model rather than n8n's or Temporal's (see [run-model research](https://github.com/basaltbytes/usine/blob/research/run-models/docs/research/run-models.md)): a deduplicated Event owns at most one open Run, the Run's work lives in named Steps with stored results (exactly one in v1), and every execution try is an Attempt under its Step. Dedup keys are derived by the engine per trigger type and never expire — "never act twice on the same state" is a permanent ledger, not Inngest's 24-hour window — and a coarser item key lets a newer Event supersede a stale open run.

## Considered Options

- **n8n's shape** (trigger firing = run, retry = a new linked run) — conflates identity and splinters the history of one piece of work.
- **Temporal's shape** — the business-key uniqueness invariant is borrowed; the replay-determinism regime and server cluster are not, since memoized step results give resumability without them.
- **Inngest's shape as-is** — the closest fit, but its 24 h idempotency window contradicts the permanent guarantee, and its trigger→run coupling hides the Event as a first-class row.

## Consequences

- Run state machine: pending → waiting (per-loop approval gate) → running → succeeded / failed / canceled; failed → running on operator retry (attempt N+1, with optional steering text on the attempt); canceled is reachable from any open state (operator cancel, or supersede).
- An approval is an Event the waiting run consumes — deduplicated and auditable like every other fact, and v1's only waiting reason.
- Loop-authored step names are step identity (mirroring filename = loop identity, [ADR 0001](./0001-loops-live-in-the-instance-repo.md)): renaming a step retires it; prior results stay under the old name.
- Auto-retry applies only to typed infra errors, capped at 2–3 attempts; agent-level failures always wait for the operator.
- Polling cursors are an efficiency detail only — the dedup key is the guarantee.
- **Revised by [ADR 0007](./0007-polling-triggers-content-hashed-events.md)**: supersede acts only on runs with no started attempt; a running attempt always finishes, the newer state re-judged when it ends.
- **Revised by [ADR 0018](./0018-takeover-and-edit-and-retry.md)**: retry's optional steering text grows into a sticky effective context (task text + agent, amendable via edit-and-retry); Attempt rows gain an operator-intervened flag.
- **Revised 2026-09-03**: an approval moves the run from waiting to **queued** (gate passed, no attempt yet) instead of leaving it in waiting until a worker slot frees up. Queued and waiting looked identical on the Board, so an approved run behind a busy worker read as still needing approval and repeat approvals returned success silently; queued is the state an operator sees, and a repeat approval is rejected as an operation on a run past its gate. Supersede and revoke apply to queued as to pending and waiting.
- **Revised 2026-10-19 ([#152](https://github.com/basaltbytes/usine/issues/152), [#342](https://github.com/basaltbytes/usine/issues/342))**: the operator can run a succeeded or canceled run again. A run can succeed and leave its Item unresolved, as when its Agent stopped on a blocker, and a cancel followed by a label round trip within one poll interval is seen only as the state the run already had. The permanent ledger then left one way to act on that state again: change the Item on GitHub so that its content hash changes. Running a run again records a new Event for the same Item state with an identity of the operator's, the dedup key `["operator-run-again", n, <trigger dedup key>]`, where `n` continues the numbers of that state's reopenings ([ADR 0007](./0007-polling-triggers-content-hashed-events.md), #267). The polled Event keeps its key and its run, so polling still never acts twice on one state; a later sighting of the unchanged Item follows the newest reopening and joins the new run. The new run starts with the task text and agent that edit-and-retry can amend ([ADR 0018](./0018-takeover-and-edit-and-retry.md)), and with the step, approval requirement, and cycle limit of the loop file as it is now and the Item's current cycle generation, so the approval gate and the cycle budget apply as they do to a polled Event. A failed run is retried, not run again, and another open run of the same loop on the Item refuses the request, so one loop keeps at most one open run per Item. The Event records the operator login that asked, as an approval records its approver. A paused loop runs again too: pause stops a loop's triggers, and running again is the operator acting on one Item. A sighting whose `updated_at` is newer than the cancel, the other remedy #342 proposed, would have made a timestamp part of an Event's identity, which ADR 0007 keeps out of it.
