# A gateway host attaches credentials to Worker VMs and is their only way out

Worker VMs that usine runs at an EU provider ([#223](https://github.com/basaltbytes/usine/issues/223), stage 2) have no GitHub token and no API key, and they cannot reach the open internet. They are on a private network without public addresses. One gateway VM on that network is their SSH bastion, their DNS resolver, a reverse proxy for GitHub and the LLM providers that adds the credential, and a forward proxy that opens connections only to an allowlist of package hosts. The executor attaches an Attempt's installation token to the gateway for the Worker and the repository at preparation and detaches it at cleanup. `@usine/gateway` is the service; `infra/hetzner/gateway/` creates the host.

The reason is the blast radius of a compromised Worker. With a token on the machine, an agent that is talked into it can push to the repository from anywhere for the token's hour, or hand the token to someone else; with an API key on the machine it can spend the key. With the credential at the gateway, a Worker can use only what the executor attached, only while it is attached, and only from inside the private network. Without a route to the internet, the paths out are the ones the gateway serves, so an agent cannot send a checkout to a host of its choosing. This is the shape of exe.dev's integrations, an edge that checks which VM is calling and adds the credential for the grant attached `--for` the Attempt ([ADR 0011](./0011-github-app-identity-scoped-worker-tokens.md)), without a control plane in the United States.

The gateway decides with a caller token, not with the caller's address. Providers do not document whether a VM on a private network can send packets with another VM's source address, so each Attempt's children send a token that names their attachment, the Worker, and the repository. The gateway issues it with the attachment and signs it with an HMAC key of its own, so the token is the same for every renewal and survives a gateway restart without a table, and it is honored only while that attachment is in force. Each attach gets a new attachment id, so a token copied from one Attempt is refused once its attachment is detached, even when a later Attempt attaches the same Worker and repository. Binding the token to one repository is what lets `gh`'s GraphQL calls, which name no repository in their path, pick the right installation token when one Worker runs Attempts for several repositories at once. Worker tools present the token wherever they already send a credential (`Authorization`, `x-api-key`, or git's `http.extraHeader`), so no tool needs a wrapper.

Traffic between a Worker and the gateway is plain HTTP on the private network, and the gateway speaks HTTPS to the upstream. A certificate authority for the gateway's own names would have to be generated, distributed to every Worker, and renewed; the only client that insists on HTTPS is `gh`, and `gh` speaks plain HTTP over the Unix socket its `http_unix_socket` setting names, which systemd forwards to the gateway. What crosses the private network in the clear is caller tokens, which are useless outside it, and repository contents, which are already on the provider's disks.

The forward proxy pins each tunnel to its name. A `CONNECT` tunnel is opaque, and package registries sit on shared CDN addresses, so a tunnel opened to an allowed name could carry a TLS connection to any other tenant of that address. Before it opens the upstream connection, the proxy reads the client's TLS ClientHello and requires its server name to be the CONNECT host; a ClientHello that names no server, hides it with encrypted ClientHello, names another one, or is not TLS ends the tunnel. Tunnels are for port 443 only, and plain HTTP goes through the proxy's absolute-form relay, which sees the host it sends to. The name is read rather than intercepted because reading it needs nothing on the Worker: interception would need a certificate authority on every Worker that can impersonate any host, which is what this decision rules out below. Package managers and the harnesses send the server name in every ClientHello and do not use encrypted ClientHello, so pinning changes nothing for them.

## Considered Options

- **Envoy with `credential_injector`**: the filter is alpha and its credential is static per route, while usine's rule is per Worker, per repository, and per Attempt window, and changes at every attach and detach.
- **superfly/tokenizer**: the client sends a sealed secret in a `Proxy-Tokenizer` header, which git, `gh`, Claude Code, and Codex do not send without wrappers on the Worker.
- **A TLS-intercepting proxy** (iron-proxy, Squid bump, sandbox-runtime with TLS termination): needs a certificate authority trusted on every Worker that can impersonate any host, which turns a gateway compromise into the ability to read and alter all of a Worker's TLS.
- **A credential on the Worker with IP firewall rules**: stage 1's posture; kept for Workers without a gateway, but it leaves the token and keys on the machine.
- **Our own small proxy** (chosen): the injection rule, which VM, which repository, until when, is usine's own and small; git smart HTTP, the GitHub API, and LLM streaming need verbatim passthrough, not request rewriting, which keeps the service small and keeps pace with what the harnesses send. It is Effect end to end with a platform-free core, as ADR 0012 asks.

## Consequences

- The executor's credential step for a gateway Worker changes from writing a token to attaching it, and its cleanup detaches it; a renewal attaches the new token under the same attachment id before the old one expires.
- Attachments are in memory. After a gateway restart, requests are refused until the executor attaches again, which its next renewal does.
- An LLM request also needs a live attachment, so a Worker spends no API credit outside an Attempt.
- A Worker reaches github.com and the LLM providers only through the gateway. The forward proxy never lists them, because a tunnel is opaque: the gateway could not remove a caller token from it, and a tunnel to github.com would let a Worker push with a credential it was handed in a prompt. Plain HTTP requests the forward proxy relays lose their caller tokens before they leave.
- Package registries on the allowlist can still receive uploads made with a credential an agent was handed; the allowlist keeps that path to registries, which is the residual risk the research note accepts when no secret is reachable from the Worker.
- Inside a tunnel whose ClientHello named the allowed host, an HTTP/2 client may reuse the connection for another name the same certificate covers (connection coalescing, RFC 9113, section 9.1.1), and a CDN that routes by the HTTP `Host` rather than the server name lets a client front another tenant. The operator weighs both when listing a host on a CDN: the names on its certificate and how its CDN routes ([#240](https://github.com/basaltbytes/usine/issues/240)).
- API keys and an OpenAI-compatible key move to the gateway. The Claude subscription login stays on the Worker: Anthropic documents gateways that forward the login from the machine, not one that keeps it ([LLM gateways](https://code.claude.com/docs/en/llm-gateway)). The gateway can send a subscription token, and `test/placeholder-swap` in `@usine/gateway` checks the swap with Claude Code.

## Amendment (2026-10-14, #223): a Gateway per Worker, and the caller token through the SSH connection

A Worker's Gateway is set on the Worker in `usine.yaml`, not once for the factory, because the private network a machine sits on is a fact about that machine. One factory can then keep Workers without a Gateway while others move behind one, and the Workers of two customers can sit behind two Gateways.

The executor sends the caller token to the Worker in the environment of the SSH connection (OpenSSH `SendEnv`, which the Worker's sshd accepts with `AcceptEnv`), never in the remote command line or a file. A command line shows in the process listings of both machines for as long as a child runs, and the executor logs it when a command fails; a file outlives a crashed orchestrator. The variables are the ones the tools read a credential from: `GIT_CONFIG_VALUE_0` for git's header, `GH_ENTERPRISE_TOKEN` and `GH_TOKEN` for gh, and `ANTHROPIC_AUTH_TOKEN` for Claude Code.

The executor also stores each live attachment again every two minutes with its current token. A renewal comes only when the token is about to expire, so after a Gateway restart it alone would leave running Attempts refused for most of an hour.

## Amendment (2026-10-15, #244, #250): the harness logins stay on the Worker

The factories usine runs today pay for Claude Code and Codex with the operator's subscriptions, a Claude plan and a ChatGPT plan ([ADR 0013](./0013-cost-accounting-native-meters-guardrails.md)), not with API keys. For them the gateway is there for the GitHub token and for egress, not for an LLM credential. A subscription login is made with the harness on the machine it runs on, Anthropic documents gateways that forward the login from the machine rather than keep it, the gateway's swap of a Claude subscription token is unverified (#234), and it has no ChatGPT login (#235). So a Worker behind a gateway keeps the harness logins on its machine by default, as a Worker without one does ([ADR 0026](./0026-eu-ssh-worker.md)), and the forward proxy allowlists the hosts those logins call: `api.anthropic.com` and `platform.claude.com` for Claude Code, `chatgpt.com` and `auth.openai.com` for Codex. Holding a provider's credential at the gateway stays an option, set per Worker with `llm_providers`.

The rule in the consequences above, that the forward proxy never lists an LLM provider, becomes: the forward proxy never lists github.com, nor a provider whose credential the gateway holds. A tunnel to that provider would carry the caller token around the gateway, since Claude Code opens connections to `api.anthropic.com` outside `ANTHROPIC_BASE_URL`. For a provider whose login is on the Worker, the tunnel carries the login the Worker already has, and the proxy still pins the tunnel to the listed name.

What this leaves on the machine is the subscription login, which an agent on the Worker can read and spend, as on a Worker without a gateway. It cannot take the login to a host of its choosing: the paths out are still the gateway's.

## Amendment (2026-10-19, #254): the gateway is the Workers' time server

A Worker behind the gateway could reach no time server, so its clock was never corrected after boot and drifted. TLS certificate checks and the harnesses' OAuth token expiry on the Worker compare against that clock. The gateway now runs chrony, which syncs from Hetzner's time servers (`ntp1.hetzner.de`, `ntp2.hetzner.com`, `ntp3.hetzner.net`) and the Debian pool and answers NTP queries from the private network only. Each Worker's systemd-timesyncd asks the gateway's private address, and the Worker's firewall allows UDP port 123 to the gateway and nothing more.

The time server is chrony rather than a relay in the gateway service because the time is the same for every Worker, so the service has no per-caller decision to make, and chrony serves the private network with one `allow` line where a relay would add a UDP listener to a service that speaks HTTP. NTP opens no way out of the private network: chrony answers each query from its own clock and forwards nothing, so a Worker's packets to port 123 end at the gateway, as its DNS queries do.

## Amendment (2026-10-19, #249): the executor keeps its own forward to the admin API

The executor reached a gateway's admin API at `admin_url`, a local port that the operator forwarded through an SSH connection to the gateway (`LocalForward` in the SSH configuration, or `ssh -N -L`). Nothing reopened that forward when it closed: attaches failed, so Attempts failed with `CredentialUnavailableError`, and renewals failed until the token expired.

The executor now opens the forward itself when its layer is built, `ssh -N -L 127.0.0.1:<port>:127.0.0.1:<admin port> <gateway>` with the SSH options of its other SSH clients, and closes it with the layer. When the SSH client exits, the executor starts another one after a pause that doubles from one second up to one minute. A request that finds the forward closed, or that gets no answer through it, has the forward reopened at once and is sent once more; a second failure is the request's failure, and its message says since when the gateway has been unreachable. The executor never stops reopening the forward: the forward lives as long as the executor, and a gateway that comes back after an outage of any length is usable again without a restart.

`usine.yaml` names the gateway's SSH destination (`gateway.destination`), which the operator's SSH configuration resolves like a Worker's `destination`, and the admin API's port on the gateway (`gateway.admin_port`, 7070 by default as on the gateway), instead of a URL. `admin_url` is removed rather than kept beside them: no release had it, the factory's own instance was the only one that set it, and keeping it would keep the hand-run forward, with the failure this amendment removes, as a supported setup.

The local port is one the kernel picks for each SSH client, so the executor's forward never competes with one the operator opens by hand. OpenSSH refuses port 0 for a local forward, so the executor has the kernel pick a free port on 127.0.0.1, releases it, and passes it to `ssh`; with `ExitOnForwardFailure` the client exits if another process took the port in between, and the next client gets another port. The client prints a line through `LocalCommand` once its listener is up, which tells the executor that the forward is open. A `LocalForward` in the SSH configuration for the gateway's host would also apply to the executor's client and make it exit whenever that port is taken, so the gateway's host entry has none.
