# A gateway host attaches worker credentials and is the workers' only way out

Worker VMs that usine runs at an EU provider ([#223](https://github.com/basaltbytes/usine/issues/223), stage 2) have no GitHub token, API key, or internet route, on a private network without public addresses. One gateway VM there is their SSH bastion, DNS resolver, credential-adding reverse proxy for GitHub and the LLM providers, and forward proxy to allowlisted package hosts. The executor attaches an attempt's installation token to the gateway for the worker and repository at preparation, and detaches it at cleanup. `@usine/gateway` is the service; `infra/hetzner/gateway/` creates the host.

The reason is a compromised worker's blast radius. A token on the machine lets a manipulated agent push from anywhere for the token's hour, or hand it on, and an API key there can be spent. With credentials at the gateway, a worker uses only what the executor attached, only while attached, only from the private network, and with no internet route it can't send a checkout anywhere else. This mirrors exe.dev's integrations, an edge that checks the calling VM and adds the credential for the grant attached `--for` the attempt ([ADR 0011](./0011-github-app-identity-scoped-worker-tokens.md)), without a US control plane.

The gateway decides by caller token, not address: providers don't document whether a private-network VM can spoof another's source address. Each attempt's children send a token naming their attachment, worker, and repository, which the gateway issues with the attachment and signs with its own HMAC key. It's stable across renewals, survives a gateway restart without a table, and is honored only while the attachment is in force. Each attach gets a new attachment id, so a copied token is refused after detach, even if a later attempt attaches the same worker and repository. Repository binding lets `gh`'s GraphQL calls, whose paths name no repository, pick the right installation token when a worker serves several repositories. Tools send the token where they already send credentials (`Authorization`, `x-api-key`, git's `http.extraHeader`), with no wrappers.

Worker-gateway traffic is plain HTTP on the private network; the gateway uses HTTPS upstream. A certificate authority for the gateway's names would need generating, distributing, and renewing on every worker, and `gh`, the only HTTPS-insistent client, speaks plain HTTP over its `http_unix_socket` Unix socket, which systemd forwards to the gateway. In the clear are only caller tokens, useless outside the network, and repository contents, already on the provider's disks.

The forward proxy pins each tunnel to its name: `CONNECT` tunnels are opaque and registries share CDN addresses, so a tunnel to an allowed name could carry TLS to another tenant. Before connecting upstream, the proxy requires the ClientHello's server name to be the CONNECT host, and ends the tunnel on a missing name, encrypted ClientHello, another name, or non-TLS traffic. Tunnels are port 443 only; plain HTTP uses the absolute-form relay, which sees its target. Reading the name needs nothing on the worker, while interception needs a worker-trusted certificate authority able to impersonate any host, which this decision rejects below. Package managers and harnesses always send the name, unencrypted, so pinning doesn't affect them.

## Considered options

- **Envoy with `credential_injector`**: alpha, with a static per-route credential, while usine's rule is per worker, repository, and attempt window, and changes at each attach and detach.
- **superfly/tokenizer**: needs a sealed secret in a `Proxy-Tokenizer` header, which git, `gh`, Claude Code, and Codex don't send without wrappers on the worker.
- **A TLS-intercepting proxy** (iron-proxy, Squid bump, sandbox-runtime with TLS termination): needs a worker-trusted certificate authority that can impersonate any host, so a gateway compromise could read and alter all of a worker's TLS.
- **A credential on the worker plus IP firewall rules**: stage 1's posture, kept for workers without a gateway, but the token and keys stay on the machine.
- **Our own small proxy** (chosen): usine's injection rule (which VM, which repository, until when) is small, and git smart HTTP, the GitHub API, and LLM streaming need verbatim passthrough, not rewriting, which keeps the service small and in step with the harnesses. It's Effect end to end with a platform-free core, as ADR 0012 asks.

## Consequences

- For a gateway worker, the credential step attaches the token instead of writing it, and cleanup detaches it. A renewal attaches the new token under the same attachment id before the old one expires.
- Attachments are in memory: after a gateway restart, requests are refused until the executor's next renewal attaches again.
- LLM requests also need a live attachment, so workers spend no API credit outside attempts.
- Workers reach github.com and the LLM providers only through the gateway. The forward proxy never lists them: the gateway can't remove a caller token from an opaque tunnel, and a github.com tunnel would let a worker push with a credential handed to it in a prompt. Plain HTTP requests the proxy relays lose their caller tokens first.
- Allowlisted registries can still receive uploads made with a credential an agent was handed. The allowlist confines that to registries, the residual risk the research note accepts when no secret is reachable from the worker.
- In a tunnel whose ClientHello named the allowed host, an HTTP/2 client may reuse the connection for another name on the same certificate (connection coalescing, RFC 9113, section 9.1.1), and a CDN that routes by HTTP `Host` rather than server name lets a client front another tenant. Before listing a CDN host, the operator weighs its certificate names and routing ([#240](https://github.com/basaltbytes/usine/issues/240)).
- API keys and an OpenAI-compatible key move to the gateway. The Claude subscription login stays on the worker, since Anthropic documents gateways that forward the machine's login, not ones that keep it ([LLM gateways](https://code.claude.com/docs/en/llm-gateway)). The gateway can send a subscription token, and `test/placeholder-swap` in `@usine/gateway` checks the swap with Claude Code.

## Amendment (2026-10-14, #223): a gateway per worker, and the caller token through the SSH connection

A worker's gateway is set on the worker in `usine.yaml`, not once per instance, because a machine's private network is a fact about that machine. Some workers can stay without a gateway while others move behind one, and two customers' workers can use two gateways.

The executor sends the caller token in the SSH connection's environment (OpenSSH `SendEnv`, accepted by the worker's sshd `AcceptEnv`), never in the remote command line, which shows in both machines' process listings while a child runs and in failed-command logs, or a file, which outlives a crashed orchestrator. The variables are those the tools read: `GIT_CONFIG_VALUE_0` for git's header, `GH_ENTERPRISE_TOKEN` and `GH_TOKEN` for gh, `ANTHROPIC_AUTH_TOKEN` for Claude Code.

The executor also stores each live attachment again with its current token every two minutes. Renewals come only near expiry, so alone they would leave running attempts refused for most of an hour after a gateway restart.

## Amendment (2026-10-15, #244, #250): the harness logins stay on the worker

usine's current instances use the operator's Claude and ChatGPT plans for Claude Code and Codex ([ADR 0013](./0013-cost-accounting-native-meters-guardrails.md)), not API keys, so their gateway handles only the GitHub token and egress. Subscription logins are made with the harness on its machine, Anthropic documents gateways that forward the machine's login rather than keep it, the gateway's Claude subscription-token swap is unverified (#234), and it has no ChatGPT login (#235). So gateway workers keep harness logins on the machine by default, like workers without one ([ADR 0026](./0026-eu-ssh-worker.md)), and the forward proxy allowlists the login hosts: `api.anthropic.com` and `platform.claude.com` for Claude Code, `chatgpt.com` and `auth.openai.com` for Codex. Gateway-held provider credentials stay a per-worker option, `llm_providers`.

The rule above that the forward proxy never lists an LLM provider becomes: it never lists github.com, or a provider whose credential the gateway has. Claude Code opens connections to `api.anthropic.com` outside `ANTHROPIC_BASE_URL`, so a tunnel to that provider would send the caller token around the gateway. For a provider whose login is on the worker, the tunnel exposes only that login, still pinned to the listed name.

That leaves the subscription login on the machine, where an agent can read and spend it, as without a gateway. It can't take the login to a host of its choosing: the paths out are still the gateway's.

_Note, 2026-10-25 ([ADR 0029](./0029-worker-kinds-and-adapter-set.md), [#549](https://github.com/basaltbytes/usine/issues/549)):_ this amendment assumes a worker is one long-lived machine, where a login made once serves every attempt. A machine created for one attempt can't keep a login: an image or snapshot contains one refresh token, and the first machine that refreshes it invalidates it for the others. On such machines, the gateway stores the Claude or ChatGPT session by default and sends it in place of the caller token ([#234](https://github.com/basaltbytes/usine/issues/234), [#235](https://github.com/basaltbytes/usine/issues/235)), and an API key in the same provider entry is the alternative. By the rule above, a gateway that has a provider's session doesn't list that provider's hosts, so the long-lived workers behind it use the session too.

## Amendment (2026-10-19, #254): the gateway is the workers' time server

Workers behind the gateway reached no time server, so their clocks drifted after boot, though TLS certificate checks and harness OAuth expiry depend on them. The gateway now runs chrony, syncing from Hetzner's time servers (`ntp1.hetzner.de`, `ntp2.hetzner.com`, `ntp3.hetzner.net`) and the Debian pool and answering NTP only on the private network. Each worker's systemd-timesyncd asks the gateway's private address, and its firewall allows only UDP port 123 to the gateway.

chrony is used instead of a relay in the gateway service: time is the same for every worker, with no per-caller decision, and chrony serves the network with one `allow` line where a relay would add a UDP listener to an HTTP service. NTP opens no way out: chrony answers from its own clock and forwards nothing, so port-123 packets end at the gateway, like DNS queries.

## Amendment (2026-10-19, #249): the executor keeps its own forward to the admin API

The executor reached a gateway's admin API at `admin_url`, a local port the operator forwarded over SSH (`LocalForward` in the SSH configuration, or `ssh -N -L`). Nothing reopened a closed forward, so attaches failed (attempts failed with `CredentialUnavailableError`) and renewals failed until the token expired.

The executor now opens the forward when its layer is built, `ssh -N -L 127.0.0.1:<port>:127.0.0.1:<admin port> <gateway>` with its other SSH clients' options, and closes it with the layer. If the client exits, another starts after a pause doubling from one second to one minute. A request that finds the forward closed or unresponsive reopens it at once and retries once; a second failure fails the request, with a message saying since when the gateway has been unreachable. Reopening never stops, so a gateway back from any outage works without a restart.

`usine.yaml` sets the gateway's SSH destination (`gateway.destination`, resolved by the operator's SSH configuration like a worker's `destination`) and the admin API's port on the gateway (`gateway.admin_port`, 7070 by default, as on the gateway) instead of a URL. `admin_url` is removed: no release had it, only usine's own instance set it, and keeping it would keep the hand-run forward, with the failure this amendment removes, as a supported setup.

The kernel picks each client's local port, so the executor's forward never competes with the operator's. OpenSSH refuses port 0 for local forwards, so the executor has the kernel pick a free 127.0.0.1 port, releases it, and passes it to `ssh`; with `ExitOnForwardFailure`, the client exits if another process took it meanwhile, and the next client gets another. The client prints a line through `LocalCommand` once listening, which signals the forward is open. A `LocalForward` for the gateway's host in the SSH configuration would also apply to this client and make it exit when that port is taken, so the gateway's host entry has none.

## Amendment (2026-10-19, #236): a reload replaces the allowlist and the API keys and keeps the attachments

Attachments are in memory, so a restart refuses every worker's GitHub and LLM requests until the executor stores them again, up to two minutes later, and editing the allowlist or an API key needed a restart that interrupted running attempts. `usine-gateway` now reloads on SIGHUP, which `systemctl reload usine-gateway` sends: it rereads its environment and allowlist files, replaces the allowlist and LLM provider settings, and keeps the attachment store, admin API, listening sockets, and open tunnels.

A reload stops at what running attempts depend on: the domain and listeners, bound into the servers; the caller key, which signs every live caller token, so a new one would refuse them all; and the admin token the executor uses. These change only on restart, and a reload that finds one changed logs it. A tunnel stays open after its host leaves the allowlist, since it was checked at opening and closing it would cut a download; a restart closes all tunnels when needed. An unparsable file keeps the current settings, because a partial allowlist would refuse hosts running attempts use.

systemd doesn't give a running process new `EnvironmentFile=` contents, and refreshes `LoadCredential=` files on reload only from systemd 260, later than Debian 13's 257. So the gateway reads its environment files itself, from the paths in `USINE_GATEWAY_ENVIRONMENT_FILES`, and `secrets.env` is readable by the `usine-gateway` group. Those secrets were already in the service's environment, so the group read adds nothing, and they leave its process environment.

## Amendment (2026-10-25, #528): gh's downloads stay refused, and an attachment learns its repository's new name

gh sends every request through its `http_unix_socket`, so when it follows GitHub's redirect to a download host, for `gh release download` or `gh run download`, the request reaches the reverse proxy, which refuses hosts other than `git.<domain>` and `llm.<domain>`. Serving them would make the reverse proxy fetch allowlisted hosts itself, through the forward proxy's resolver and private-address check: a second way out, with its own copy of the forward proxy's checks. It would fix only release assets and archives, which curl already downloads from `git.<domain>` through the forward proxy ([#527](https://github.com/basaltbytes/usine/pull/527)). Actions logs and artifacts redirect to `results-receiver.actions.githubusercontent.com` and Azure Blob Storage, which no allowlist should list, because a blob host takes uploads to any storage account ([#540](https://github.com/basaltbytes/usine/issues/540)). So the reverse proxy still refuses other hosts, and its refusal for an allowlisted host tells gh users to use curl.

GitHub answers a request for a renamed or transferred repository's former name with a permanent redirect to the new name, which #527 points at `git.<domain>`. The gateway checked the followed request against the caller token's repository and refused it. Now an attachment learns the new name from a 301 or 308 that answers a request whose path named the attached repository, and serves paths with either name until it's detached or expires; a renewal keeps the names. The installation token is issued for the repository's id, so the new name reaches nothing the token couldn't. A path that names no repository, such as `/repositories/ID/...`, teaches no name, because the gateway can't tell which repository GitHub redirected; the token's own scope limits those paths. Attaching by repository id would need the executor to send the id, and the gateway to resolve each name it sees to an id with an API call, for the same outcome.
