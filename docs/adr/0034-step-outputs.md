# Step outputs are JSON documents stored separately from step results

An attempt can produce a document that later steps or readers need after its checkout is removed. A compiled walkthrough can exceed a megabyte, so final-answer markers would require the parent model to reproduce the document as output tokens. Agents instead write typed JSON envelopes under `.usine/outputs/`, and the executor collects them through the checkout's command runner after the parent reports. Preparation excludes `.usine/` from Git commits and salvage.

`StepResult.outputs` contains refs with the output name, opaque type, optional commit, content size, and SHA-256. Bodies are gzip-compressed JSON in `usine_step_outputs`, outside `usine_steps.result`, because run selection reads that result and active task pages refetch it frequently. The engine treats output types as agent-supplied strings rather than maintaining a catalog. The optional commit must match the attempt's pinned base, which is the reviewed head for a pull request run.

The executor collects at most ten files of at most 8 MiB each, with the same limit on each stored content body. Types remain opaque but have a 128 UTF-16 code unit limit so refs stay small. The orchestrator bounds collection stdout and stderr and independently checks the count and content sizes because the checkout can replace its collection command. Parent and child completion instructions include the pinned base commit so retries from salvage can produce valid envelopes. Invalid envelopes, names, JSON, or commits fail the attempt with a file-specific `AgentFailure`; ordinary salvage still preserves its unfinished work. Full documents are included in the durable `StepCompletion` record, so a restart after collection can complete the engine write without the checkout.

`StepOutputStore` owns output persistence. Its SQL adapter uses the application's `SqlClient` and the separate `usine_step_output_migrations` ledger; its memory adapter uses an injected attempt-success reader. ConfigurationStore established this port-and-adapter pattern. The runtime store's step result and the durable attempt record serve different read and recovery needs, so neither existing store owns body reads. Contract tests run against both output adapters.

The engine writes bodies before `finishAttempt`, idempotently by `(attempt_id, name)`. A crash can leave an output row before the attempt's completion commits, so reads expose only rows whose attempt has a succeeded outcome. Replaying completion rewrites the same rows while preserving their creation time. This avoids a transaction across ports; run listings and `usine export-run` read refs without fetching bodies.

The SQL adapter uses Web Compression Streams for gzip, keeping compression independent of Node and available to Cloudflare compositions. SQL tables for output bodies and their migration ledger remain in the runtime database and use its backup procedure.
