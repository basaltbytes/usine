# Away intervention: GitHub-native Asks answered by reaction or reply; questions park the attempt

The single operator must be able to unblock runs from a phone with **zero inbound path** to the orchestrator — so the notification must carry the action, not just the alert, and both ride GitHub. When a run blocks on a run-blocking moment — approval wait, agent-failed attempt, runaway trip, or an agent question — the engine posts an **Ask**: an @mention comment by the App bot on the run's item (the distinct bot identity from [ADR 0011](./0011-github-app-identity-scoped-worker-tokens.md) is what makes the factory's own writes trigger the operator's native GitHub notifications, which the GitHub mobile app pushes). Two lanes: a **yes/no ask** carries a minimal fixed gist — loop, agent, what's needed, typed error class name; never error detail, transcript excerpts, or cost figures, since managed repos can be public — and closes with a reaction on the ask-comment (👍 = approve / retry / restart, 👎 = cancel the run); a **question** posts the agent's question text — what a human dev would ask in-thread anyway — and is answered by a reply comment @mentioning the bot. Both are auth-checked against the operator's GitHub login (captured into `usine.yaml` at bootstrap). Answers are Events — same polling, same content-hash ledger ([ADR 0007](./0007-polling-triggers-content-hashed-events.md)); yes/no answers resume runs between attempts exactly as [ADR 0002](./0002-run-model-event-run-step-attempt.md)'s approval gate, while a question's answer is delivered down the live attempt channel: **ask-and-park** — the attempt stays alive, the Pi parent blocked on its ask tool, so the agent can ask follow-ups and hold a real multi-round clarification, the conversation living on the issue thread. The runaway guard's wall-clock pauses while an ask is open. Only run-blocking moments notify; factory-health warnings (quarantine, registry drift, pool thresholds, webhook misconfig) stay on the in-UI needs-you strip. Delivery sits behind a **notifier seam** so the channel is swappable — bespoke channels (ntfy, Web Push, a desktop shell's native notifications) are additive.

## Considered Options

- **Bespoke push (ntfy / Web Push) as the v1 channel** — no repo noise and covers item-less runs, but adds accounts/config, and with zero inbound path the notification can alert without enabling action. Rejected as primary; additive behind the seam.
- **Deep-link-only notifications assuming Tailscale-class reachability** — makes the web UI the only act surface and reachability a hidden requirement; local-first turns dishonest. Rejected; phone→UI access stays a bonus, never assumed.
- **Label protocol for approval** — rides the payload slice and the label-loop idiom, but a label is item-scoped (ambiguous when two runs wait on one item) and must be stripped after consumption. The reaction on the run-scoped ask-comment won.
- **Comment commands (`/approve`, `/retry`)** — invents a parse vocabulary for what a tap does; only the question lane needs prose, and it needs no commands, just @mention addressing.
- **Ask-and-end for questions** (attempt ends with a typed needs-input outcome; the answer Event starts the next attempt — Inngest's `waitForEvent` shape) — no held workers and restart-proof, but it kills multi-round clarification, which is the point of asking. Parking is cheap at this scale: exe.dev workers are persistent VMs and a local run host is one blocked process. Rejected.
- **Any-operator-comment reply binding** — zero ceremony, but a casual remark on the issue becomes the agent's answer. Replies must @mention the bot; a reply binds to the item's oldest open question.

## Consequences

- **Ask** enters the glossary; the needs-you strip and the ask stream surface the same run-blocking moments. One ask-comment per needs-you transition — no edits, no re-pings.
- GitHub emits no webhook event for reactions: the engine polls open asks' reactions on its own cadence (a tiny targeted request per waiting ask). Replies ride normal item polling + hints (~10s–60s).
- Revises [ADR 0013](./0013-cost-accounting-native-meters-guardrails.md): the runaway wall-clock pauses while an ask is open — waiting on the operator is never runaway (tokens don't accrue while parked anyway).
- Additive to [ADR 0006](./0006-executor-contract-run-host-attempt-channel.md): ask/answer envelope types join the attempt channel. A parked attempt waits indefinitely — no v1 timeout; the operator can always 👎. Channel loss or orchestrator restart while parked is the existing typed retryable failure: the capped auto-retry starts a fresh attempt carrying the prior transcript, so answered questions aren't re-asked, but in-session state is rebuilt — accepted, since v1 has no reattach.
- Additive to [ADR 0005](./0005-pi-parent-agent-layer-team-roster.md): the usine-owned Pi extension gains the ask tool the parent blocks on.
- Bootstrap (issue #23) captures the operator's GitHub login into `usine.yaml`; the @mention target and answer auth both read it.
- Schedule-stream runs have no item to anchor an ask — their blocking moments are strip-only until a bespoke notifier lands (the seam's first customer).

[ADR 0022](./0022-item-cycle-budgets-and-comment-reviews.md) extends this decision with durable Item cycle budgets, operator reset Asks, and comment-only reviews under the shared App identity.

## Amendment (2026-10-18, #241): a question ends its Attempt until the ask tool exists

The ask tool and the GitHub notifier (#36) are not built, and Agents still stopped to ask for decisions: they posted the question, ended their Attempt with a blocker, and their own comment was new Item content, so the Loop opened a new Run that asked again until the cycle budget ran out. Without the ask tool, an Agent asks by opening its final answer with the reserved marker `[usine:question]`. The Attempt ends with a typed `QuestionFailure` that never retries automatically, and the question appears in the Needs you strip. A marker, like `[usine:blocked]`, is the one channel every harness child shares with the parent; reading prose for questions would misfire on any answer that contains one.

The Run's Loop then holds the Item: the first Item state after the question, normally the Agent's own comment, opens no Run. The Item moving on (another content change, such as the operator's reply or a push, or a sighting that does not match) ends the hold, and so do an operator retry and marking the question answered, which re-evaluates the Item's newest state. The hold keys on the first state after the question rather than on any change, because the question's own comment is a change; the operator can always answer from the UI when that heuristic does not fit. This is the ask-and-end shape listed in the options above, with one round of clarification per Attempt.

## Amendment (2026-10-19, #341): a blocker holds the Item like a question

An Agent that hits a blocker it cannot resolve records it on the Item, as the prompt asks, and opens its final answer with `[usine:blocked]`. Its Attempt used to fail with `AgentFailure`, which does not hold the Loop. The blocker comment is new Item content, so the next poll opened a new Run of the same Loop, which usually met the same blocker and posted it again until the cycle budget ran out: the loop the amendment above removed for questions.

A blocker is the same situation as a question. The Agent says it cannot go on until something changes, and it has just written that on the Item. The marker now ends the Attempt with its own typed failure, `BlockedFailure`, which never retries automatically, and the Loop holds the Item as for a `QuestionFailure`: the first Item state after the blocker opens no Run, and another content change, a sighting that does not match, an operator retry, or marking the Run resolved ends the hold. A child's blocker that the parent does not relay fails the Attempt the same way. Leaving blockers to the cycle budget would spend one Attempt and one more comment per round on a blocker the Agent already reported, and the budget is there to stop review and fix rounds that never converge, not to count repeats of a known stop. The other causes of `AgentFailure`, such as a harness that is not logged in or a model that cannot be used, post nothing on the Item, so they do not reopen on their own output and keep their behaviour. 2026-10-19 (#364): a child's harness failure posts nothing on the Item either, so it now reaches the parent as `[usine:failed]` instead of `[usine:blocked]` and ends the Attempt with `AgentFailure`, and only an Agent's own `[usine:blocked]` holds the Item.
