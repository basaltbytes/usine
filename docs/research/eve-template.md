# Prior art: Vercel's eve Software Factory template

Resolves [#2](https://github.com/basaltbytes/usine/issues/2). Question: what does [vercel-labs/eve-software-factory-template](https://github.com/vercel-labs/eve-software-factory-template) actually provide — its primitives, how it drives agents, how it models GitHub issue/PR state, what it assumes about hosting — and what should usine steal or avoid?

**Method.** Cloned the repo at commit `4cb890e` (2026-08-14, "refactor: consolidate the Blob plumbing behind one registry and shared helpers (#6)") and read the source. File citations below are paths inside that repo. Framework claims cross-checked against the eve docs ([eve.dev/docs/introduction](https://eve.dev/docs/introduction)) and the template's own docs site ([ask-foreman.dev/docs/pipeline](https://ask-foreman.dev/docs/pipeline)).

## What it is

"Foreman": a single-repo **software factory** agent built on **eve**, Vercel's filesystem-convention agent framework (`eve` `^0.37.0` in `package.json`; TypeScript, Zod, pnpm, Node 24). It takes work items from GitHub (an issue labeled `factory`, an `@Foreman` mention, a failed check suite on its own PRs, a newly opened PR) and Linear Agent Sessions, moves each through four subagent "stations" — classifier → analyst → implementer → reviewer — and delivers a **draft pull request** on the one configured repository. A person marks it ready and merges (`README.md`, `.github/ARCHITECTURE.md` Overview).

## Primitives: sessions and stations, not loops, tasks, or queues

- **No loop, queue, or scheduler exists.** Every entry point is a webhook that dispatches one isolated session: `onIssue` (label added), `onComment` (mention), `onCheckSuite` (red CI), `onPullRequest` (opened) in `agent/channels/github.ts`, plus `onAgentSession` in `agent/channels/linear.ts`. There is no run database — "There is no application database. Anything that must outlive a session ... belongs in an external store" — and continuous operation ("a sweep schedule ... needs cross-run dedupe state, which needs an external store") is explicitly listed under Future considerations (`.github/ARCHITECTURE.md`).
- **eve's primitives** are filesystem-discovered under `agent/`: Agent (`defineAgent`), Channels, Tools (`defineTool`), Connections (MCP), Extensions (prebuilt tool packs, here `@github-tools/eve-extension`), Skills (Markdown, loaded on demand), Subagents, Sandboxes (`defineSandbox`), and Schedules (unused here). "There is no central registry or wiring file: a tool's name is its filename, a subagent's name is its directory" (`.github/ARCHITECTURE.md`; [eve.dev/docs/introduction](https://eve.dev/docs/introduction)).
- **The pipeline is prompt-orchestrated, not engine-enforced.** The station order, the "never skip a station" rule, the max-2 revision cycles, retry-once-on-malformed-output, and when to open the PR all live in the orchestrator's system prompt (`agent/instructions.ts`, sections "The pipeline", "The review loop"). Code enforces only fragments: eve's built-in free-form agent tool is disabled so the root can't bypass the stations (`agent/tools/agent.ts`), and branch/push safety is in code (below). Everything else is model obedience, backstopped by an eval suite (`evals/`).
- **"Task mode" is the one structural sequencing device.** Each station's `agent.ts` declares a JSON `outputSchema` (e.g. classifier: `type/priority/complexity/actionable/needs_clarification/questions`; reviewer: `verdict: approve|request_changes|reject` with per-criterion evidence — `agent/subagents/*/agent.ts`), which makes every delegation return structured output and **forbids it from pausing for approval or input** — "a design constraint, not an accident" (`.github/ARCHITECTURE.md` Core components).
- **Handoffs**: each delegation message must be self-contained (stations inherit nothing from the root: no instructions, tools, or history). Long documents travel by id as "handoff artifacts" in Vercel Blob; the orchestrator relays only the id, downstream stations `read_artifact` themselves; ids are validated against an anchored pattern so a model-supplied id can't escape the reserved Blob prefix (`agent/lib/artifacts/config.ts`, `agent/instructions.ts` §3).

## How it drives agents

- **Stations are model calls, not coding-agent CLIs.** No Claude Code / codex / external agent binary is invoked anywhere; the "coding agent" is eve's own tool-loop running a Gateway model with sandbox tools. Models are centralized in `agent/lib/models.ts`: implementer on `anthropic/claude-fable-5` ("the station that writes the code gets the strongest coding model"), reviewer deliberately on a **different vendor** (`openai/gpt-5.6-terra-fast`) for independent review; ids are Vercel AI Gateway strings so no provider SDK is wired in.
- **Execution environment**: each repo-facing station has its own **Vercel Sandbox** with a clone of `FACTORY_REPO`. The clone plus optional `FACTORY_SETUP_COMMAND` (e.g. `pnpm install`) run **once per template build** (`factoryBootstrap`); each session pays only a fetch of the current default branch (`factoryOnSession`) (`agent/lib/github/repo-sandbox.ts`, `agent/subagents/implementer/sandbox.ts`).
- **The implementer's only side effect is `push_branch`**, ungated because it is "inert by construction": `validateBranch` refuses `main`/`master`, `refs/*`, `HEAD`, and anything outside a conservative character set; the push targets the literal `https://github.com/<FACTORY_REPO>.git` URL, never the model-writable `origin` remote (`agent/subagents/implementer/tools/push_branch.ts`, `agent/lib/github/git-remote.ts`).
- **Credentials never enter the sandbox**: the GitHub App installation token is injected at the **sandbox firewall** as a header transform on egress to github.com (`brokerPolicy`), applied around each git operation and dropped in a `finally` (`agent/lib/github/git-remote.ts`, `agent/lib/github/repo-sandbox.ts`).
- **Retry/loop bounds are prose plus thread-archaeology**: the CI-fix loop is capped at 2 attempts by having each fresh session *count its own earlier fix-attempt comments on the PR* — "each fresh session's only shared memory is the thread" — and post its attempt comment *before* fixing so a run that dies mid-fix still leaves its mark (`agent/channels/github.ts`, `CI_FIX_TASK`).

## How it models GitHub issue/PR state

**GitHub is the state store; there is none inside the app.**

- The `factory` **label is the trigger**; classification is mirrored back as repo-vocabulary labels; progress is posted as comments; the deliverable is a draft PR with `Closes #N` (`agent/instructions.ts` §3, §7; `agent/channels/github.ts` `FACTORY_INTAKE_TASK`).
- **PR draftness is the state machine.** `createPullRequest` with `draft: true` runs for every caller "because a draft can't merge"; marking ready (`updatePullRequest`) parks on human approval for everyone and is denied unattended; **merge tools are excluded from the tool surface entirely** (`agent/extensions/github.ts`, `agent/lib/github/approval.ts` `shipPolicy`/`createPullRequestPolicy`).
- **Trust is decided at dispatch on the signed webhook, never re-derived from model-readable content** (`agent/lib/trust.ts`): mentions dispatch only for OWNER/MEMBER/COLLABORATOR `author_association` and stamp `attributes.trusted`; label intake verifies the *labeler* holds ≥ triage permission via the API — because GitHub fires `labeled` even for labels attached at issue creation, which issue templates let unauthenticated reporters do — and fails closed (`agent/channels/github.ts` `isTrustedLabeler`). Unattended runs are rewritten to a constructed autonomous principal (`github:foreman-factory`) carrying the intake issue number as an auth attribute.
- **Approval predicates are the authorization policy** (`agent/lib/github/approval.ts`): each returns `not-applicable` (run), `user-approval` (park for a person), or `denied`. Unattended runs are *denied rather than parked* — "nobody is watching to answer, and a server-side denial costs one step instead of a stranded session" — and allowed only labels, comments scoped to their own intake issue (checked against the stamped issue number, not model input), close/reopen (reversible triage), and draft PRs. Two paths to one action share one policy (`updateIssue` with `state` follows `closeIssuePolicy`).
- **Staleness guards in event-driven runs**: the CI-fix task re-reads the PR and check runs fresh and stops "if the checks are green by now, or the failure belongs to a commit that is no longer the branch head" (`agent/channels/github.ts` `CI_FIX_TASK`). The fix loop only fires on PRs whose head branch carries `FACTORY_BRANCH_PREFIX` (`factory/`), so a person's red PR never triggers an uninvited fix.
- **Cross-run memory** is a size-bounded (40k chars) "factory brain" Markdown document in Vercel Blob, keyed by a hash of `FACTORY_REPO` (never model input), readable by every run but **write-denied on unattended runs** so "an untrusted issue body can't write into the context every future run reads" (`agent/lib/factory-brain.ts`, `agent/lib/github/approval.ts` `factoryBrainPolicy`).

## Hosting assumptions

All-in on Vercel; the platform is the architecture (`.github/ARCHITECTURE.md` Deployment & External integrations; `README.md`):

- **Deploy**: `eve deploy` (wraps `vercel deploy --prod`); one-click Vercel deploy button provisions everything.
- **Credentials**: Vercel Connect brokers the GitHub App and Linear OAuth (connector UIDs in env; tokens resolved per call, never exposed to the model). Blob and the AI Gateway authenticate via the project's OIDC token — no static keys anywhere.
- **Storage**: Vercel Blob (preferences, factory brain, artifacts). **Compute**: Vercel Sandbox — pinned "for both local development and production, so the same environment runs everywhere" (`agent/sandbox.ts`). **Models**: Vercel AI Gateway.
- **"Local" dev is thin**: `pnpm dev` runs the same runtime in a TUI, but requires `vercel link` + `vercel env pull` for an OIDC token, and still executes in the *hosted* Vercel Sandbox; webhook surfaces only work against a deployment (`README.md` Local development, `.github/ARCHITECTURE.md`).
- **Single repo, fixed at build time**: `FACTORY_REPO` is required at module load (discovery fails without it), is baked into the orchestrator prompt at build (`agent/instructions.ts`), and keys the sandbox snapshot (`factoryRevalidationKey`); changing the target repo means rebuilding the template (`agent/lib/constants.ts`, `agent/lib/github/repo-sandbox.ts`). Watching N repos means N deployments.

## Answer in one paragraph

The template is not a loop engine and provides no queue, scheduler, or run store. It is a **hardcoded set of event→session rules plus one prompt-orchestrated pipeline**: webhooks dispatch isolated agent sessions, a root orchestrator prompt routes each work item through four schema-constrained subagent stations running in per-build-cloned Vercel Sandboxes, and GitHub itself (labels, comments, branch prefixes, PR draftness) is the entire state model. Its genuinely strong material is the **security and approval architecture** — trust stamped at dispatch, approval predicates as authorization, deny-don't-park for unattended runs, draft-PR ceiling, inert-by-construction push, firewall-brokered credentials — all of it written up with unusual care in `.github/ARCHITECTURE.md`. Its weaknesses, from usine's seat, are that control flow lives in prose, state lives in thread archaeology, and every layer assumes Vercel's hosted platform and exactly one target repository.

## What this means for usine

Read the template as a validation and a foil: its channel hooks are exactly usine's loops, frozen in TypeScript. `onIssue` labeled → pipeline → draft PR is usine's v1 loop 1 (specified issue → PR); `onPullRequest` opened → orienting comment is a degenerate loop 2 (review a PR); `onCheckSuite`/`request_changes` → implementer revision is loop 3 (act on review findings). usine's premise is making those user-authorable files on a multi-repo engine instead of code in a single-repo deployment.

### Steal

- **Trust stamped at dispatch + a single trust authority.** Decide who the caller is once, on the signed webhook, in the trigger layer; stamp it into the run; make one module (`agent/lib/trust.ts`) the only reader. Loop filters and worker policies should gate on those predicates, never re-derive trust from content an agent read. Fits Effect naturally as a context value on the run.
- **Approval predicates as the authorization policy, with three outcomes: run / park for human / deny.** And the killer rule for usine's headless orchestrator: **unattended runs get `denied`, not `user-approval`** — a parked card with nobody watching is a stranded run; a denial resolves in one step. usine's UI "approve" surface should only ever hold runs a human is actually attached to (`agent/lib/github/approval.ts`).
- **Draft PR as the unattended ceiling; merge absent from the tool surface; policy parity across paths** (`updateIssue.state` ≡ `closeIssue`). A clean default write-policy for every usine loop that ends in a PR.
- **Inert-by-construction side effects inside non-interactive workers.** A worker mid-run can't stop for approval, so its tools must be safe ungated: validated branch names, protected branches refused in code, push to the literal URL, never a model-writable remote (`push_branch.ts`, `git-remote.ts`). Directly applicable to usine's local-process executor, where the workspace is model-writable by definition.
- **Credentials brokered at the executor boundary.** The token is injected at the sandbox network layer and never enters the workspace. Make this a requirement of usine's executor seam: the executor interface should hand workers *authenticated egress*, not tokens — trivially true for a local firewall-less process only if usine at least keeps tokens out of the worker env; exe.dev-class remotes can do it properly.
- **The labeler-permission check.** GitHub fires `labeled` for labels set at issue creation, so a label trigger authorizes on the *sender's* repo permission via API, failing closed (`isTrustedLabeler`). Any usine label-triggered loop needs this verbatim, or issue templates become an unauthenticated trigger.
- **Staleness guards as trigger hygiene**: re-read the world before acting; stop if the failure no longer belongs to the branch head. usine's engine can hoist this into the trigger/filter layer (compare event SHA to current head) instead of trusting each prompt to do it.
- **Structured output contracts per stage + artifact-by-id handoffs.** Schema-constrained results (`verdict`, per-criterion evidence) are what makes a run's outcome routable and renderable in an observe/intervene UI; big documents pass by validated id, not by re-pasting through the orchestrator's context.
- **Bounded, write-gated shared memory** (factory brain): if usine grows cross-run repo memory, copy the shape — size-bounded, keyed by config not model input, readable by all runs, unwritable by runs triggered from untrusted content.
- **Safety evals over the write surface**: one shared write-tool list, read-only scenarios asserting none of it was called, a prompt-injection case, a no-push-to-main case (`evals/helpers.ts`, `evals/safety/`). Cheap to port to usine's loop engine as acceptance tests per loop.

### Avoid

- **Prompt-orchestrated control flow.** Station order, retry caps, revision limits, and "when to open the PR" live in the system prompt; evals are the only thing keeping the model honest. usine's core bet is the opposite: the loop (trigger → filter → one run per item, retries, caps) is an engine-enforced Effect program authored as a file; the agent gets judgment *inside* a step, never custody of the loop.
- **GitHub-thread archaeology as run state.** Counting your own past comments to enforce an attempt cap is ingenious and fragile (edited/deleted comments break it, and it costs a read fan-out per event). usine already needs a run store for observe/intervene; own attempt counts, dedupe keys, and run status there, and treat GitHub as the *interface*, not the database. Keep the template's insight, though: durable state must also be *visible* where humans look — mirror status to the thread, don't store it there.
- **No queue, no dedupe, no concurrency control.** Every webhook dispatches an independent session; re-labeling twice runs the pipeline twice; nothing serializes runs per item. The template defers this ("needs cross-run dedupe state, which needs an external store"). For usine this is the product: per-item idempotency keys and per-loop concurrency limits are first-class engine features, not future work.
- **Platform as architecture.** Connect, Blob, hosted Sandbox, Gateway, OIDC — even `pnpm dev` needs a linked Vercel project and runs in the hosted sandbox. usine is local-first: the local process executor is the default backend and remote (exe.dev) is a capability behind the seam, never a prerequisite for development.
- **Single repo baked at build time.** `FACTORY_REPO` in the prompt at build, keying the sandbox snapshot; multi-repo means multi-deploy. usine watches many repos from one orchestrator: repo targeting is runtime data carried by the loop file, never build input. (The per-build clone+install cache is still worth keeping as an *optimization* per repo, not a binding.)
- **A fixed pipeline shape as the engine.** The four stations are the template's one loop, hardcoded. Steal classifier→analyst→implementer→reviewer as a *loop template usine ships*, not as engine structure.

### Irrelevant

- The Linear channel and GitHub↔Linear bridging skill; per-user preference storage; the writing-quality skill; the Vercel deploy-button/marketplace plumbing; bot-name resolution from the GitHub App slug (nice touch, but specific to eve's mention-reply approval flow).
